## 1. 原则

1. **测试不能悄悄跳过。**
   - 每个 Go 模块的默认测试集里禁止出现 `t.Skip`，CI 用 `go test -json` 检查有没有 `"Action":"skip"`。
   - 需要环境的测试放在 build tag 后面。打了 tag 但缺少环境变量时，用 `t.Fatal` 报错，不能跳过。
   - 每个模块有一个测试数量下限文件 `testdata/test-count.min`，通过的测试少于这个数，CI 就失败。
2. **每条测试都要标明它覆盖哪条行为。**
   - 测试函数的注释里写上 01 文档的条目编号，例如 `// covers: H5 T3 BUG-11(fixed)`。
   - §9 的追踪脚本据此检查每个条目是否都有测试；没有测试的条目必须写进豁免表，并说明理由。
3. **与 Python 版"保持一致"和"有意不同"要分开处理。**
   - 01 §15 里的缺陷，Go 版要么修正，要么保持原样，由 §8 的表决定。
   - 保持原样的，测试断言旧行为；修正的，测试断言新行为，并在差分测试的"有意差异清单"里登记。差分测试只对清单以外的部分要求逐字节一致。
4. **不碰真实账号的凭证。**
   - 集成测试只用合成的草稿 key（`d00000000000a000N`），配合假上游和代理夹具。
   - 不复制任何真实的 OAuth 凭据：刷新令牌会轮换，复制会让生产账号失效。
5. **测试不能影响生产。**
   - 所有真机测试都在 ovh 的隔离实例里跑：前缀 `ccg-gt`，控制网 `172.29.255.8/29`，独立的链和目录，参数见 04 §7。
   - 第 6 层的 iptables 测试在一次性的特权容器里新建网络命名空间来跑，不写宿主机的规则。
   - 每一轮测试结束都执行清理，并确认生产的 `CCG-PROXY-BRIDGE` 规则数不变。

## 2. 测试分层一览

| 层 | 内容 | 在哪跑 | 什么时候跑 | 耗时 |
|---|---|---|---|---|
| L0 静态检查 | `gofmt`、`go vet`（本机加 `GOOS=linux`）、规则扫描（§3） | 本机、CI | 每次提交 | 1 分钟内 |
| L1 单元测试 | 控制器 185 项移植测试加新增项；guard 的 policy、API 拒绝、firewall 规则生成、配置解析 | 本机（Windows）、CI | 每次提交 | 1–2 分钟 |
| L2 接口契约 | guard 的真实 HTTP 处理器和控制器的 FakeGuard 读同一组"请求 → 应答"样例；`guardapi` 客户端也用这组样例做解码测试 | 本机、CI | 每次提交 | 1 分钟内 |
| L3 跨语言兼容 | Python 生成的参照向量（三种摘要）、状态文件 Python 与 Go 互读、HTTP 黄金样例差分 | CI（需要 Python 3.12） | 每次提交，直到 Python 源码删除 | 2 分钟 |
| L4 Linux 组件 | guard 的 files 包（`O_NOFOLLOW`、inode、硬链接）、store 的 flock、目录 fsync、权限位 | ovh 一次性 `golang` 容器，或 Linux CI | 每次合并 | 2 分钟 |
| L5 Docker 组件 | guard 的 dockerapi 与 policy 接真实 dockerd：建出的容器 inspect 后逐项核对；exec 帧、拉取和导入的错误、事件流 | ovh 隔离前缀 | 每次合并 guard | 5 分钟 |
| L6 防火墙组件 | 在一次性特权容器的独立网络命名空间里，用 veth、网桥和真实的 `iptables-nft` 验证三条链：放行、拦截、失败关闭、重复应用不变 | ovh 一次性容器 | 每次合并 guard 的 firewall 包 | 3 分钟 |
| L7 系统集成 | 隔离实例中完整的 guard、控制器、网关和假上游：场景见 §4–§6 | ovh 隔离实例 | 每个里程碑，以及每个发布候选版 | 30–60 分钟 |
| L8 安装脚本 | 核心脚本的黄金文件、假 docker 的 9 个分支（04 §2.10）；一次性主机上真实执行三轮 | CI 加一次性主机 | 改核心脚本时 | 20 分钟 |
| L9 生产验收 | 04 §6 的全部清单 | ovh 生产 | S4 和 S5 | 1–2 小时 |

## 3. L0：规则扫描

`scripts/lint-guard.sh`，CI 里执行。下面任何一条命中，CI 就失败：

| 规则 | 防止什么 |
|---|---|
| guard 的 `internal/api` 里出现 `HostConfig`、`Privileged`、`Binds`、`CapAdd` 字面量 | 绕过 policy 包，自己拼容器参数 |
| guard 的 `internal/policy` 以外调用 `dockerapi.CreateContainer`、`CreateNetwork`、`CreateVolume` | 同上 |
| 控制器模块的 `go.mod` 或源码里出现 `docker` 依赖，或引用 `/var/run/docker.sock` | 控制器又拿到 Docker 权限 |
| 默认测试集的源码里出现 `t.Skip` 或 `testing.Short()` | 测试被悄悄跳过 |
| 日志调用的参数里出现 `Token`、`Password`、`Env`、`Body` 等字段名 | 敏感内容进日志 |
| compose 模板里 controller 服务出现 `docker.sock`、`network_mode: host`、`privileged`、`cap_add` | 模板被改坏 |

## 4. L7 系统集成场景

编号规则：

| 前缀 | 类别 |
|---|---|
| `IT-F` | 功能 |
| `IT-S` | 安全负面检查 |
| `IT-X` | 故障注入 |
| `IT-M` | 迁移与回滚 |
| `IT-P` | 性能 |

驱动程序是 ovh 上的 `ccg-it` 测试程序。它用 Go 写，build tag 为 `guardintegration`，放在 `companions/controller-go/integration/`，在 ovh 的 `golang` 一次性容器里运行。它以管理密钥调用隔离控制器的 `127.0.0.1:18787`，与核心调用控制器的方式一致。

- **假上游：** 沿用"离线端到端"的做法。一次性容器里跑一个假的 Anthropic 接口，只返回固定的流式应答。
- **代理夹具：** 沿用 `shared_proxy_fixture.py`，起两个代理，分别记录各自转发了哪些连接，用来判断流量走了哪个代理。

### 4.2 安全负面检查（IT-S）

在 04 §6.3 的基础上，加上只有隔离实例才能做的项目。做法与 04 §6.3 相同：用共享控制器网络命名空间的临时 curl 容器发起访问。

| 编号 | 检查 | 期望 |
|---|---|---|
| IT-S01 | 控制器访问宿主机只监听回环地址的服务（3130、8010、8795） | 超时 |
| IT-S02 | 控制器访问外网 443，以及宿主机公网 IP；控制器解析一个代理域名 | 访问失败；**DNS 解析必须成功**。这一项同时验证 03 §7.4 的假设"内置 DNS 不经过 FORWARD"：ovh 宿主机用 systemd-resolved（`127.0.0.53`），Docker 会改用真实上游，内置 DNS 很可能从容器的网络命名空间向外转发、经过 FORWARD。若解析失败，就把 `CCG_GUARD_CONTROL_DNS` 默认打开，只放行到上游 DNS 服务器的 53 端口 |
| IT-S03 | 控制器访问 Worker 的 8787 可通；访问其他端口、其他账号未就绪的地址不通 | 符合 |
| IT-S04 | 宿主机进程、其他容器访问 guard 的 8790 | 失败 |
| IT-S05 | 用错误令牌访问 guard；用正确令牌但从错误的来源 IP 访问（另起一个容器接入控制网 `.4`）；把 `.2` 换成一个非 compose 起的容器后用正确令牌访问 | 前两项都是 401（03 §3.2 不区分原因）；第三项 403 `controller_unguarded` |
| IT-S06 | 隔离实例的令牌访问生产前缀的资源（`ccg-21-app`） | 403 或 404，生产资源不受影响 |
| IT-S07 | 导入带 `caddy:latest` 标签的归档 | 400 `load_forbidden`；`caddy:latest` 的镜像 ID 不变 |
| IT-S08 | 按标签拉取非白名单仓库的镜像 | 403 |
| IT-S09 | 以 root 把测试账号的 `resolv.conf` 换成指向 `/etc/hostname` 的符号链接，再触发重启 | 403，容器不动 |
| IT-S10 | 同上，换成硬链接（`st_nlink` 为 2） | 403 |
| IT-S11 | 账号容器不经网关直连 `1.1.1.1:443` | 失败 |
| IT-S12 | 账号容器访问网关的 Xray API 端口 10085、访问控制器的 `172.29.255.2` | 失败 |
| IT-S13 | 用 guard API 尝试越权：建容器时塞 `Privileged` 字段、在 env 里加带换行的变量名、IP 填在子网外、对别的账号 exec、在 suffix 里用 `../` | 全部 400 或 403，Docker 里没有出现对应资源 |
| IT-S14 | 检查 inspect 结果：控制器、guard、网关、账号容器的 `HostConfig` 逐项核对 | 与 policy 的期望完全一致 |
| IT-S15 | 检查网关的 `/config` 目录 | 没有 `state.json` |
| IT-S16 | 收集 guard、控制器、核心三方的日志，搜索令牌、管理密钥、代理密码、OAuth 字样 | 搜不到 |

### 4.3 故障注入（IT-X）

这一组验证"出事时不放宽、事后能自己恢复"。每一项都要同时检查两件事：**失败期间**账号是否仍然出不了网（失败关闭），以及**恢复之后**是否不需要人工处理。

| 编号 | 注入方式 | 期望 |
|---|---|---|
| IT-X01 | 下发配置的过程中停掉 guard（`compose stop guard`），10 秒后再启动 | 这次下发返回 503；已就绪的账号照常处理请求（数据路径不经过 guard）；guard 回来后，核心下一次下发即可完成 |
| IT-X02 | 成对激活进行到"已暂停准入、还没切换"时，杀掉控制器容器 | 控制器重启后账号仍是旧程序；暂停租约 300 秒后过期，准入自动恢复；不留半个新版本（核对 BUG-8 的处理结论，§8） |
| IT-X03 | 成对激活进行到"已切换、等健康检查"时，杀掉控制器 | 重启后由后台恢复或核心重新下发把账号带回 ready；状态文件不损坏 |
| IT-X04 | 重启 dockerd（隔离实例上只能用 `docker restart` 模拟各容器重启，不重启宿主机的 dockerd） | guard 的事件流断开后重连并做一次全量校对；规则与重启前一致 |
| IT-X05 | 让 `iptables-restore` 失败：在一次性环境里先持有 xtables 锁 30 秒 | guard 报错，并保留上一份已生效的规则，不清空；锁释放后自动重试成功 |
| IT-X06 | 让规则计算失败：网关容器删掉一半，模拟 inspect 出错 | 相关账号的放行规则被撤销（失败关闭）；其他账号不受影响（对应现有测试"一个账号消失不影响别人"） |
| IT-X07 | 网关容器被意外重启（`docker restart ccg-gt-shared-egress`） | 约 10 秒内后台恢复把所有账号重新配置好；期间请求失败、不泄露 |
| IT-X08 | compose 重建网关（相当于 recreate） | 同 IT-F18：所有账号在限定时间内恢复，具体时长写进报告 |
| IT-X09 | 控制器连续 3 次请求 guard 都超时（在 guard 前面加一个延迟代理，或在 FakeGuard 里注入） | 控制器返回 503，不卡住请求路径：账号锁和 guard 调用都有超时 |
| IT-X10 | 控制器数据目录写满（数据根挂一个 10 MiB 的 tmpfs） | 写状态失败时返回 503，原状态文件不损坏（原子写） |
| IT-X11 | 宿主机重启（只在一次性 VM 上做） | compose 拉起 guard、控制器、网关；账号容器按 BUG-23 的结论处理；规则在 guard 启动后、开放 API 之前就已算好 |
| IT-X12 | guard 收到畸形请求：超大请求体、慢速发送的 slowloris、1000 个并发连接 | guard 不崩溃，内存有上限，其他请求照常处理 |

### 4.4 迁移与回滚（IT-M）

顺序与 04 §7 的演练顺序一致，这里给出每一步的判据。

| 编号 | 步骤 | 判据 |
|---|---|---|
| IT-M01 | 以旧方式起 Python 0.1.118 隔离控制器，建好 a1、a2，并制造出 04 §2.6 列出的各类文件 | 基线状态的快照（文件哈希、容器 ID、规则）存档 |
| IT-M02 | 起 guard，只跑 `print-rules`，与旧 bridge guard 加 `--once` 的输出对比 | 两份 `CCG-*-PROXY-BRIDGE` 规则逐条一致 |

| IT-M10 | 清理 | 04 §7 的清理核对全部通过 |

### 4.5 性能（IT-P）

| 编号 | 指标 | 方法 | 判据 |
|---|---|---|---|
| IT-P01 | 就绪检查耗时 | 对 a1 连续 200 次 `GET connection` 和建隧道，分别在 Python 和 Go 两个实现下测 | Go 的 p50 不比 Python 差；p95 不超过 Python 加 10 ms |
| IT-P02 | 首字节延迟 | 经隧道向假上游发 100 个流式请求，测到第一个字节的时间 | 与 Python 实现相比差异在 5% 以内 |
| IT-P03 | 并发 | 20 个账号、每个 10 条并发隧道，持续 5 分钟 | 没有错误；控制器内存稳定 |
| IT-P04 | guard 的 CPU | 空闲 10 分钟，用 cgroup 的 `cpu.stat` 取差值 | 低于单核的 2% |
| IT-P05 | 事件突发 | 30 秒内重启 20 个账号容器 | 规则在最后一个事件后 1 秒内收敛；`iptables-restore` 的次数少于事件数（防抖生效） |
| IT-P06 | 网关重建后恢复全部账号的耗时 | IT-F18 中按账号数（5、20）分别记录 | 写进报告，作为 S6 维护窗口时长的依据 |

## 5. L2 接口契约

样例放在 `companions/guard/testdata/api-contract/`，每个端点一个子目录，每个文件是一条样例：

```json
{
  "name": "create app: ip outside subnet",
  "setup": {"networks": [{"aid": "21", "subnet": "10.52.74.0/24"}]},
  "request": {"method": "PUT", "path": "/v1/accounts/21/app", "body": {"image": "x", "ipv4": "10.9.9.9", "env": {}}},
  "response": {"status": 400, "body": {"error": "invalid_request", "message": "ipv4 outside account subnet"}}
}
```

- `setup` 描述 Docker 侧需要预置的资源。guard 的契约测试把它灌进 dockerapi 的内存替身，控制器的 FakeGuard 则直接灌进自己的内存模型。
- 三处都读同一组样例：guard 的真实 HTTP 处理器（下面接 dockerapi 替身）、控制器的 FakeGuard、控制器 `guardapi` 客户端的解码测试。
- **样例的维护方式：**
  - 只有 guard 的作者能改样例；
  - 控制器那边只读；
  - 样例变化时，两个模块的 CI 都要通过才能合并；
  - guard API 的每次不兼容变更都要提升 features 里的版本号，同时增加一组新版本样例。
- **覆盖要求：** 每个端点至少有 1 个成功样例；每条校验规则至少有 1 个拒绝样例；每个错误码至少有 1 个样例。

## 6. L3 跨语言兼容

| 项 | 做法 |
|---|---|
| 三种摘要的参照向量 | 一个只在 CI 里运行的脚本 `controller/reference_vectors.py`：import Python 控制器的 `auth_fingerprint`、`container_identity`、`node`，对约 50 组输入（含中文、emoji、`<>&`、空值、嵌套、键序打乱）输出结果，写入 `controller-go/testdata/pyref/*.json`。Go 测试逐条比较。输入覆盖要能触发 Python `json.dumps` 的各种转义 |
| `container_identity` 用的真实 inspect | 从 ovh 隔离实例取 3 个真实账号容器的完整 inspect（去掉环境变量的值），放进参照向量。防止 guard 返回的 inspect 少了字段而对不上（RB4） |
| 状态文件互读 | 用 Python 写出各种状态（每种 `status`、`disk_quota`、`active_runtime`、`cli`、未知字段），Go 读入、修改一个字段、写回，再交给 Python 读，结果必须一致；反方向也做一遍。重点是 Go 不丢失自己不认识的字段 |
| HTTP 黄金样例 | 照 02 §8.5：约 60 条请求序列，Python 用 FakeDocker 录制，Go 用 FakeGuard 重放；对比状态码、头集合、应答体。§8 中"有意不同"的条目走单独的期望文件，不和 Python 的录制结果比 |
| 删除时机 | Python 源码删除之后，参照向量和黄金样例作为固定文件保留，测试继续运行 |

## 7. L5、L6 组件测试要点

**L5（真实 dockerd，隔离前缀）：**
- policy 每个函数建出的资源，inspect 后与期望逐项比较：能力、安全选项、挂载、网络、资源上限、日志、重启策略。期望写在测试里，不从 policy 包取，防止"自己验证自己"。
- 在一个带 sh 的测试容器里，让 exec 先写 stdout、再写 stderr、再以退出码 3 结束，核对帧解析与合并顺序。
- 拉取不存在的镜像、导入损坏的 tar、导入带非白名单标签的 tar，核对错误。
- 订阅事件流，然后启动、停止、删除测试容器，核对事件到达和过滤；模拟断线（关闭连接）后能重连。

**L6（独立网络命名空间里的防火墙）：**
- 在一次性特权容器里搭出最小拓扑：两个网桥分别模拟账号网和控制网，三个网络命名空间分别模拟 app、网关和控制器，用 veth 连起来，再造出 DOCKER-USER 链。用 guard 的 firewall 包生成并应用规则。
- 用 `nc` 核对：
  - app 到网关的 TCP 通，到别处不通；
  - 控制器到 app 的 8787 通，到 app 的其他端口不通；
  - 控制器的 DNS 通，访问外部的 443 不通；
  - 回环访问 guard 端口被丢弃。
- 重复应用同一份规则，`iptables -S` 的输出不变；改一个账号，只影响这个账号的规则。
- 注入失败（例如规则语法错误），核对失败关闭的结果。

## 8. 现有缺陷在 Go 版里修还是不修

默认原则：**影响安全或会掩盖错误的，修；只是错误码或日志不一致的，保持原样**，避免核心侧的行为跟着变。下表已经用户确认（2026-11-01："按你的建议修"），实现时照此执行。

| 缺陷 | 建议 | 测试怎么写 |
|---|---|---|
| BUG-1 就绪检查等共享网关锁没有上限 | 修：就绪检查不再持有共享网关锁，改读快照 | 新测试：另一个账号 configure 持锁时，`connection` 在 100 ms 内返回 |
| BUG-2 每次就绪检查调 4 次 Docker | 修：一次 guard 调用 | 断言调用次数为 1（02 已有） |
| BUG-3 被拒绝的新配置在约 10 秒后被报为就绪 | 修：`egress-desired.json` 改为在激活成功（状态写成 ready 且就绪）之后才写入；阻断时照旧在阻断前写入。这样后台恢复和代理复查读到的永远是最后一次生效的配置。被拒绝的下发不会改动这个文件：账号保持旧修订号，核心看到修订号不符会再次下发，再次得到同样的 409 或 503，错误不再被掩盖。文件名和格式不变，回滚到 Python 0.1.118 后它读到的也是最后生效的配置，比现在更安全（RB2 仍然满足） | 新测试：① 下发因 CLI 不可用返回 409 后，推进假时钟让后台恢复跑过，状态仍是旧修订号，`egress-desired.json` 仍是旧内容；② 下发成功后文件更新为新内容；③ 阻断时文件写入阻断配置；④ 新账号第一次下发失败时，不留下这个文件 |
| BUG-4 改 egress 镜像后新建网关仍用旧镜像 | 随 compose 化自然消失（网关只在显式维护时由 compose 建） | 不需要 |
| BUG-5 代理参数不在入口校验 | 修：入口校验，返回 400 | 新测试：缺 host、端口越界、协议错误都返回 400，且不建任何容器 |
| BUG-6 镜像不合格时错误码不一致 | 保持 | 断言旧行为 |
| BUG-7 租约不合规时账号停在暂停状态 | 修：尽力调一次不带租约的 resume，并记录日志 | 新测试 |
| BUG-8 返回 busy 时留下半个新版本 | 修：清理已放置的目录和快照 | 新测试 |
| BUG-9 换好之后因身份变化返回 503 | 修：返回 updated，同时带 `online:false` | 新测试 |
| BUG-10 同名外部容器返回 404 | 保持 | 断言旧行为 |
| BUG-11 鉴权的两处宽松 | 修：必须带 `Bearer ` 前缀；非 ASCII 返回 401 | 新测试；核心一直带前缀，不受影响 |
| BUG-12 HEAD 等方法在鉴权前返回 501 | 修：先鉴权，再返回 JSON 405 | 新测试 |
| BUG-13 网关归属不符时返回 503 | 保持（标签由 compose 固定，这种情况实际不会出现） | 断言旧行为 |
| BUG-14 多调一次 resume | 保持（无害） | 不需要 |
| BUG-16 没有网关时每 10 秒一行告警 | 修：没有网关时跳过 collect | 新测试 |
| BUG-17 `active.nft` 规则顺序不稳定 | 修：排序后输出 | 断言输出确定 |
| BUG-18 识别运行目录时符号链接处理不一致 | 修：一律排除符号链接 | 新测试 |
| BUG-20 挂载源在控制器可写目录 | 由 guard 解决 | IT-S09、IT-S10 |
| BUG-21 阻断账号的 status 报 pending | 保持（核心依赖现有行为） | 断言旧行为 |
| BUG-22 网段耗尽返回 503 | 保持（核心依赖现有行为）；日志里写明原因 | 断言旧行为 |
| BUG-23 宿主机重启后账号容器不自动启动 | 保持 | IT-X11 记录现象 |

BUG-15 和 BUG-19 只涉及测试文件和文档，不影响 Go 版。

## 9. 覆盖追踪

脚本 `scripts/coverage-ids.sh`（只用 grep 和 awk）：

1. 从 01 文档里取出全部条目编号：表格行首的 `E1`、`H1`、`R1`……`RB9`。
2. 从两个 Go 模块的 `_test.go` 和集成场景表（本文 §4）里，取出 `covers:` 后面的编号。
3. 求差集，得到没有测试的条目，减去豁免表 `testdata/coverage-waivers.txt`（每行一个编号加理由）后，剩下的必须为空，否则 CI 失败。

豁免只允许两种理由：`removed`（行为随 guard 化而删除，例如 C3、C4 的 upgrade.py）和 `integration-only`（只在 L7 覆盖，例如 T7 的空闲超时）。
