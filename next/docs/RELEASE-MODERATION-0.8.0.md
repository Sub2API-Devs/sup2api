## 1. 现有配置升级后的变化

### 1.1 复核出错或超时不再放行

0.7.2：流程里任何一级出错或超时，整个请求放行，记为 `error`。

0.8.0：没有结论的级跳过，前面的命中保留。

- 初审命中、复核出错或超时 → **命中**。先审的请求被拒绝，用户按违规处理（进名单、计违规）。
- 流程总超时到点时前面已有命中 → 命中，不再放行。先审请求的预算是 min(流程总超时, 29 秒)。
- 一级里有的审核器出错、有的判了：出错的不参与表决。例：两个审核器、组合方式"全部命中"，一个出错、一个命中 → 这一级命中（0.7.2：无结论）。
- 只有所有级都没有结论时才放行，记为 `error`。

后果：审核渠道不稳定时，以前被放行的请求现在会被拒绝；`error` 记录变少。

### 1.2 `mode = enforce` 的含义变了

0.7.2：`enforce` = 所有人先审。

0.8.0：`enforce` = 开启，**默认级别为拦截**。时机依次按：

1. 黑名单（`blocklist_user_ids`）→ 先审；
2. 白名单（`allowlist_user_ids`）→ 只后审，永不被拒绝；
3. 有未过期的观察名单条目 → 按条目的级别：拦截级先审，**观察级只后审**；
4. 没有条目 → 按默认级别（`enforce` 先审，`observe` 后审）。

对 `mode = enforce` 的部署：

- 没有名单条目的用户：不变，仍然先审。
- **观察级条目的用户从先审变成只后审。** 为了不让自动进名单的用户因此"降级"，插件首次以 0.8.0 运行时把未过期的、自动加入（`source = auto`）的观察级条目改成拦截级（每条写一条名单历史）。管理员手动设成观察级的（`manual`）和 AI 降到观察级的（`analysis`）不改，这些用户升级后只后审。第 2.2 节的查询数出各有多少。
- 之后自动加入的条目以拦截级加入，有效期 `watch_days`；拦截级条目也计违规，但命中不延长有效期。

对 `mode = observe` 的部署：时机规则与以前相同（只有拦截级条目的用户先审），新增黑名单和白名单。

### 1.3 "豁免用户"变成白名单

`exempt_user_ids` 退役，读作白名单。原来列在里面的用户，0.7.2 下完全不审核；0.8.0 下**后台审核、有记录、可能自动进观察名单、永不被拒绝、不会被封禁**。0.8.0 没有"完全不审核的用户"。

设置页里它显示为"白名单"；保存白名单时写入新键 `allowlist_user_ids`。保存白名单或黑名单时，同时把 `exempt_user_ids` 写成"白名单减去黑名单"（镜像）：同时在两个名单上的用户在 0.8.0 下是先审，不能让仍在 0.7.2 上的节点把他们当成完全不审的豁免用户。

### 1.4 绑定到停用或未发布流程的分组和账号，从不审核变成审核

0.7.2：绑定指向已停用或未发布的流程 → 这个分组（或账号）不审核。

0.8.0：这样的绑定视为不存在，请求按更宽的绑定审核，通常是默认分组 0 的流程。绑定到"不审核（免审）"（flow 0）的不变，仍然不审核。

有人可能就是用"绑一个停用的流程"来让某个分组不审核。**升级前必须跑第 2.1 节的查询并逐条处理。**

### 1.5 繁忙时得到 503 的用户范围变大

处理中的钩子请求合计超过 `max_inflight_mb`（默认 128）时，新请求立即回答：本应先审的用户得到 503 `moderation_busy`，其余放行、不审核。

- 0.7.2："本应先审"只算观察名单上拦截级的用户。
- 0.8.0：按第 1.2 节的规则。**`mode = enforce` 时，是白名单和观察级条目之外的所有用户。**
- 分组没有流程、绑定为免审、或模型被流程的模型过滤排除的请求，不会得到 503。

`mode = enforce` 且流量大、请求体大的部署，升级后留意 503 `moderation_busy` 的数量（插件健康指标 `busy`）；需要时调大 `max_inflight_mb`，但插件进程的内存上限是 1024 MB（0.8.0 起，此前 512 MB）。

### 1.6 缓存在第一天全部重建，审核调用和费用上升

0.8.0 的判定缓存用新的键和新的 KV 命名空间，0.7.2 的缓存全部作废。升级后所有内容重新审一遍（Claude Code 的系统提示词和工具定义每次几万字），**第一天审核调用数和费用会明显上升**，之后回落。

- 缓存保留 `verdict_cache_days` 天，默认 7。没保存过这个键时：旧键 `cache_ttl_seconds` 也没保存过 → 7 天；旧键保存过 → 按它换算，0 表示缓存关闭（保持关闭，直到在设置页填了天数），其他值向上取整到整天（例如存的是 86400 秒 → 1 天）。想要 7 天而旧键存的是别的值，升级后在设置页填上天数。
- 0.8.0 也缓存命中：一段内容被判命中后，之后包含这段内容的请求直接按原结论处理（先审的被拒绝），不再调用审核渠道，记为"重放"。重放不算新的违规。0.8.1 起结论在请求得到回答之后才写进缓存，这之前的重复请求不是重放（第 7 节"要知道的三件事"）。
- 改了流程的级、审核器、题集、阈值或渠道模型，该流程的缓存自动失效（又是一轮重审）。改流程名、模型过滤、抽样比例、超时、渠道密钥不影响缓存。
- **多节点**：一个节点判出的命中写进 KV 之后，内存里没有这些内容的其他节点下一次查询就读到；内存里已经把这些内容的各个片段记成"通过"的节点，在收到写入节点的广播后立即生效。人工处理（误报、确认、改回待处理）对缓存的改动同样：广播送达即生效，做处理的节点自己立即生效。广播丢失时怎样，0.8.0 和 0.8.1 不同，见第 7 节"改了什么"第 2 条。

### 1.7 Jev（TypeSafe）：每次调用都开长上下文，送审更多图片

- 每次调用带长上下文请求头。按上游文档，更慢、准确度略低、单价不变。Jev 渠道的超时（默认 8000 ms）是否够用，升级后看渠道健康度的延迟。
- 以前跳过的图片现在重画后送审：GIF（第一帧）、WebP、尺寸不合规格的 PNG / JPEG。一次调用能带的图片也更多（预算从 24k token 提高到 200k token）。**Jev 的 token 用量和费用上升，可能出现新的命中。**
- 重画在请求路径上进行，先审请求的延迟会增加；每次调用里重画最多占 5 秒，超时的图跳过，文字照常审。
- 仍然不送审：URL 图片、超过 16 MiB、超过 1200 万像素、解码内存估算超过 112 MiB 的图片（例如很大的渐进式 JPEG）。
- **没有送出去的图片不进缓存。** 一张图这次没有被任何审核器收到（上面这些，以及没等到重画名额、超出重画时间或请求预算的），它不会被记成"通过"，带它的下一个请求会再送一次；同一请求里的文字照常缓存。例外：图片被某个审核器收到并判了命中、请求却因为另一个没收到图片的审核器而通过时，同一块的文字也不缓存，这样的请求每次都整块重新审（第 6 节第 6 条）。所以带多张图的请求在头几次会多几次审核调用。 OpenAI 审核器是例外：它每次调用只随机带一张图作为抽样，调用成功时这次输入里的可用图片一起缓存，不会为其余图片再调用。

### 1.8 更多记录带原始消息

新设置 `record_pass_input_message` 没保存过时取默认值"开"。`store_text` 开着的部署升级后：

- 被推翻的记录（默认会写）开始带原始消息，包括其中的图片。`events` 表会变大，留存期是 `overturned_retention_days`（默认 30 天）。
- 开了 `record_pass` 的部署，通过的记录也带原始消息，量可能很大。
- 命中过的记录的保存条件也放宽了：只要运行里有任何一级判过命中就保存（0.7.2 只在第一级命中时保存）。
- 出错记录仍然不保存原始消息。

不想要就在升级后把这个开关关掉。

### 1.9 记录结果和异常率的含义变了

- **记录结果**：有失败的级、但别的级判过的运行，结果从 `error` 变成 `hit`、`overturned` 或 `pass`。`error` 只表示这次什么都没判出来。`error` 记录变少，`record_errors`、`error_retention_days` 管到的记录相应减少。
- **流程异常率**（概览、趋势、告警）：分子从"结果为 error 的运行"变成"有审核器出错或有级失败的运行"。同样的流量下数值变大或持平，**升级前后的异常率不能直接比较**；`error_rate_alert_percent` 的阈值按新的数值重新看一下，同样的阈值下告警更容易触发。
- 多块请求全部通过时，记录显示的是最后一块（以前是第一块）。
- 概览的"可疑"里包含重放，另有"其中缓存重放 N"。

### 1.10 其他

- 已存的、内容等于 new-api 旧内置题集的 Jev 审核器，题集版本号的显示从 `custom-…` 变为 `content-audit-13-zh-v1` 或 `-en-v1`。判定不变。
- 模拟流程时"未标记"的用户按默认级别决定时机（以前固定为后审）。
- 白名单用户不能被手动封禁，也不能手动设为拦截级（接口返回 400）。

### 1.11 LLM 审核器开始收到图片

负责人 2026-11-10 的决定：LLM 审核器必须看到图片。两种 LLM 审核器（`llm_verdict`，以及 0.8.0 新增的 `llm_questions`）默认把请求里的图片和文字一起发给模型；审核器上有一个开关（`review_images`）表示它的模型是否支持图片，**默认"支持"**。new-api 的 LLM 审核器只发文字，这一点有意不同。

**现有配置升级后的变化**（不改任何配置就发生）：

- 已有的 `llm_verdict` 审核器没有存过这个开关，按默认"开"处理，**升级后开始发图片**。从 new-api 导入的 `llm` 审核器同样（导入文档里带不带 `review_images` 都接受，原值保留）。
- **费用**：每次带图片的调用按图片计 token；`llm_verdict` 多轮时每一轮都重发图片。LLM 审核器放在复核级时只在前一级命中后才调用；放在第 1 级时每个带新图片的请求都多付这笔钱。请求体也变大（图片以 base64 内联）。
- **延迟**：带图片的调用更慢，请求体更大。LLM 渠道的超时（默认 15000 ms）和 `ttft_timeout_ms` 是否够用，升级后看渠道健康度的延迟和超时数。
- **结论可能变**：以前第 1 级（OpenAI、Jev）因为图片命中、LLM 复核只看文字并推翻的请求，每次都放行。现在复核看得到图片，可能确认命中，**以前放行的请求可能被拒绝**。复核看图后仍然通过的，图片进缓存，这类请求不再每次重审。
- 只有图片、没有文字的内容以前让 LLM 审核器跳过，现在会调用它。
- 这次改动换了判定指纹的版本，判定缓存全部重建一次（从 0.7.2 升级本来就全部重建，第 1.6 节；已经在跑 0.8.0 预发布构建的环境会再重建一次）。

**怎么关**：按审核器关。在"审核器"页编辑这个 LLM 审核器，关掉图片开关并保存；或者 `PUT /api/v1/p/moderation/auditors/<id>`，在原来的 `config` 里加 `"review_images": false`（请求体要带完整的 `name`、`type`、`channel_id`、`config`）。关掉后与升级前相同：只发文字。改开关会让引用这个审核器的流程的缓存失效一次。回滚到 0.7.2 不用先去掉这个键：0.7.2 的 `llm_verdict` 忽略它。

**哪些审核器应该关**：

- **模型不支持图片、上游拒绝带图调用的：必须关。** 上游（或它前面的代理）用 400、413、415 或 422 拒绝带图调用时，审核器自动只发文字重试一次，所以开着也能得到文字的结论，但不能就这样留着：
  1. 开着的审核器算"收图片的"，流程不算"有的收图片、有的不收"的流程，第 6 节第 6 条里"图片总是带着本请求的文字一起审"的保护不生效：一个请求的文字已被缓存、图片被第 1 级的审核器命中时，这个请求会被拒绝，而缓存为空时同一个请求是放行的。
  2. 它的图片从不算被审过，也就从不进缓存：对话之后的每一轮都把所有没缓存的图片再传一遍、再被拒绝一遍。每轮多一次调用；后审（post）路径上按字节计的队列会被这些请求占满，其他请求的后审任务被丢掉（`dropped` 上升）。
  3. 怎么发现：这种回退本身不报错。看 `/status` 的 `runtime.images_refused`（本节点启动以来被拒绝的带图调用数，持续增长就是在发生）、插件的 warn 日志（每个审核器每次加载配置记一条，带审核器 id），以及记录的 trace 里该审核器结果的 `images_refused: true` 和 `status`（上游拒绝时的状态码；通过的请求默认不写记录，所以先看计数器和日志）。也可以用试跑接口带一张图片试一次（`POST /api/v1/p/moderation/auditors/<id>/try`，请求体 `{"text": "...", "images": ["data:image/png;base64,..."]}`）：返回里有 `images_refused` 和 `status`。
- **模型不支持图片、上游不报错而是直接忽略图片的**（一些兼容 OpenAI 的网关接纯文字模型时如此）：必须关。否则审核器被当作"看过"图片并通过，图片被缓存成"通过"，而模型其实没看到。
- 自己写了系统提示词的 `llm_verdict` 审核器：图片照发，但提示词不会自动提到图片（默认提示词加了一句）。想让模型明确把图片当作待审内容，在提示词里补一句；不想让它看图，关掉开关。

**发哪些图片**：只发内联的 PNG、JPEG、GIF、WebP；URL 图片不发；超过 5 MiB 或某一边超过 8000 px 的不发；base64 里的换行先去掉再发（按行折断、末尾带一个换行是客户端常见的写法）；去掉换行后仍不合规范的那一张不发（URL 安全字母表、缺填充、被截断、末尾多出内容、末尾填充位不为零——严格的上游会因为这样一张图拒绝整次调用）；一次调用最多 20 张、base64 合计 20 MiB（最大的图片只放得下两张），超出的不发。LLM 渠道指向 Amazon Bedrock 或 Google Cloud 上的 Claude 时，那里每张图片只收 5 MB 的 base64（约 3.75 MiB 的文件）：3.75–5 MiB 的图片会让带图调用被 400 拒绝，按文字重试（第 6 节第 10 条）。不发的图片计入 trace 里的 `skipped_images`，不重画（Jev 会把过大的图片缩小后送审，LLM 审核器不会）。

**连带的一处收窄**：第 6 节第 6 条里"带着没缓存的图片时把已缓存的文字再送一遍"现在只用于"有的审核器收图片、有的不收"的流程。全部审核器都收图片的流程（例如 Jev + 开着图片的 LLM 复核）不再重送文字。

## 2. 升级前的核对

### 2.1 绑定到停用或未发布流程的绑定

```sql
SELECT 'group' AS kind, g.group_id, 0 AS account_id, g.flow_id, f.name, f.enabled, f.published IS NOT NULL AS published
FROM plg_moderation.flow_groups g LEFT JOIN plg_moderation.flows f ON f.id = g.flow_id AND f.deleted_at IS NULL
WHERE g.flow_id <> 0 AND (f.id IS NULL OR NOT f.enabled OR f.published IS NULL)
UNION ALL
SELECT 'account', a.group_id, a.account_id, a.flow_id, f.name, f.enabled, f.published IS NOT NULL
FROM plg_moderation.flow_accounts a LEFT JOIN plg_moderation.flows f ON f.id = a.flow_id AND f.deleted_at IS NULL
WHERE a.flow_id <> 0 AND (f.id IS NULL OR NOT f.enabled OR f.published IS NULL);
```

结果为空：没有受影响的绑定。

结果不为空：每一行是一条升级后会回落的绑定（第 1.4 节）。由管理员逐条决定：

- 要继续不审核 → 升级前在"绑定"页把它改成"不审核（免审）"。0.7.2 已支持，改了之后新旧版本都不审核。
- 接受按默认流程审核 → 不用改，记下来。

迁移不会自动改这些绑定：它分不清"有意不审"和"流程临时停用"。

### 2.2 观察级条目的来源

```sql
SELECT source, count(*) FROM plg_moderation.watchlist
WHERE level = 'observe' AND (expires_at IS NULL OR expires_at > now()) GROUP BY source;
```

记下结果。`mode = enforce` 的部署：

- `auto` 的条数 = 升级后会被转成拦截级的条目数（第 4.2 节核对）。
- `manual`、`analysis` 的条数 = 升级后从先审变成只后审的用户数。其中有需要继续先审的，升级后把他们改成拦截级，或加进黑名单。

`mode = observe` 的部署不转换，这一步只作记录。

## 3. 升级

顺序照以往只改插件的版本：构建 0.8.0 的包 → 上传并升级。没有新增或扩大的权限，核心自动沿用现有授权，不需要在控制台批准。迁移 `0010` 由核心在切换到新版本的过程中执行（一个迁移文件一个事务）：给 `auditors` 重建类型约束，给 `config_state`、`events`、`stats_hourly` 加列，都不重写表，`events` 上只短暂持锁。

**滚动升级期间（还有节点在跑 0.7.2 时）不要做：**

1. **不要发布带补审级的流程。** 0.7.2 的节点读不了带 `fallback` 的流程（未知字段），会跳过整个流程，绑定它的分组在这些节点上不审核。
2. **不要创建 `llm_questions`（"LLM 题表"）审核器，更不要把它放进流程。** 0.7.2 的节点不认识这个类型，引用它的那一级在这些节点上出错，而 0.7.2 的规则是出错放行。

这两件事等所有节点都在 0.8.0 上之后再做。

滚动期间还会看到的现象，都在滚动结束后消失：

- 新旧节点对同一请求的判断不同：复核出错时一个拒绝一个放行；`mode = enforce` 下观察级条目的用户一个后审一个先审；绑定到停用流程的分组一个审一个不审；同一张图一个送审一个跳过。
- 新旧节点各用各的缓存，同一内容可能两边各审一次。
- 旧节点在转换之后自动加入的观察级条目，由 0.8.0 的节点在首次转换后的 24 小时内继续转成拦截级。所以**滚动升级要在 24 小时内完成**；拖得更久，之后旧节点加的观察级条目不会被转换，需要手动改。
- 在 0.8.0 的设置页保存过白名单或黑名单后，`exempt_user_ids` 是"白名单减去黑名单"：旧节点把白名单里（且不在黑名单里）的用户当豁免用户（完全不审核），从白名单移出或被加进黑名单的用户在旧节点上不再豁免。

### 4.2 名单转换

插件拿到设置后的几秒内做首次转换，日志里有一行：

```
moderation: 0.8.0 watch list conversion  mode=<mode> converted=<条数> first_run=true
```

- `mode = enforce`：`converted` 应等于第 2.2 节 `auto` 的条数（期间过期或被改动的条目会有出入）。
- `mode` 不是 `enforce`：`converted=0`。

之后 24 小时内如果又转换了条目（滚动期间旧节点加的），会再出现这一行，`first_run=false`。

```sql
SELECT parity_converted, parity_converted_at FROM plg_moderation.config_state WHERE id = 1;

SELECT count(*) FROM plg_moderation.watch_events
WHERE action = 'set_level' AND reason LIKE '0.8.0 升级%';

SELECT source, count(*) FROM plg_moderation.watchlist
WHERE level = 'observe' AND (expires_at IS NULL OR expires_at > now()) GROUP BY source;
```

期望：`parity_converted` 为真，`parity_converted_at` 是首次转换的时间；第二条等于转换的总条数；`mode = enforce` 时第三条里不再有 `auto` 一行（滚动期间可能短暂出现，下一轮会被转换）。

日志里出现 `converting the watch list for 0.8.0 failed, retrying later` 表示某一步失败，插件每 5 秒重试；持续出现要查原因。

### 4.3 `/status` 的新字段

`GET /api/v1/p/moderation/status` 应有：

| 字段 | 期望 |
|---|---|
| `default_level` | `mode = enforce` 时为 `enforce`，否则 `observe` |
| `watch.blocking_with_new` | 存在（数字）。拦截级条目里有新命中的个数 |
| `today.replayed` | 存在。升级后一段时间内为 0，出现第一次缓存命中重放后增加 |
| `runtime.cache_epoch` | 0（没清空过缓存） |
| `runtime.cache_bytes`、`runtime.cache_entries` | 随流量增长；`cache_bytes` 不超过约 64 MiB |
| `runtime.kv_errors` | 存在（数字）。本节点启动以来读写 KV 失败的次数；正常为 0 或很少，持续增长说明 KV（Redis）有问题，这期间缓存不起作用、内容照常送审。0.8.0 的节点上这个数字也包含"KV 太慢、在预算内没读完"的批次，KV 没出错时也会涨。0.8.1 只计真正失败的调用（一次批量调用算一次；因为客户端断开、节点关停而中断的不算），慢的 KV 表现为请求变慢（看核心一侧 `moderation` 钩子的耗时），不表现在这里 |
| `runtime.kv_writing` | 0.8.1 起存在（数字，是此刻的值，不是累计）。结论还没写进 KV 的运行数（在等轮到自己，或正在写）；概览页有一行（0.8.1 的文案是"正在写入共享缓存的结论"，0.8.2 改为"等待写入共享缓存的审核（当前）"）。KV 正常时是 0 或个位数；**持续增长说明 KV 不回答**（第 7 节"KV 不回答时"） |
| `runtime.kv_skipped` | 0.8.1 起存在（数字）。本节点启动以来整次没写缓存的运行数：人工处理可能在它的请求查缓存之后改过缓存（第 6 节第 3 条），或者本节点的内存缓存在那之后被换掉了（在本节点清空缓存、改 `cache_entries`）；0.8.2 起概览页有"未写缓存的审核（期间有人工处理或缓存被换）"一行，0.8.1 里只在这里和健康指标里。只在这些操作前后增长 |
| `runtime.redraw_panics` | 存在（数字），正常为 0。本节点启动以来因图片解码器异常而跳过的图片数 |
| `runtime.images_refused` | 存在（数字）。本节点启动以来 LLM 审核器的带图调用被上游拒绝、改为只审文字的次数（试跑和模拟也计）；正常为 0 或很少，持续增长说明某个 LLM 审核器的模型或上游不收图片，关掉它的图片开关（第 1.11 节） |

所有节点都升级后，各节点回答里的这些字段都应存在。只缺 `runtime.kv_writing`、`runtime.kv_skipped` 的回答来自 0.8.0 的节点；其余字段也缺的来自还在 0.7.2 的节点。

### 4.4 模拟一次流程

在"流程"页对默认流程用"模拟"各跑一次（或 `POST /api/v1/p/moderation/flows/<id>/simulate`，请求体 `{"text": "...", "source": "published", "user_state": "none"}`）：

1. 一段正常文本 → 通过；返回的时机在 `mode = enforce` 时是先审（pre），否则后审（post）。
2. 一段确定会命中的文本 → 命中；trace 里每一级带 `stage`。

模拟不读写缓存、不写记录、不计违规，费用记在来源 `simulate` 下。

### 4.5 头一两天要看的

- 审核调用数和费用（第 1.6、1.7 节）：第一天高，之后回落。没有回落时看是否有人反复改流程配置或清空缓存。
- Jev 渠道的延迟和错误率（第 1.7 节）；先审请求的延迟。
- LLM 渠道的 token 用量和费用，以及图片是否被上游拒绝（第 1.11 节）。有文字的输入被拒绝后，只发文字的重试是成功的调用，渠道健康度里没有错误，也没有"400 的次数"可看（只有图片的输入被拒绝后没有可重试的内容：渠道那一行记一次错误，审核器那一行记一次跳过）；带图和不带图的调用都被 400、413、415、422 拒绝时（例如模型名写错）是普通的上游错误，不算拒绝图片；要看的是 `/status` 的 `runtime.images_refused`（本节点启动以来的次数）、记录 trace 里审核器结果的 `images_refused` 和 `status`、插件的 warn 日志（"the upstream refused a call with images"，带审核器 id，每个审核器每次加载配置一条）。它持续增长时，关掉那个审核器的图片开关。
- 被拒绝的请求数：第 1.1 节会让它在渠道不稳定时上升。
- 503 `moderation_busy`（第 1.5 节）。
- 流程异常率告警（第 1.9 节）。
- `events` 表的大小（第 1.8 节）。
- 记录页筛选"缓存重放"，看重放记录是否符合预期。
- `/status` 的 `runtime.kv_errors`、`runtime.kv_writing`（第 4.3 节）：持续增长时查 KV。0.8.1 起 KV 慢不会让 `kv_errors` 增长：怀疑 KV 慢时看核心一侧 `moderation` 钩子的耗时，以及这个节点到数据库和 Redis 的延迟。

## 5. 回滚到 0.7.2

回滚不需要改数据库。但 0.7.2 读不了 0.8.0 才有的三样东西：带补审级的流程、`llm_questions` 审核器、设置里的四个新键。**按下面的顺序做，前三步都在 0.8.0 还在运行时完成。**

### 第 1 步：去掉补审级

```sql
SELECT id, name, enabled FROM plg_moderation.flows
WHERE deleted_at IS NULL
  AND (published::text LIKE '%"fallback"%' OR draft::text LIKE '%"fallback"%');
```

对查到的每个流程：在流程画布里删掉补审级，或关掉它的"补审级"开关，然后**发布**。草稿和已发布版本里都不能留 `fallback`。做完再跑一次查询，结果应为空。

注意两种做法的结果不同。删掉：流程回到没有补审的样子。关掉开关：这一级变成排在最后的普通级，也就是对前面命中的再一次复核——它判通过会**推翻**前面的命中，这通常不是想要的。拿不准就删掉。

不做的后果：0.7.2 把这个流程整个跳过，绑定它的分组和账号不审核。

### 第 2 步：换掉 `llm_questions` 审核器

```sql
SELECT id, name, channel_id FROM plg_moderation.auditors
WHERE type = 'llm_questions' AND deleted_at IS NULL;
```

对查到的每个审核器：在所有引用它的流程里换成别的审核器（或去掉）并发布，然后删除这个审核器。做完再跑一次查询，结果应为空。

不做的后果：0.7.2 不认识这个类型，引用它的那一级出错；0.7.2 的规则是出错即放行。

### 第 3 步：去掉四个新设置键

0.7.2 的设置 schema 不认识 `allowlist_user_ids`、`blocklist_user_ids`、`verdict_cache_days`、`record_pass_input_message`（它是 `additionalProperties: false`）。0.7.2 读设置时会忽略它们，但核心保存设置时按当前安装版本的 schema 校验整份文档：**这四个键只要还存着，降级后 0.7.2 的设置页就保存不了任何设置。** 0.8.0 的设置页不能把这四个键都删掉（开关和名单只能改值），所以要直接调核心的设置接口。在降级之前做，这样 0.7.2 的设置页一开始就能用；漏了的话，降级后用同一个接口提交去掉这四个键的文档也可以（那时按 0.7.2 的 schema 校验，去掉之后能通过）。

1. `GET /api/v1/plugins/moderation/settings`，取出响应里的 `values`（整份设置）。
2. 从 `values` 里删掉这四个键。其他键原样保留；密钥类的值读到的是 `******`，原样回传表示沿用。
3. **白名单**：已经镜像好了，一般不用做什么。0.8.0 的设置页每次保存白名单或黑名单，都把"白名单减去黑名单"写进 `values.exempt_user_ids`，所以这里它应当等于刚删掉的 `allowlist_user_ids` 去掉 `blocklist_user_ids` 里的用户，核对一下即可。只有白名单是绕过设置页、直接调设置接口写的，才需要手动把原来 `allowlist_user_ids` 里的 id 写进 `values.exempt_user_ids`。注意 0.7.2 下这个名单的含义是**完全不审核**（没有记录），不是"只后审"。不想让这些用户在 0.7.2 下免审的，把 `exempt_user_ids` 改成空数组，他们按普通用户审核（`mode = enforce` 时先审）。
4. `PUT /api/v1/plugins/moderation/settings`，请求体 `{"values": { …修改后的整份设置… }}`。PUT 是整体替换，所以必须带上全部其他键。用持有核心 `plugin:manage` 的账号做；只有 `moderation:manage` 的账号改设置时要重填所有已存的密钥。
5. 再 `GET` 一次，确认四个键都不在了。

这一步做完到降级之前，0.8.0 的节点按旧键工作：白名单取 `exempt_user_ids`；黑名单为空（原黑名单用户按名单条目或默认级别处理）；缓存天数取 `cache_ttl_seconds` 的换算值（没有则 7 天，为 0 则缓存关闭）；`record_pass_input_message` 取默认值"开"。这段时间**不要在 0.8.0 的设置页改白名单、黑名单、缓存天数和"通过的记录也保存原始消息"这四项**，否则键又被写回去。

回滚后黑名单没有对应物：需要继续先审的用户，把他们在观察名单里设为拦截级。

### 第 4 步：开着自动封禁时，看一下重放记录

0.7.2 的封禁计数不认识 `replayed`，会把重放记录当普通的可疑记录计入。`ban_threshold > 0` 时，回滚前看有没有用户因此接近或超过阈值：

```sql
SELECT user_id,
       count(DISTINCT CASE WHEN request_id = '' THEN id::text ELSE request_id END) AS replayed_requests
FROM plg_moderation.events
WHERE replayed AND result IN ('hit', 'block') AND review_status <> 'false_positive'
  AND created_at >= now() - interval '24 hours'   -- 换成 ban_window_hours 的值
GROUP BY user_id ORDER BY replayed_requests DESC LIMIT 50;
```

数字大的用户，回滚后下一次命中就可能被自动封禁。可以先把 `ban_threshold` 调高或暂时设为 0，等这些记录滑出封禁窗口再恢复。`ban_threshold = 0`（默认）时跳过这一步。

### 第 5 步：降级插件

照上线 0.7.2 时的做法把插件切回 0.7.2 的包。0.7.2 与 0.8.0 申请的宿主权限和 scope 相同。

### 第 6 步：降级后的核对

- 在 0.7.2 的设置页随便改一项再改回来，保存两次都成功（验证第 3 步）。保存失败并提示有未知字段，说明还有新键没去掉：回到第 3 步，这时用同样的接口在 0.7.2 下提交去掉新键的文档即可。
- 插件日志里没有 `moderation: published flow is invalid`（第 1 步漏了）和 `moderation: auditor config is invalid`（第 2 步漏了）。
- 概览页正常，流程数与回滚前相同。

### 回滚后的状态

- **缓存**：0.7.2 读不到 0.8.0 的缓存，从空缓存开始，又是一轮重审（费用再上升一天）。KV 里 0.8.0 的键到期自动消失（最长 30 天）。
- **时机**：`mode = enforce` 恢复为所有人先审。升级时被转成拦截级的条目保持拦截级；0.7.2 不给拦截级计违规、不延期，它们到 `expires_at` 后过期。
- **绑定**：指向停用或未发布流程的绑定恢复为不审核。
- **记录**：0.8.0 期间写下的记录都还在。重放记录在 0.7.2 的界面上显示为普通的命中记录，AI 分析也把它们当普通记录。trace 里的 `failed`、`fallback`、`stage`、`cache` 是 0.7.2 的界面不认识的键，不显示。
- **出错行为**：恢复为出错即放行。

### 迁移留下了什么，为什么不用撤销

| 留下的东西 | 0.7.2 下 |
|---|---|
| `auditors` 的类型约束多允许一个值 `llm_questions` | 约束只是放宽了，0.7.2 写入的三种类型照常通过 |
| `config_state.cache_epoch`、`parity_converted`、`parity_converted_at` | 0.7.2 不读这三列；都有默认值或可空 |
| `events.replayed`（默认 false） | 0.7.2 的写入语句逐列写明列名，不写这一列，取默认值；读取也逐列写明，不受多出的列影响 |
| `stats_hourly.replayed`（默认 0） | 同上 |
| 核心迁移记录 `public.plugin_migrations` 里 `0010_newapi_parity.sql` 一行 | 核心只对包里有的迁移文件逐个比对，多出来的记录不看 |
| 名单历史里"0.8.0 升级"的记录、被转成拦截级的条目 | 普通的名单数据 |

所以回滚不执行任何 SQL。再次升级到 0.8.0 时迁移不会重跑（内容没变）；名单转换只在距首次转换不到 24 小时内继续，超过后不再转换。

## 6. 已知限制

1. **后审的请求被缓存命中重放时，这个请求里新增的内容不审。** 一个对话的历史里有过一次命中并进了缓存，之后这个对话的每一轮请求都包含那段内容：先审的用户每一轮都被拒绝；后审的用户每一轮只记一条重放记录（不算新的违规），**这一轮新写的内容不会送到审核渠道**，直到命中条目过期（`verdict_cache_days`）、那条记录被标为误报或缓存被清空。这与 new-api 的行为相同，是有意保留的。要拦住这类用户，靠把他们升为拦截级或加进黑名单。
2. **重放不分用户。** 一段内容被判命中并缓存后，别的用户第一次发同样的内容也是重放：会被记录，先审时会被拒绝，但不进名单、不计违规。广为流传的越狱提示词在缓存期内不会让后来的用户进名单。与 new-api 相同。
3. **人工处理后的缓存同步是尽力而为的。** 把记录标为误报、确认或改回待处理，会同步更新缓存（处理结果提示里的"已同步判定缓存 N 条"；N 小于处理的条数表示有的没写成功，再处理一次即可）。做处理的节点和收到广播的节点立即生效；没收到广播的节点不会自己跟上——例如继续重放已标为误报的命中（0.8.1，第 7 节"改了什么"第 2 条）。KV 写入失败、处理请求在同步做完之前结束（0.8.1 起同步没有自己的时限，随请求结束而停），或被别的节点晚到的写入盖掉时，旧结论也会留到缓存到期。**0.8.1 起，本节点上处理之前就开始审、处理之后才写缓存的运行不会把旧结论写回来**，不论它审了多久、写等了多久。代价：每次处理（本节点做的或收到广播的）前后，各节点上别的、审了 4 秒以上的运行的结论都不进缓存——通过的下次重审；**命中的在用户重试时不是重放，而是再审、再拒绝、再计一条违规**。LLM 复核的流程审 4 秒以上是常态，所以管理员连续逐条处理的那几分钟里这类流程的缓存基本不起作用；一次批量处理只算一次。次数在 `runtime.kv_skipped` 里（第 4.3 节；0.8.2 起概览页也显示）。这几种情况都可以用设置页的"清空判定缓存"兜底，代价是又一轮重审。
4. **清空缓存最多 5 秒后在所有节点生效。** KV 里的旧键不删除，到期消失。一个节点新判出的命中和人工处理的结果靠广播传给其他节点；广播丢失时，内存里已把相关片段记成"通过"的节点仍会放行这段内容，直到这些"通过"过期、被淘汰或缓存被清空（0.8.1，第 7 节"改了什么"第 2 条）。
5. **改配置会让缓存失效。** 改流程的级、审核器、题集、阈值或渠道模型之后，该流程的内容全部重审，费用随之上升。
6. **图片**：超过 1200 万像素、解码内存估算超过 112 MiB、或在重画时间预算内画不完的图片不送审（记为未送审的图片数）。没送审的图片不进缓存，每次带它的请求都会再试一次；一直送不出去的图片（例如解不了的）永远不会被审，也不会被缓存成"通过"。**"有的审核器收图片、有的不收"的流程里，请求里只要有一张没缓存成"通过"、这次要送审的图片，已经缓存成"通过"的文字也跟着图片再送一遍**：图片总是和本请求的文字一起审，结果不取决于别的请求缓存了什么（其他流程不重送文字，见第 10 条）。代价是这样的请求不省文字的审核调用，图片一直进不了缓存时（URL 图片、送不出去的图片、下面说的被推翻的图片）带它的每个请求都如此，块数上限 `input_max_chunks` 也按整个请求的文字算（超出时抽样，`input_overflow=block` 时先审的请求被拒绝，与缓存为空时相同）；图片都已缓存成"通过"的请求、流程里没有收图片的审核器的请求、全部审核器都收图片的流程的请求不受影响。图片只有被"自己判了通过"的审核器收到过才缓存成"通过"：OpenAI 审核器命中、Jev 没收到这张图而让请求通过时，图片不进缓存，下次再送，**同一块的文字也不缓存**：规则是"请求通过，但块里有图片被某个审核器收到、却没有被任何通过的审核器收到"时整块不记"通过"，同一个请求每次都整块重新审、每次都得到同一个结果，别的请求把其中的文字审过并缓存了也一样（上一条规则保证图片不会单独送审）。**被后面只读文字的复核推翻的图片命中，每次都放行**（第 1 级收到图片并命中，第 2 级是收不到图片的复核——关掉了图片开关的 LLM 审核器或 Jev，或这一次没收到这张图的审核器（没等到重画名额的 Jev、上游拒绝了图片的 LLM 审核器）——通过；同一级"全部命中""至少 N 个"里另一个审核器没收到图片也一样）；new-api 会拒绝这种请求，因为那里一张图片自成一个内容块，只读文字的审核器推翻不了它。这是负责人 2026-11-10 的决定：按"没有得出结论的审核"处理，而不是第一次放行、之后拒绝。代价是这类请求不走缓存，每个请求都重新调用审核器。**例外**：这张图片一旦在某个请求里单独被判命中（请求里只有这张图，没有文字可供复核，命中没人能推翻），命中进缓存，此后所有含这张图的请求都按重放拒绝，包括之前放行过的那个请求，直到命中条目过期、记录被标为误报或缓存被清空。OpenAI 审核器每次调用只带一张随机抽的图，这一张代表这次输入里全部可用的图片，不逐张补审。
7. **KV 故障与缓存写入**：缓存读 KV 失败时内容照常送审（不会放行从未审过的内容；片段指向的命中条目读不到时，这个片段也按未知处理、重新送审，不凭它的"通过"放行），失败次数在 `runtime.kv_errors` 和健康指标 `kv_errors` 里（第 4.3 节）。**0.8.1 起，一次审核的结论先写 KV，写成功后才进节点的内存，而且是在请求得到回答之后写**（后台写，不重试；写完之前的重复请求见第 7 节"要知道的三件事"）。KV 写失败时这次的结论哪里都不缓存，这段内容下次重新审。一个命中没写进 KV 时，如果它的各个片段随后在别的请求里各自通过并进了缓存，整段内容会按这些"通过"放行，直到缓存到期或被清空——缓存对任何没有作为整体见过的内容都是这样。（0.8.0：结论先进内存、再在后台写 KV，写失败的命中和一个请求里超过 64 个新片段时多出来的"通过"只留在那个节点的内存里；0.8.1 起没有只在内存里的结论。）KV 既不报错也不回答时的后果见第 7 节"KV 不回答时"。
8. **插件不可用时一律放行**（钩子是 `failure: open`，与以前相同）：本应先审的用户和被封禁的用户在这段时间里也会被放行。
9. 界面的改动没有在浏览器里走查过（开发环境没有浏览器）：发布后请走一遍——建一个带补审级的流程并发布、建一个"LLM 题表"审核器并试跑、看一条重放记录的详情、清空缓存、对白名单用户做名单操作、看一条停用流程的绑定。前两项要等所有节点都在 0.8.0 上之后再做（第 3 节）。
10. **LLM 审核器的图片**（第 1.11 节）。
    - **被上游拒绝的图片只按文字审。** 带图片的调用被上游以 400、413、415 或 422 拒绝后只发文字重试一次；一次调用里的图片一起回退，分不出是哪一张被拒。这些图片不算被审过，不会缓存成"通过"；结果里有 `images_refused`（第 1.11 节）。base64 写得不合规范的图片已逐张跳过，不会连累别的图片；但 base64 合规、文件头正常而图像数据损坏的图片仍可能让上游拒绝整次调用，这次调用的全部图片随之只按文字审。
    - **带图调用本身的内存没有按字节准入。** 一次调用最多带 20 MiB 的图片 base64，实测这样一次调用在请求本身之外分配的量随图片张数增加：`openai_chat`、`openai_responses` 约 83–143 MiB（base64 的 4–7 倍；默认最多 8 张图时约 126 MiB），`anthropic` 约 63–123 MiB（3–6 倍）。调用本身不按字节准入，请求是：先审路径上一个钩子请求在整个处理期间占着 `max_inflight_mb`（默认 128 MB）里自己的字节数，后审队列的上限是 96 MiB，所以同时在处理的最大请求在先审路径上大约 6 个、后审队列里还能再有大约 4 个，合计大约 10 个，每个再乘以它那一级里的 LLM 审核器数——最坏情况下仍可能超过插件进程的内存上限（0.8.0 把上限从 512 MB 提高到 1024 MB；最坏情况约 1.3–1.4 GB），进程被结束期间钩子按第 8 条放行。0.8.0 没有为它加限流；带大图的流量大时，把 LLM 审核器放在复核级（只在前一级命中后才调用），或调小 `input_max_images`。
    - **不重画。** 超过 5 MiB 或某一边超过 8000 px 的图片、URL 图片，LLM 审核器看不到。
    - **不报错而忽略图片的上游**会让没被看过的图片缓存成"通过"：这样的审核器要关掉图片开关。
    - **全部审核器都收图片的流程里，同一个请求仍可能先放行、后被拒绝。** 条件是三件事同时成立：一个审核器收到某张图片并命中；另一个本来收图片的审核器这一次没收到它（URL 图片——只有 OpenAI 审核器收；超出 LLM 审核器上限的图片；Jev 没等到重画名额或时间；LLM 的上游拒绝了图片），只审了文字并通过；之后请求的文字被别的请求缓存成"通过"。这时图片单独送审，没收到图片的审核器没有可审的内容，命中成立，请求被拒绝、计一次违规。"有的审核器收图片、有的不收"的流程不会这样（第 6 条：图片总是带着本请求的文字）；这条保护没有用到所有流程，是因为代价——请求里只要有一张进不了缓存的图片（例如 URL 图片），每一轮都要重审全部文字。

## 7. 0.8.1（2026-11-11，0.8.0 上线后的修改）

**为什么改。** 0.8.0 上线当天量到：承载流量的节点上，插件的每次 KV 调用约 50 ms（核心先在 PostgreSQL 里检查插件的授权，约 27 ms，再调 Redis，约 23 ms；另一个节点约 8 ms），而且只能一个键调一次。一个请求约 150 个片段。

- 0.8.0 的判定缓存每 5 分钟把内存里的每个片段结论和 KV 核对一次；核对在请求路径上只有 100 ms 可用，永远读不完，还给每个请求加上 KV 调用和等待。`runtime.kv_errors` 因此每分钟涨约 27——而 KV 一次错也没有报，只是慢（0.8.0 把"在预算内没读完"也计成出错）。
- 一个请求第一次到达某个节点时，0.8.0 最多发 64 个单键调用、合计 200 ms，在这个节点上大约只读得到 32 个，其余的重新送审。
- 0.8.0 的结论先进内存、再在后台写 KV，靠 5 分钟核对把别的节点写的命中读回来。只去掉核对是不够的：一个没先读 KV 就进了内存的"通过"会盖住别的节点已经存进 KV 的命中，该节点把整段内容答成"通过（缓存）"，直到那些结论过期。所以写入的顺序一起改了（下面第 3、4 条）。

**改了什么。**

1. **内存里的缓存不再和 KV 核对**（负责人 2026-11-11 的决定：内存层就是缓存）。一个结论进了节点的内存，就一直用到它过期（`verdict_cache_days`）、被内存缓存淘汰、被别的节点的广播点名、缓存被清空或进程重启。请求的内容都在内存里时，查询不产生任何 KV 调用。
2. **其他节点多久跟上，变了**：新判出的命中、人工处理的结果，靠广播传给其他节点，送达即生效；做处理或判出命中的节点自己在写完后生效。广播丢失时，没收到的节点**不再在 5 分钟后自己跟上**，而是继续按内存里的结论回答，直到这些结论过期或被淘汰（最长 `verdict_cache_days`）。发现某个节点没跟上时，用设置页的"清空判定缓存"（第 6 节第 3、4 条）。
3. **缓存用核心的批量 KV 调用读写，插件不再给 KV 设时限和个数上限。** 内存里没有的内容，查询一次（每 512 个键一次）全部读出来，一直等到 KV 回答；一次审核的结论全部写进 KV（0.8.0 每次最多写 64 个"通过"）。一个 150 个片段的请求第一次到达节点：从"64 个单键调用里读到约 32 个、其余重审"变成"1 次调用、约 50 ms、全部读到"。唯一的时限是请求自己的：客户端断开或核心放弃这次钩子调用时，查询立刻结束，请求按"客户端已离开"处理。
4. **先写 KV，写成功后才进内存；写在请求得到回答之后进行。** 节点内存里的结论因此总是 KV 里有过的。KV 写失败时这次的结论哪里都不缓存（计一次 `kv_errors`），内容下次重新审。0.8.0 那种只留在一个节点内存里的命中和"通过"没有了。
5. **`runtime.kv_errors` 只计真正失败的 KV 调用**（一次批量调用算一次）。KV 慢不再让它增长，也不再有请求因为 KV 慢而重审：慢的 KV 现在表现为钩子变慢。
6. **`/status` 多了 `runtime.kv_writing` 和 `runtime.kv_skipped`**（第 4.3 节）。概览页"队列与运行状态"卡片多了 `kv_writing` 的一行（"正在写入共享缓存的结论"）；`kv_skipped` 在 0.8.1 里界面不显示（0.8.2 加上，第 8 节）。

**要知道的三件事。**

- **写完之前的重复请求会再审一次。** 从请求得到回答到结论写进缓存，正常是两三次 KV 调用的时间（承载流量的节点上约 0.1 到 0.15 秒）。这期间同样的内容再来：通过的再审一次；**命中的再被拒绝一次，并算一次新的违规**（计入观察名单的违规数和自动封禁），不是重放。客户端在被拒绝后立刻原样重试时会碰到。同时到达的相同请求不受影响，仍然只审一次。
- **KV 不回答时请求会等，后果见下面"KV 不回答时"一段。** KV 报错（例如拒绝连接）时与以前一样：立刻当作没有缓存，内容送审。
- **写失败的命中不再留在判出它的节点上。** 见第 6 节第 7 条。

**KV 不回答时。** 这是去掉时限之后新出现的情况（负责人 2026-11-11 的决定：不设时限，也不设兜底）。KV 既不报错也不回答的那段时间里：

1. **先审的请求等在缓存查询上。** 等多久取决于核心的 Redis 客户端：按它的默认设置（读超时 5 秒、重试 3 次），连接还在但不回答时，一次调用约 20 秒后以出错返回，计一次 `kv_errors`，请求在剩下的时间里送审；连不上、或一次查询要读好几批时，会等满核心给钩子调用的 30 秒，然后按 `failure: open` 放行。这些时间是按代码和客户端默认值推出来的，没有在真实的 Redis 故障上量过。
2. **有的先审请求得到 503，而不是放行。** 等待中的请求一直占着 `max_inflight_mb`（默认 128 MB）里自己的字节数（0.8.0 最多占 200 ms）。合计占满之后，新来的先审用户得到 503 `moderation_busy`，后审用户照常放行（第 1.5 节）。
3. **后审基本停掉。** 后审的工作协程在出队时查缓存，同样等在 KV 上；队列满了之后新请求记为丢弃（`dropped`），不审核。
4. **新结论都进不了缓存，重试的命中反复计违规。** 同样的内容每次都重新审；被拒绝的用户每重试一次，就多一条新的违规，计入观察名单和自动封禁。0.8.0 时判出命中的节点靠内存重放，不计违规。
5. **后台写越积越多，没有上限。** 每次审核结束都有一个写在后台等 KV，排在前面的写不结束，后面的就一直等。个数在 `/status` 的 `runtime.kv_writing` 和健康指标 `kv_writing` 里。实测每个等待中的写约占 7 KiB（请求片段多、带命中时更多）：2 万个约 150 MiB。积压到插件进程触及内存上限（1024 MB）时进程被结束，这期间钩子按第 6 节第 8 条放行；进程重启后积压清零。KV 恢复后，积压的写一个接一个处理：故障期间本节点没有过人工处理（包括没做成的，第 6 条）时逐个写完；有过时，查缓存已超过 4 秒的那些什么都不写（第 6 节第 3 条的规则，计入 `kv_skipped`），内容下次重审。
6. **人工处理也排在同一队列后面**，最多等到核心放弃这次 HTTP 调用（30 秒），处理结果提示"已同步 0 条"，KV 恢复后再处理一次。

**这段时间能做什么。** 发现 `kv_writing` 持续增长时先看 Redis：KV 就是核心的 Redis，修好它是唯一能让缓存恢复的办法。设置页上没有关掉判定缓存的选项，`verdict_cache_days` 只能是 1 到 30（插件读到更小的值也按 1 天算）。按代码还有两件事可以做，都没有在真实的故障里试过；设置的保存和下发经过核心，Redis 不回答时这条路本身是否通畅也没有验证过：

- **把 `mode` 从默认拦截改成默认观察**（设置页）。没有名单条目的用户改为后审：钩子只看内存、不等 KV，他们的请求不再变慢，也不会得到 503。代价：这些用户的违规内容不再被拒绝，只在事后记录；而后审在 KV 不回答期间基本停着（上面第 3 条），所以这段时间对他们近似于不审。黑名单用户和拦截级条目的用户仍然先审、仍然等。再退一步的 `mode = off` 是所有请求直接放行，被封禁的用户也不再被拒绝。
- **通过核心的设置接口关掉缓存。** 缓存只在一种状态下是关的：已存的设置里没有 `verdict_cache_days`，且旧键 `cache_ttl_seconds` 为 0。做法同第 5 节第 3 步：`GET` 整份设置，删掉 `verdict_cache_days`，把 `cache_ttl_seconds` 设为 0，`PUT` 回去。之后新来的请求不读也不写 KV，每个请求都整份送审：审核调用、费用和先审的延迟上升，命中每次都是新的违规而不是重放。已经等在 KV 上的查询和已经积压的写不受影响，仍要等 KV 回答或进程重启。恢复：KV 好了之后在设置页填上缓存天数并保存。

**上线经过。** 批量 KV 调用是核心 0.1.273 的构建加的，插件 0.8.1 的 `hostCompat` 因此从 `>=0.1.258 <0.2.0` 抬到 **`>=0.1.273 <0.2.0`**：0.1.272 的核心装不上 0.8.1，必须先升核心。核心 0.1.273 在 2026-11-11 构建、签名之后没有导入、也没有发布；当天北京时间 21:20–21:28 发布的是核心 0.1.274，它带着 0.1.273 的全部内容，内置集里的 moderation 0.8.1 就是为 0.1.273 构建的那个包。核心的滚动升级（两个节点轮流，约 7 分半）全部完成之后，内置同步把插件从 0.8.0 升到 0.8.1，没有单独装插件。发布后两个节点都在 0.8.1 上、ready、没有重启；承载流量的节点上 1791 次审核调用之后，`kv_errors`、`kv_writing`、`kv_skipped` 都是 0。发布记录在 `deploy/gateway/ovh/README.md`。

为什么不允许在 0.1.272 上跑（测试里量的，每次 KV 调用 50 ms）：没有批量调用时 SDK 改成逐键调用、8 个一组。一个 150 个片段的请求第一次到达节点要约 1 秒才查完；更要紧的是写——一次审核的写要占着它涉及的全部键，150 个键的写约 2 秒，这期间本节点别的写几乎都得等。4 次互不相干的 150 片段审核，有批量调用时合计 0.4 秒写完（8 次 KV 调用），没有时 7.8 秒（1200 次）。也就是节点每秒只写得完约半次这样的审核，流量一超过就积压，后果同"KV 不回答时"的第 4、5 条。

插件版本 0.8.1；宿主权限、用户权限、路由都不变，**不需要管理员重新批准，没有数据库迁移，没有设置变化**。KV 里的键和值的格式不变，0.8.0 和 0.8.1 的节点可以滚动混跑（混跑期间 0.8.0 的节点仍按 0.8.0 的方式工作）。构建和上线照以往插件版本的做法。

**升级后的核对。**

- `GET /api/v1/p/moderation/status` 的 `runtime` 里有 `kv_errors`、`kv_writing`、`kv_skipped`；升级时进程重启，计数器从 0 开始。概览页"队列与运行状态"卡片有 `kv_writing` 的一行。
- `runtime.kv_writing` 在承载流量的节点上是 0 或个位数，不持续增长。`runtime.kv_skipped` 在没人处理记录、清空缓存或改 `cache_entries` 时不增长。
- 承载流量的节点上，`runtime.kv_errors` 不再持续增长。它增长就是 KV 调用真的失败了：查 Redis 和核心的日志。
- 核心一侧 `moderation` 钩子的耗时：节点重启后的头一批请求各多一到两次 KV 调用的时间（约 50 到 100 ms），之后回落到没有 KV 调用。插件自己的耗时数字（`runtime.avg_latency_ms`、记录里的耗时）**不包含缓存查询的时间**，从这些数字看不出这次修改的效果。
- 同一个用户的命中记录里，如果出现间隔不到一秒、内容相同、都不是重放的两条，就是上面说的"写完之前的重复请求"。

**回滚。** 插件装回 0.8.0 即可，没有别的步骤：没有迁移要撤，设置和 KV 里的数据两个版本通用，核心不用降级（0.8.0 不用批量调用）。核心 0.1.274 的内置集是 0.8.1，但内置同步只升不降，不会把手动装回的 0.8.0 再升上去。**如果连核心也要退回 0.1.272，先把插件装回 0.8.0，再退核心**：0.8.1 不能跑在 0.1.272 上。回滚后 0.8.0 的行为一起回来：5 分钟核对和它在慢节点上的代价、每个请求最多读 64 个新片段的上限、`kv_errors` 在 KV 慢时增长。

## 8. 0.8.2（0.8.1 上线后的整理，尚未发布）

**是什么。** 0.8.1 上线之后把判定缓存的代码和测试整理了一遍。缓存的规则没有变，第 7 节照旧适用：先写 KV 后进内存、不设时限、`kv_writing`、`kv_skipped`、人工处理之后不写回，都是线上 0.8.1 已有的。对运维可见的只有概览页的两行；另有三处很小的行为变化。整理前后的代码用同一批随机操作序列（150 组）对比过，在这批序列上除下面第 4 条的取整外结果逐字节相同。

**改了什么。**

1. **概览页"队列与运行状态"卡片的两行。**
   - 新增"未写缓存的审核（期间有人工处理或缓存被换）"，就是 `runtime.kv_skipped`（0.8.1 里只在 `/status` 和健康指标里）：本节点启动以来，结论整次没写进缓存的审核次数——人工处理可能在它查缓存之后改过缓存，或者本节点的内存缓存在那之后被换掉了。它只在处理记录、清空缓存、改 `cache_entries` 前后增长；增长不是故障，是第 6 节第 3 条说的代价。
   - `runtime.kv_writing` 一行的文案从"正在写入共享缓存的结论"改为"等待写入共享缓存的审核（当前）"：数的是结论还没写进 KV 的审核次数，是此刻的值，不是累计。KV 正常时是 0 或个位数，持续增长说明 KV 不回答（第 7 节"KV 不回答时"）。
2. **片段特别多的审核，写到一半失败时。** 一次审核有超过 512 个片段键要写时，写分几次调用。中途失败的话，已经写进 KV 的那些键从本节点内存里删掉，并通知其他节点从 KV 重读。0.8.1 不这样做：一个刚判出的命中可能在各片段已记成"通过"的节点上继续按通过回答，直到那些结论过期。
3. **流程异常率告警的状态**存在 KV 里。它的读写失败现在和缓存一样计入 `runtime.kv_errors`：因为节点关停等原因中断的调用不再计。
4. **片段键在 KV 里的有效期向上取整到整秒**（0.8.1 向下取整，最多短 1 秒）。平时看不出区别。
5. 其余是内部整理（代码用词统一、测试拆成五个文件、运行时间减半），没有行为变化。

**不用配置任何东西。** 插件版本 0.8.2；`hostCompat` 不变（`>=0.1.273 <0.2.0`），宿主权限、用户权限、路由都不变，**不需要管理员重新批准，没有数据库迁移，没有设置变化**。KV 里的键和值的格式不变，0.8.1 和 0.8.2 的节点可以滚动混跑。

**上线。** 计划随核心 0.1.275 作为内置插件发布：核心的滚动升级全部完成之后，内置同步把插件从 0.8.1 升到 0.8.2，不需要单独装插件。0.8.2 本身不依赖 0.1.275，在 0.1.274 上也能跑。核心 0.1.275 里与插件 KV 有关的改动（CONTRACTS §93：校验规则只写一处、单键写的有效期有了上界、批量读超限时提前拒绝）对 moderation 没有可见的影响。

**升级后的核对。**

- 两个节点的 moderation 都是 0.8.2。
- 概览页"队列与运行状态"卡片有上面两行。`GET /api/v1/p/moderation/status` 的 `runtime` 里字段与 0.8.1 相同（`kv_errors`、`kv_writing`、`kv_skipped` 都在）；升级时进程重启，计数器从 0 开始。
- `runtime.kv_writing` 是 0 或个位数；`runtime.kv_errors` 不持续增长；`runtime.kv_skipped` 只在处理记录、清空缓存、改 `cache_entries` 前后增长。对照：0.8.1 上线后，承载流量的节点上这三个数都是 0。
- 审核照常进行：记录在增加，重放记录符合预期。

**回滚。** 插件装回 0.8.1 即可，没有别的步骤：没有迁移要撤，设置和 KV 里的数据两个版本通用，核心不用动（0.8.1 在 0.1.275 上照常跑）。回滚后概览页不再显示 `kv_skipped` 一行（`/status` 里仍有），上面第 2 到 4 条回到 0.8.1 的做法。
