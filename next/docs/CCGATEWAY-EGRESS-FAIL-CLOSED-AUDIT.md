# CCGateway 出口故障与兜底检查

日期：2026-10-15。修复源码 `d0a25545c`，核心 `0.1.142`，控制器 `shared-xray.d0a25545c`。

## 结论

同一个 Worker 不会在共享网关或指定上游代理故障后切换到宿主机直连。共享网关停止时，绑定代理及显式直连两种账号都无法出网。生产只做配置读取和升级后的正常请求验证；停止组件、删除路由等破坏性验证均使用独立测试容器。

账号 21、22、27 当前显式配置为直连，它们也必须经过共享 Xray。其余运行账号绑定指定代理。这里的直连是保存的配置，不是故障后的备用路径。

## 生产核对

- 8 个 Worker 各自只有一个 internal Docker 网络，没有 uplink 网卡。
- 所有 Worker 的唯一默认网关和唯一 nameserver 都是本账号网络中的共享 Xray 地址。
- Worker 非 privileged，cap_drop=ALL，没有额外能力；没有 HTTP_PROXY、HTTPS_PROXY、ALL_PROXY、NO_PROXY 环境变量。
- 外部出口模式下，Worker 启动 CLI 时剔除代理环境变量；网络约束仍由容器路由与防火墙执行。
- 共享出口 `ip_forward=0`、forward 默认丢弃；未知来源、非允许流量被拒绝。Xray 默认出站和最终路由为 blackhole。
- 核心的控制器连接、账号隧道失败返回错误，不转发到另一个本地 Worker 地址。

## 实际故障结果

| 操作 | 实测结果 |
| --- | --- |
| 停共享网关，账号为显式直连 | 公网 IP 请求失败，DNS 失败 |
| 停共享网关，账号绑定代理 | 公网 IP 请求失败，DNS 失败 |
| 启动网关但未重放规则 | 公网 IP 请求失败，DNS 失败 |
| 停指定上游代理，Xray 内同时保留 direct 出站 | 绑定代理的 IP 请求和 DNS 都失败，没有改用 direct |
| 删除选中的 outbound | IP 请求和 DNS 都失败 |
| 删除账号来源路由 | IP 请求和 DNS 都失败 |
| 删除共享网关防火墙表，保持 ip_forward=0 | 业务 IP 请求失败，没有普通转发逃逸；修复后可重新建立表 |
| Worker 重新启动，尚未激活默认路由 | 公网 IP 请求失败 |
| 在 Worker 内指定 Docker DNS 127.0.0.11 | 查询失败，不能绕过指定 DNS |
| 暂停 DNS 所在 Python 进程，保留 Xray 子进程 | DNS 失败，已知公网 IP 仍可通过原代理连接 |
| 不运行控制器服务，保留已配置数据面 | 独立网络探针仍可经原代理连接；不代表核心能建立新控制器隧道 |

最后两项不是切换到直连。DNS 并不是每个已建立连接的依赖，控制器也不在每个数据包的路径上。当前没有设计“任意管理组件故障便主动切断全部已建立连接”的租约，本次未增加控制器停机联动策略。

## 已修复的边界

1. **代理记录丢失或协议异常被当作直连。** 原逻辑使用 LEFT JOIN 后的空 protocol 判断无代理；未认领草稿的代理记录被删除时可能落入这个分支。现按是否明确绑定代理区分：绑定记录丢失、协议不合法时 `enabled=false`、`proxy_unavailable`，不能产生 direct 配置；只有明确未绑定才保留原直连语义。独立 PostgreSQL 回归测试覆盖缺失草稿代理、空协议及合法显式直连。
2. **防火墙表缺失后无法恢复。** 原更新批次无条件先删除旧表；旧表已不存在时整个批次失败。现先检查旧表是否存在，再原子提交删除/创建内容。故障期间流量仍关闭，恢复后才重新就绪。

## 仍需区分的账号重试

核心当前 `max_attempts=3`，失败分类允许时会选择同组另一个合格账号。候选选择没有要求新账号与原账号使用同一代理；若组内存在合格的显式直连账号，后续尝试可能经那个账号的直连出口。

这是核心更换账号，不是故障 Worker 自行绕过代理。因此本次结论是“Worker 出口无直连兜底”，不能扩大成“整个 API 请求绝不会换账号或出口”。本次没有修改全局重试策略或已有账号代理绑定。

运行环境的 ready 反映已应用的配置和组件身份，不代表持续验证了所有上游代理的实时可达性。上游新故障可能先体现为请求错误；这也不会授权 direct 兜底。
