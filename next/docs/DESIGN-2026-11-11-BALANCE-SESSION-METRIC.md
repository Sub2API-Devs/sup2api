## 1. 背景

系统设置 → 调度策略 → 均衡负载（§89）有四项：均衡策略（默认 / 流量）、基于上限负载调度、均衡指标（RPM / 并发 / TPM）、根据模型限速。用户在手机上看这一页时提了两个问题：

1. 均衡策略选了“默认”，为什么还能选 RPM / 并发 / TPM。
2. 默认策略是不是就等于“按会话做流量调度”：能不能把默认改成“以会话为指标的流量策略”，不开上限负载时与原来的默认逻辑一模一样。

### 1.1 第一个问题

均衡指标由“流量策略”和“基于上限负载调度”共用（`web/src/views/settings/LoadBalanceSettingsCard.vue` 的 `balanceOff`：两项都关才置灰）。用户截图里上限负载是开着的，所以指标可选，这是对的。

问题在说明文字：策略“默认”的说明一直是“同优先级内按权重随机选号”，上限负载开着时权重其实先被折减了，这句话不完整，才让人以为指标不该可选。

### 1.2 第二个问题：不等价

默认策略的分配单位确实是新会话：每个没命中粘性的会话按权重抽一次号。但它不看各账号当前挂了多少会话，也不读 Redis（`server/internal/gateway/balance.go` `tierWeights`：`c.balance == nil && c.ranked == nil` 时直接返回账号权重）。

流量策略会读当前用量再调整：`w ÷ (r + 0.25)²`，`r` = 账号用量 ÷ 它按权重应得的份额（`trafficWeights`）。把指标换成会话数，只有两种情况与默认结果相同：这一层完全空闲，或各账号会话数恰好按权重比分布。其余情况都不同：

| 情况 | 默认 | 以会话为指标的流量策略 |
|---|---|---|
| 权重 1:1，会话数 40 比 0 | 各 50% | 98.8% 给空的那个 |
| 新加的号、刚恢复的号 | 只拿权重份额 | 短时间内吃掉几乎所有新会话，直到追平 |
| 随机偏差 | 不纠正 | 纠正 |
| 读 Redis | 不读 | 每次挑选读一次 |

所以“把默认改成会话流量”会改变线上行为，不是等价替换。

## 2. 决定

1. **“默认”策略不动**：它是不读用量的基线，默认配置下调度结果与 §89 上线前一致，这一点保持。
2. **均衡指标加第四项“会话”**（值 `sessions`）：流量策略和上限负载都能用它。用户想要的“按会话做流量调度”就是“流量 + 会话”。
3. **默认策略的说明随上限负载变化**：上限负载开着时，说明写明权重先按上限负载折减。

不做的事见第 7 节。

## 3. 会话指标的语义

会话数直接用 §71 已有的计数，不新增计数器、不新增 Redis key：

| 用途 | 用量 | 上限 |
|---|---|---|
| 账号 | `RateUsage.Sessions`：账号会话周期内被准入过的会话数 | `spm_limit` |
| 请求模型所在的指定模型限速列表（`model_limits` 开、上限负载开） | `ModelRateUsage.Sessions` | 列表的 `spm_limit` |
| 请求模型自己的用量（`model_limits` 开、流量策略） | `AccountLimiter.ModelUsage(...).Sessions`（`md:<model>` 层，周期跟随账号） | 无 |

要点：

- **会话是什么**：§71.2。命中粘性规则的请求按粘性会话键算；没有粘性键的请求每个算一个会话（`req:{请求 ID}`），WebSocket 连接算一个（`conn:`）。所以没配粘性规则的分组，会话数接近周期内的请求数。
- **没有滞后**：会话在准入时计数（与 RPM 同一个 Lua 脚本），不像 TPM 要等请求结束。
- **上限负载**：`会话数 ÷ spm_limit × 100`，没设 `spm_limit` 的账号负载为 0，与其他指标一致。用量和上限在同一个周期内，周期长短不影响这个比值。
- **流量均衡的限制**：会话数按各账号自己的会话周期（`spm_window_seconds`，默认 60 秒）统计。同一层里各账号周期不同时，会话数不可直接比较，周期长的账号会显得更忙。不做换算：长会话在任何周期里都只算一次，短会话的数量随周期线性增长，没有对两者都正确的换算。界面说明里写明这一点，建议同一层的账号用相同的会话周期。
- **周期越长，新号“补课”越久**：新加入或刚恢复的账号会话数从 0 起算，追上份额之前权重一直被放大，这段时间它集中接收新会话，时长随会话周期变长（没有实测过具体时长），能挡住它的只有它自己的上限。这是流量策略本来的性质，会话周期可以设得很长，所以在这里更明显。
- 其余规则（只作用于粘性不命中的挑选、读一次、读失败按插件的值调度、记录）全部沿用 §89.3、§89.4。

## 4. 设计

### 4.1 后端

指标是 `balance.go` 里的一张表（`balanceMetricTable`：每个指标给出账号上限、列表上限、账号用量、列表用量四个取值函数），读数和计算都按表走。加会话指标只是加一行，不改流程：

- `server/internal/gateway/balance_settings.go`：常量 `balanceMetricSessions = "sessions"`，加入 `balanceMetrics`（校验、归一化都用这个切片）。
- `server/internal/gateway/balance.go`：`balanceMetricTable` 加一项，四个函数分别取 `AccountRef.SPMLimit`、`ModelLimit.SPMLimit`、`RateUsage.Sessions`、`ModelRateUsage.Sessions`。`rate` 非空，所以走 `readRateUsage`（限流器），与 RPM / TPM 同一条路径。

接口不变：`GET/PUT /settings/scheduling` 的 `metric` 多接受一个值 `sessions`；其他值仍是 400 `invalid_argument`。无迁移。

### 4.2 前端

- `web/src/api/types.ts`：`SchedulingSettings.metric` 加 `'sessions'`。
- `web/src/views/settings/LoadBalanceSettingsCard.vue`：指标列表加 `sessions`（顺序：RPM、并发、TPM、会话）；策略说明改为计算属性：策略为默认且上限负载开着时用新文案，其余不变。
- `web/src/i18n/locales/{zh,en}/settings.ts`：
  - `balance.metrics.sessions`：`会话` / `Sessions`。
  - `balance.modeHints.defaultLimitLoad`：`同优先级内按权重随机选号，权重先按上限负载折减。` / 对应英文。
  - `balance.metricHint` 只留两句（两种用途共用这个指标、何时生效）；TPM 的滞后和会话的口径（各账号自己的会话周期内活跃的会话数，没有命中粘性规则的请求每个算一个，上限是会话数限制；同优先级账号周期不同时不可直接比较）放进新的 `balance.metricDetails`，用 `SSettingRow` 的 `details` 折叠区显示。原因：加上会话的说明后这段文字在手机上要占十行左右，而这一页常在手机上看。
- `web/mock/billing.ts`：本地 mock 的 `PUT /settings/scheduling` 校验也接受 `sessions`（它单独列了一份指标取值）。

### 4.3 文档

CONTRACTS §89 就地修改（标注 2026-11-11）：89.1 的 `metric` 取值、89.2 的指标与上限对应、89.3 的读数来源与周期限制、89.5 的控制台四项与默认策略说明。

### 4.4 兼容与回滚

- 旧核心读到 `metric: "sessions"` 时按 `normalized()` 归一成 `rpm`。滚动升级期间旧节点、回滚后的旧核心都按 RPM 算，不报错；旧节点的 `PUT` 会拒绝 `sessions`（400）。
- 没有迁移，没有新的 Redis key，没有新接口。设置行不改动时行为与现在完全相同。

## 5. 测试

后端（`server/internal/gateway`）：

| 测试 | 断言 |
|---|---|
| 流量 + 会话 | 会话多的账号得到的新会话明显少，读了一次账号用量 |
| 上限负载 + 会话 | 权重按 `会话数 ÷ spm_limit` 折减；没设 `spm_limit` 的账号不变 |
| 上限负载 + 会话 + 按模型 | 请求模型所在列表的会话数和 `spm_limit` 参与，取较大的负载 |
| 流量 + 会话 + 按模型 | 比较 `ModelUsage` 的会话数，不读账号自己的用量 |
| 设置接口（`db_test.go`） | `PUT` 接受 `sessions`，并且存下的行就是设置缓存读到的值；非法值的用例原来用 `"sessions"` 当非法值，换成 `"tokens"` |
| 限流器（`account/limiter_test.go`） | 按模型的会话数在周期内确实计数（原来只断言过期后为 0） |

前端（`SchedulingPolicyView.spec.ts`）：四个指标的名称和顺序；能选“会话”并随保存提交 `metric: 'sessions'`；策略为默认时，这一行自己的说明随上限负载开关切换（按中文原文断言），流量策略的说明不变。

四个后端用例没有另写一份，而是把原有的 RPM 用例改成按指标跑的子测试（`rpm`、`sessions`）。验证过它们有效：把会话那一行临时改成读 RPM，四个 `sessions` 子测试全部失败。

## 7. 不做的事

- 不改“默认”策略的行为，也不把默认值改成流量策略。
- 不新增“进行中的会话数”计数：现有的是周期内出现过的会话数，够用且已有；另起一套计数要改限流器和 Redis 结构。
- 不按周期换算会话数（第 3 节）。
- 不升版本、不写 CHANGELOG、不部署：这些随下一次核心发布做。
