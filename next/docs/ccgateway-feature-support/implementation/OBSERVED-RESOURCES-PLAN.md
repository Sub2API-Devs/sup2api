# Observed provider resources and parent-call ownership

Sixth-batch design; fifth-batch ports/schema remain frozen until its checkpoint.

## RegisterObserved contract

Input: authenticated `ResourceOwner`, verified `ResourceBinding`, plugin/kind, remote ID, real bytes/metadata, optional provider expiry, and trusted `RequestStartedAt`. The latter is generated by the core after successful ownership validation immediately before dispatch; it is never taken from client metadata, a client timestamp, or response arrival time. Output is the existing or newly allocated public resource record.

The service uses an owner quota advisory lock, a binding/remote identity advisory lock, then row locks. This ordering serializes same-owner quota changes and cross-owner registrations of one remote identity. Identity is `(plugin, kind, account, principal, generation, remoteID)`; it never depends on an unverified filename or tool input. The existing unique index remains a database defense for active rows.

- An existing remote identity owned by another tenant conflicts. No reassignment or copying occurs.
- A same-owner ready record returns the same public ID. Repeated JSON/SSE observations do not consume another object or byte reservation. File bytes are immutable; a mismatch is an error requiring investigation rather than a new alias.
- Deleting, delete-uncertain, deleted and failed records cannot be revived by observation. Tombstones must be checked even though the current active-remote unique index excludes deleted rows.
- New records require quota for count and real bytes. A generated file must first be verified by the gateway's fixed-account metadata GET; this port is not evidence that the provider created an arbitrary reported ID.
- No remote provider side effect is performed by registration. If quota is unavailable after a provider has already produced an artifact, the service returns a typed error without inventing ownership, silently freeing another object, or repeating the model call. The response integration must explicitly handle that outcome.

## Container expiry versus Files expiry

New containers require a real, nonzero provider expiry. Unknown expiry cannot create an indefinitely usable container. Files retain their separate existing expiry semantics.

An existing container may be renewed only if it was ready and unexpired at the trusted request dispatch time. A request starting after expiry is rejected. A response may arrive after the old expiry and still complete that previously authorized dispatch; response arrival is not a fresh permission grant.

The effective container expiry uses the maximum of the previously verified expiry and the new provider-confirmed expiry. This prevents concurrent late responses from shortening a newer verified lifetime. It does not revive deleted/failed resources or reuse a changed issuer. Provider metadata is retained as facts from the observation; the effective lifetime is a separate scheduling constraint. Timestamp values are normalized to PostgreSQL microsecond precision for replay stability.

## Parent tool-call context binding

A new additive migration (proposed `0039_provider_resource_contexts.sql`, coordinate the number at checkpoint) stores:

- owner user/group;
- plugin and full account/principal/generation binding;
- bounded context kind and parent tool-call ID;
- target public resource ID, created timestamp, and optional metadata/evidence digest if needed by the final caller contract.

The unique lookup key is owner + full binding + context kind + parent ID. `BindContext` validates the target resource within the same transaction and inserts idempotently. The same key may only point to the original target; another container owned by the same tenant is still a conflict. `ResolveContext` checks that owner/binding still match and the target is currently usable before returning it. Cross-owner lookup returns not found. A missing mapping never falls back to a caller-supplied container or guessed remote ID.

Use a small generic context-kind contract (initially PTC parent calls), not a second generic task scheduler. Resources retain tombstones; context associations do not cascade into authorization for another issuer. No credentials are stored in either table.

## Verification plan

- Parallel duplicate observations yield one public ID and one quota allocation.
- Cross-owner registration of the same binding/remote ID cannot win twice.
- Deleted/failed identities and changed issuer generations cannot be resurrected.
- Container response arriving after old expiry renews only with a valid earlier trusted dispatch time; genuinely late new requests fail.
- Older concurrent expiry facts cannot shorten a newer verified expiry.
- Parent-ID bindings remain immutable across restart and cannot select another same-owner container.
- Linux PostgreSQL integration verifies advisory locks, unique constraints, quota accounting and recovery. Unit tests cover validation and expiry decisions. Real provider artifact discovery belongs to the gateway/Worker integration stage.
