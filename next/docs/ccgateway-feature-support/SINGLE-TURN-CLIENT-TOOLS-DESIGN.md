# CCWorker 单轮响应与客户端工具循环设计说明

日期：2026-10-08（Asia/Shanghai）。状态：**设计提案，尚未作为配置或代码变更执行。** 本文用于说明分支讨论中的单轮方案，不修改、取消或替代主任务正在实施的计划；是否采用及实际支持范围须经后续评审与测试确认。

## 1. 目标

对于客户端负责执行的工具，CCWorker 每次接收一个 API 请求，返回一个完整的模型响应。工具执行及下一次请求由客户端驱动，Worker 不擅自增加客户端不可见的工具发现和推理循环。

建议该模式统一向 CC 传入 `--max-turns 1`，同时实现工具执行前拦截、完整响应提取与历史恢复。**仅设置该参数并不能完成此设计，也不能保证只有一次上游 HTTP 请求。**

“一轮”不表示“只能调用一个工具”。一个 assistant 响应可以包含多个 `tool_use`；例如五个 Read 应完整返回，客户端执行后再提交五个对应结果。

## 2. 官方参数的含义

Agent SDK 将 `maxTurns` / `max_turns` 定义为工具使用往返轮次上限，达到上限会产生 `error_max_turns`。CLI 的 `--max-turns` 用于 print 模式，默认不限制，触及上限以错误结束。官方没有要求网关采用 2、4 或 5 轮。[Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop#turns-and-budget)、[CLI reference](https://code.claude.com/docs/en/cli-reference)。

官方说明工具搜索会增加一次往返，发现的工具定义供后续轮次使用。因此，直接把现有内部搜索流程的轮次上限改成 1，不能据此认定搜索及后续调用仍完整可用。[Tool search](https://code.claude.com/docs/en/agent-sdk/tool-search#how-tool-search-works)。

参数限制不是 HTTP 请求次数控制，也不是“禁止工具执行”的权限设置。CLI 重试、辅助请求、提供商内部执行，应分别观测和约束。

## 3. 三类工具必须分开处理

### 客户端声明并负责执行的工具

Read、Bash、自定义工具，以及客户端自己提供的工具搜索函数，均按客户端工具协议处理。归属依据是本次请求的工具定义、协议类型和执行合同，不能只根据名称是否包含 ToolSearch 或 MCP 前缀判断。

Worker 将原始工具定义适配给 CC，获得模型响应后，把需要映射的工具名称还原为客户端原名，保留调用 ID、输入及所有响应块。实际执行交回客户端。

CC 的本地 Read、Bash 等能力必须在执行前被可靠拦截；不能因为 `maxTurns=1` 就允许它先在容器执行，再把结果返回。容器文件系统和客户端文件系统不是同一个执行环境。

### CC 容器额外提供的内部 ToolSearch

这是运行时增加的工具，客户端可能从未声明，也无法查询容器中的 MCP 目录。不能将它冒充客户端工具直接返回，更不能只改名来制造兼容。

在本文建议的单轮模式下，不主动注入这种内部发现流程。对按原 API 语义本就应完整提供的工具，提前加载本次请求的完整可用定义；不改变其名称、schema、可见性和客户端执行归属。

若客户端明确使用 `defer_loading`、工具引用或动态发现协议，不能为了单轮而默默改成全量加载、将 `defer_loading` 改为 false 或删除相关 beta。必须走已验证的等价适配；不具备时，在调用模型前明确拒绝该组合。

### Anthropic API 服务端工具

API 服务端 Tool Search、Web Search 等由提供商执行，使用相应的服务端工具块、结果及续接协议。它们不等于 CC 本地 ToolSearch，也不能转换成客户端 `tool_use` 后要求客户端代执行。

保留提供商实际返回的工具调用、结果、引用、用量和终态；若返回 `pause_turn`，由调用方依据该 API 协议携带完整内容继续。`maxTurns=1` 不意味着提供商内部只能执行一次工具。具体模型及工具组合仍需验证。[官方服务端工具协议](https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools)。

## 4. 客户端工具的完整流程

1. 客户端提交 system、完整 messages、tools 及其他合法参数。
2. Worker 还原历史，加载本次可用工具定义，以单轮模式启动 CC。
3. Mod／执行控制在任何客户端工具产生本地副作用之前拦截调用。
4. Worker 提取完整模型响应，保留文本、thinking、签名和全部工具调用，按原协议返回。
5. 客户端执行工具；下一次请求带上完整 assistant 内容和对应 `tool_result`。
6. Worker 根据新请求继续正常生成，不能因为历史里存在工具调用而再次执行旧工具。

下面是五工具场景的结构示意，不是完整 HTTP 响应：

```text
客户端请求 1
  → Worker / CC
  ← assistant: Read A、Read B、Read C、Read D、Read E
     stop_reason: tool_use

客户端执行五个 Read

客户端请求 2
  messages: 原历史
          + 完整 assistant 响应
          + 五个按 tool_use_id 配对的 tool_result
  → Worker / CC
  ← 最终回答，或下一批工具调用
```

“都返回”指合法模型响应中的全部内容；不包括容器凭据、内部 Mod 控制帧、随机传输标记或客户端未声明的运行时工具。

## 5. 达到轮次上限时如何处理

需要分别判断 CLI 进程结果与 Anthropic API 响应完整性，不能仅根据退出码决定请求成败。

- 已取得可验证的完整工具调用响应，且工具未在容器执行：可以按原 API 返回该响应；CLI 因交接触及上限的状态不能自动改写成 502。
- 只收到部分参数、缺少必要终态、工具 ID 冲突或响应被截断：不能补造成功响应或 `message_stop`。
- 尚未取得完整响应就达到上限：明确报告未完成，不静默追加内部轮次。
- 上游正常返回 refusal：保留正常响应和原终态，不改成网关错误。
- 上游 HTTP 错误或流内错误：保留适当的错误语义；已经发出 SSE 后不能假装还能重新发送 HTTP 状态。

这里的“可验证完整响应”需要以原始响应事件或等价完整结果为证据，不能仅因为看见一个 `tool_use` 就忽略所有 `error_max_turns`。

## 6. 历史、缓存和用量要求

- 保留原始角色、顺序、工具 ID、输入精度、完整结果、system、thinking 和签名；不插入虚构工具结果。
- 工具拦截不能留下“容器已执行／拒绝执行”的合成结果，污染下一次客户端历史。
- 新账号冷导入、客户端续聊和回退分支，应从客户端提供的完整有效历史还原，不依赖上一次 CC 进程仍存活。
- 缓存断点和工具目录需要按原协议保真；本地 prefix-hit 不等于提供商缓存命中。
- 返回实际提供商报告的用量，不把内部状态事件当作新增计费请求，也不能因 CLI 触及上限丢掉已经发生的用量。
- 不保证改变内部工具加载策略后仍命中旧缓存；历史 namespace 与旧快照兼容性必须明确验证。

## 7. 前端与配置展示建议

在“请求与工具”中，以“客户端工具执行”功能说明默认单轮与客户端回传结果的流程。在“CC 特性”中，明确内部工具搜索是否启用，以及它与单轮模式的兼容关系。

不能让界面同时宣称“严格单轮交回客户端”和“Worker 自动隐藏执行内部 ToolSearch”，却不说明两者差异。若保留内部多轮模式，应作为明确不同的运行模式，并展示其支持条件。

能力目录应将客户端工具搜索、CC 内部工具搜索、API 服务端工具搜索放在同一特性下说明不同执行归属，而不是只放一个含义不明的 ToolSearch 开关。保存配置后显示实际生效模式；不靠镜像名称推断能力。

## 8. 实施与验收

先确定并验证工具执行归属与拦截时机，再修改轮次配置。建议按以下顺序实施：

1. 为单轮模式建立明确合同，确认当前所有相关路径及旧内部结构化续轮的兼容策略。
2. 关闭该模式额外注入的 CC 内部搜索，仅按原请求加载合法工具；不静默降级延迟加载协议。
3. 完成工具执行前拦截、名称还原和完整响应交接。
4. 区分正常工具交接导致的上限退出与真正不完整响应。
5. 校验 JSONL 历史、缓存、用量和错误处理，再同步前端说明与能力目录。

必要验收项：

- 普通文本、单工具、同一响应五工具；JSON 和 SSE 都覆盖。
- 客户端声明的搜索工具往返，确认 Worker 不自动执行下一轮。
- 客户端未声明的内部 ToolSearch 不被注入或泄漏。
- 服务端搜索及 pause_turn 保持独立协议，不转成客户端工具。
- 延迟加载、工具引用和 beta 的等价适配或明确拒绝，不偷偷改参数。
- 新会话、完整历史续聊、冷账号导入、回退后追加消息、工具定义变化。
- 容器没有执行客户端 Read/Bash 的副作用；一个响应中的多个工具不会被拆掉或丢失。
- 完整 tool_use + 上限退出、参数半截、错误 SSE、取消、超时及正常 refusal。
- 原生工具／MCP 工具映射、工具结果尾部空白、签名和大整数保真。
- 显式采集实际上游调用次数与用量，不能从 `maxTurns=1` 推断只有一次 HTTP 请求。

旧的内部结构化输出续轮不能直接继承到单轮模式：能走真正 API 结构化输出的请求按对应适配处理；仍必须由 CC 内部续轮完成的组合，应明确区分或拒绝，不能隐藏第二轮。

## 9. 与当前实现的区别

本次只读代码中，`runner_config.go` 的 `maxTurns()` 仍按路径返回 1、2、4 或 5；其中普通路径及全部工具已加载的强制路径为 1。本文没有把它修改为统一 1，也没有核验或改变线上配置。

本方案主张客户端工具循环不由 Worker 隐藏执行。若仍选择保留 CC 内部自动搜索，则需要另外的完整内部历史和用量处理合同；那是另一种运行模式，不能称为本文的单轮客户端交接模式。

**交付完成标准不是“命令行出现了 `--max-turns 1`”，而是客户端获得完整合法响应、工具执行归属正确、历史可继续，且所有不等价组合都明确说明。**
