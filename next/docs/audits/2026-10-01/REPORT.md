## 1. 范围与结论

深入审核范围是当前部署的 `next/`：核心服务、SDK、7 个插件、相关前端、构建与部署配置。先遍历生产代码中的后台循环、定时任务、进程内状态、共享读写和调用入口，再追踪有多节点影响的路径。纯展示组件和无状态解析/打包代码做状态入口扫描，不将其冒充为逐行安全证明。旧 `backend/` 做了额外风险扫描，见第 8 节，**没有完成旧平台全部代码的同深度审计**。第三方依赖、生成代码不作为本次自研代码逐行审计对象。

核心判断：项目已具备共享数据库、Redis 锁、任务认领、账本幂等和插件发布协调机制，但不能据此认为所有状态都能正确跨节点收敛。需要处理的问题主要分为：

1. 任务身份和访问归属：视频查询必须绑定用户与原账号。
2. 执行权：槽续期、租约丢失、任务执行期间互斥。
3. 状态收敛：配置确认、缓存版本、迟到写入。
4. 生命周期：发布失败 fencing、卸载排空、启动补偿、停机落账。
5. 原子业务操作：令牌撤销、权限集合替换、速率额度与冷却。

下面整理为 **20 组整改项**，另列设计边界和待验证项。P1 表示应优先修复的访问控制、数据或核心限制问题；P2 表示真实条件下可触发的正确性/可用性问题。严重度不等于已经在线上发生。

证据标记：

## 2. 视频进度轮询：现状与应有边界

### 已有机制

`volcengine` 没有在 `Init` 中启动视频轮询，也没有声明视频轮询 `jobs[]`。当前计费核对由核心 `usage.Reconciler` 执行：

- `server/internal/usage/reconcile.go:173`：扫描使用集群锁及 `KeepLock` 自动续期。
- `reconcile.go:234`：原子 `UPDATE ... FOR UPDATE SKIP LOCKED` 认领任务，推迟 `next_check_at`，形成 3 分钟租约。
- `reconcile.go:553`：结算事务重新锁行、检查状态，账本有幂等键。
- 插件建议首查约 20 秒、进行中约 30 秒。节点故障后由其他节点继续认领。

因此“每个节点的火山插件各自启动一个后台视频轮询”不是当前代码事实。

### 仍缺少的能力

客户端 `video_query` 走网关转发路径，每次 GET 都请求上游，并不读共享进度快照。这条路径可以与其他客户端查询、后台计费核对同时查询同一任务。当前 `video_tasks` 保存身份、模型、粗状态和估值，**没有可直接返回客户端的完整状态/结果快照**。

如果目标是“同一任务由一个节点查询，其他节点读取共享进度”，需要统一后台核对与客户端查询的上游观测结果。推荐边界：

| 部分 | 必要约束 |
|---|---|
| 任务身份 | 内部任务 ID，绑定 `user_id`、`account_id`、插件、上游任务 ID；不要假定不同 relay 的裸 ID 全局唯一 |
| 提交 | 将任务身份可靠落库；与计费预扣建立可恢复的关联，避免成功回包后只能依赖内存队列 |
| 轮询认领 | 按任务使用数据库条件认领/租约；不同任务可分散到不同节点，无需固定全局主节点 |
| 续期与接管 | 租约丢失停止当前工作；过期可接管；迟到结果用 claim token/版本 CAS 拒绝 |
| 进度快照 | 共享存储保存状态、结果、最后查询时间、下次查询时间；终态不可被旧响应改回进行中 |
| 客户端查询 | 先校验用户归属，再读共享结果；需即时刷新时也复用任务认领机制 |
| 账号 | 只能使用提交时账号；账号不可用时明确失败/等待，不能切到其他账号 |
| 计费 | 继续使用事务、终态检查和幂等账本；不能把 Redis 锁当作唯一的防重复扣费依据 |

这是待实现的统一异步任务能力，而非简单在插件 `Init` 外套一把全局锁。当前只有视频提交和查询端点，没有视频取消端点；未来取消应复用同样的归属与账号约束。

## 3. 确认的整改项

### F01 — P1：视频查询缺少任务所属用户校验

**证据：代码时序确认；新发现。** `plugins/volcengine/internal/volcengine/video.go:145`、`:159`、`:225`。

提交写入 `user_id`，查询却只读 `model,state`，`ResolveModel` 不比较 `RequestMeta.user_id`。用户 B 有有效 API Key、可访问同一模型且知道 A 的任务 ID 时，如果选中原上游账号，就可能拿到 A 的任务状态及生成结果。共享数据库不会自动提供租户隔离。

修复：任务解析先校验归属，未授权与不存在返回一致错误；跨两个节点、两个用户验证 B 的查询不会访问上游。不能仅在前端隐藏任务 ID。

### F02 — P2：视频查询未硬绑定提交账号

**证据：代码时序确认；已知未修。** `plugins/volcengine/internal/volcengine/video.go:161`、`platform.go:459`；`server/internal/gateway/rank.go:78`、`:134`、`:173`。

A 账号提交的任务，查询解析模型后仍进入普通账号调度，可能使用 B 账号的地址与凭证，得到 404 或其他上游的同名任务。

**仅实现 `RankAccounts` 不充分**：粘性命中会跳过排名，排名 RPC 失败会保留默认候选，全部权重为 0 也会回退。修复应增加不可被调度、粘性或失败重试绕过的账号硬约束。验证必须覆盖原账号冷却、排名 RPC 失败及多账号同模型等条件。

### F03 — P1：用户槽与账号槽的续期登记互相覆盖

**证据：已复现；新发现。** `server/internal/cluster/slots.go:110`、`:122`、`:182`；调用方 `gateway/pipeline.go:169`、`gateway/dispatch.go:265`。

同一请求先获取用户槽，再获取账号槽。Redis key 不同，但本机 `held` 仅以 `bootID:requestID` 为键，后一次登记覆盖前一次。用户槽不再续期，默认 5 分钟后过期；其他节点可再接入超过用户上限的请求。释放账号尝试也会删除这个共享索引。

修复：登记、续期、删除均使用 `(slotKey,member)` 唯一标识。复现已证明：模拟请求仍运行，续期后用户槽为 0、账号槽为 1、登记只有 1 条。

### F04 — P2：Redis 槽丢失后不向在途请求反馈

**证据：槽层已复现；新发现。** `server/internal/cluster/slots.go:193`；`gateway/pipeline.go:108`。

Redis 重启或网络分区回收后，原请求可能仍在上游执行。续期使用 `ZADD XX`，成员消失时不会重建，代码未检查结果，仍返回成功。入口健康检查不能取消已在途的请求，集群计数可低于真实并发。

修复：将槽表示为能报告丢失的租约，在途请求消费取消信号；设计恢复接流协议。直接去掉 XX 会在新请求已占满时重新插入旧槽，也不能保证上限。

### F05 — P2：插件配置下发失败后不再重试

**证据：已复现；新发现。** `server/internal/plugin/grpcruntime/instance.go:538`，周期调用 `plugin/rollout/reconcile.go:314`。

节点 B 先更新 `settings` 指纹，随后 `Configure` 失败；下一轮看到指纹相同就返回成功。A 使用新配置，B 长期使用旧配置，直到再次变更或重启。5 秒轮询无法补救提前更新的确认状态。

修复：分离“宿主已读取的期望配置/权限”和“进程已确认应用的配置”，Configure 成功后才推进后者，失败重试并串行化。**不能把宿主撤权也推迟到插件 Configure 成功之后。** 本地协议桩复现第二次 Refresh 返回成功但 Configure 总计只调用一次。

### F06 — P1：卸载清库早于全节点排空和最终并发检查

**证据：代码时序确认；新发现。** `server/internal/plugin/install/uninstall.go:61`、`:77`、`:84`。

Disable 立即将数据库状态改为 disabled。卸载据此继续 DROP schema 时，另一节点仍可能运行插件请求或任务。另一个交错是：A 读 disabled，B Enable，A 先 DROP，再在最终行锁检查中发现已启用并返回 409；报冲突时数据已经被删除。

修复：持久化卸载中状态，与启用/升级互斥；等待所有节点停止及实例 drain 完成后才清理，清库与迁移/生命周期锁遵守同一协议。验证暂停节点 B 的退出时不得清库，并发 Enable 不得导致“删完才报冲突”。

### F07 — P2：发布失败分支漏掉 fencing

**证据：代码时序确认；新发现。** `server/internal/plugin/rollout/controller.go:537`；`coordinator.go:55`、`:219`、`:307`。

旧协调者 A 停顿超过租约，B 接管推进版本；A 恢复后仍可能在取消传播前执行失败写入。`finishFailed` 只检查 ID 和 preparing，能把 B 接管的发布标失败并回退插件状态。正常 commit/complete 有 `row_version + coordinator_boot_id`，失败分支没有。

修复：协调者失败写入也带身份与版本条件。管理员主动 Cancel 另保留其操作语义，不应机械套入协调者限制。验证旧协调者的迟到失败更新必须影响 0 行。

### F08 — P1：刷新令牌整族撤销可漏掉并发新后代

**证据：代码时序确认，未做真实 PG 交错复现；新发现。** `server/internal/iam/auth.go:149`、`:167`、`:178`；`iam/users.go:435`。

已有已轮换 A 和有效 B。节点 1 锁 B、撤销 B 并插入 C 尚未提交；节点 2 处理 A 重放，以语句快照 UPDATE 同族未撤销令牌，看到旧 B 并等待，但看不到未提交 C。节点 1 提交后，节点 2 跳过已撤销 B，C 不在该 UPDATE 快照中，仍可刷新。锁当前 token 行不足以保护整个 family。

修复：持久 family 状态，旋转与撤销锁相同父行；全用户撤销用用户版本或统一父锁协议。验证按上述 barrier 固定交错，重放撤销后 C 必须不可用。

### F09 — P2：并发替换用户分组会意外合并授权

**证据：代码时序确认；新发现。** `server/internal/group/group.go:524`。

原集合为空，两节点分别 PUT `[g1]`、`[g2]`；两次 DELETE 都删不到，再各自 INSERT，最终得到 `[g1,g2]`。成员唯一键不能保证整集合替换。

修复：事务内先锁用户父行，再检查、删除、插入；各入口使用同一协议。验证最终只能等于某一份完整提交，而不能合并两份互斥授权。

### F10 — P2：API Key principal 缓存缺少版本化失效

**证据：代码时序确认；新发现。** `server/internal/apikey/apikey.go:226`、`:263`、`:500`、`:626`；`iam/users.go:277`。

两类后果：

- A 读到旧的有效 key，B 撤销并 DEL 缓存，A 再 SET 回旧状态，使已撤销 key 最长按 60 秒 TTL 继续被接受。用户的 `gateway:use` 校验不能识别其某一把 key 已被撤销。
- 修改用户 `max_concurrency` 没有使共享 API Key principal 缓存失效，所有节点最长 60 秒使用旧用户限额。

修复：认证/调度属性的单调版本、撤销版本及回填校验；不能只多发一次 DEL。验证将旧读取暂停在 SET 前，完成撤销或限额修改后再放行旧回填。

### F11 — P2：RPM/SPM 检查与占用不是原子操作

**证据：代码时序确认；新发现。** `server/internal/account/limiter.go:87`、`:124`；`gateway/dispatch.go:59`。

两节点同时读到仅余一个请求或新会话名额，都通过 `Exhausted`，之后才各自 `Hit`，突破额度。共享 Redis 和原子 INCR 不等于原子“检查并预占”。

修复：候选确定后 Lua 原子校验并占用 RPM、新 session 名额，失败再换候选；若 TPM/TPD 也要求严格限制，需要预估预占和最终差额结算。验证同时竞争最后一个名额，只有一个成功。

### F12 — P2：账号冷却可能被另一节点缩短

**证据：代码时序确认；新发现。** `server/internal/account/directory.go:156`。

PTTL→比较→SET 分离。A、B 都读无冷却，A 写 10 分钟后 B 写 1 分钟，长冷却被覆盖；双方还可能都发布首次冷却事件。

修复：原子比较截止时间并只延长，返回是否首次建立；仅首次获胜者发状态事件。验证任意交错不能缩短已有冷却。

### F13 — P2：部分配置更新发生丢失更新

**证据：代码时序确认；新发现。** `server/internal/gateway/settings_api.go:110`、`gateway/sticky_api.go:598`、`billing/settings.go:106`、`usage/reconcile_settings.go:208`。

接口读取整份 JSON、内存合并传入字段，再覆盖保存。两个节点修改不同字段时，后提交者会恢复对方字段的旧值。广播只会把已经写错的结果传播出去。

修复：锁设置行后读改写，包含首次创建竞争；或对已验证 patch 使用原子 SQL 合并，并在合并后的最终配置上验证跨字段约束。验证并发修改不同字段后两者均被保留。

### F14 — P2：失效前的旧查询可重新污染缓存

**证据：代码时序确认；新发现。** `server/internal/billing/pricer.go:36`、`billing/settings.go:42`、`gateway/settings.go:153`、`gateway/sticky.go:170`、`proxy/proxy.go:224`。

共同交错：旧查询开始→其他节点更新→本节点收到广播清缓存→旧查询返回并重新填入。价格约 60 秒、代理/粘性约 30 秒、网关配置约 10 秒才可能自然纠正。mutex 只解决内存竞争，没有确认该查询是否属于失效前版本。

修复：读之前记录 epoch，写回检查 epoch；代理拒绝倒退版本。可参考已有正确保护的 `account/directory.go:61`。验证阻塞旧查询跨过 invalidate 后不得缓存旧值。

### F15 — P2：moderation 旧自动封禁决定可覆盖人工解封

**证据：代码时序确认；新发现。** `plugins/moderation/internal/moderation/store.go:130`、`:144`；`routes.go:570`。

A 统计违规达到阈值后暂停；B 自动封禁，管理员完成解封并更新 `unblocks.at`；A 再用旧统计插入 blocks，重新封禁。唯一键挡不住被删除后重新插入，广播只会传播错误结果。

修复：统计和封禁写入与人工解封共用数据库串行化边界，优先每用户持久状态行/版本；低流量可用明确的事务表锁。验证解封完成之后，不允许旧判定重新建封禁行。

### F16 — P2：火山素材索引会被迟到响应回写为旧状态

**证据：代码时序确认；新发现。** `plugins/volcengine/internal/volcengine/routes.go:499`、`:560`、`:716`、`:767`；`store.go:115`、`:142`。

A GET 上游读到旧值，B PATCH 上游及索引成功，A 再无条件 UPDATE 旧值，共享列表便倒退。两个 PATCH 的上游完成顺序与落库顺序相反也会发生。索引身份唯一键不保护写入顺序，列表读库且没有定期校正。

修复：同账号同资源的修改、刷新、删除使用一致协调协议；读回填增加版本 CAS，拒绝调用期间已变化的行。Redis 锁失效后的迟到写入仍需数据库版本保护。用可暂停的假上游复现旧 GET 覆盖新 PATCH。

### F17 — P1：容器停止宽限不足以完成排空和落账

**证据：配置与退出路径确认；已知未修。** `deploy/single/compose.yml:40`、`:89`；`server/internal/app/app.go:59`、`:297`；`usage/settler.go:209`。

两应用服务均未设置 `stop_grace_period`；Compose 通常仅给默认 10 秒，而应用 HTTP 排空窗口为 30 秒，之后还依次关闭后台组件（共享 45 秒预算），用量队列还需写库。长请求或慢库时会在落账前被强杀。单纯重试账本无法恢复从未持久化的内存记录。30+45 秒只是计划预算，并非严格最大值，部分 Close 不接收/遵守该 context。

修复：建立统一可执行的关停预算，容器宽限覆盖该预算；先停止接流并处理在途请求，再排空所有用量写入，最后关闭 DB。验证需带长流、满队列、慢数据库执行滚动停止，核对请求、usage 和账本一致。

### F18 — P2：满队列后的异步落库不受 Stop 等待

**证据：代码路径确认；新发现。** `server/internal/usage/settler.go:151`、`:163`。

Submit 在队列满时另起 goroutine 写库，但该 goroutine 未登记到 `s.wg`。可行时序是：fallback 已创建但尚未运行或取得数据库连接，workers 排空并退出，Stop 返回，应用关闭连接池/退出；fallback 随后获取连接失败，仅记 logLost，没有持久重试。`pgxpool.Close` 会等待已借出连接，因此不能说它会强杀已经进入事务的 INSERT。即使加长容器宽限，未取得连接的写入任务仍缺少等待保护。

修复：备用写入也纳入受控生命周期和完成等待；关闭阶段拒绝/可靠接管迟到提交。验证让备用写入暂停在取连接之前、让队列 worker 结束，Stop 不应先报告完成。HTTP 排空超时后还需明确取消并等待在途请求，避免生产者在消费者退出后继续 Submit。

### F19 — P2：内置安装失败后没有持续收敛，健康也不代表插件就绪

**证据：代码路径确认；新发现。** `server/internal/app/app.go:215`、`:250`；`plugin/install/builtin.go:135`。

内置安装锁只在启动尝试一次，竞争失败/Redis 出错的节点直接跳过。持锁节点若在创建 rollout 前退出，其他已启动节点无后续安装补偿。单包错误只记日志，而 healthz 仅看 PG/Redis 健康，仍可返回正常。

修复：把内置期望状态纳入可重试协调过程；readiness 明确必要插件是否就绪。另需显式 draining 状态：SIGTERM 后立即调用 HTTP Shutdown 会关闭监听，并非“继续接新请求 30 秒”，但目前没有先通知负载均衡摘流再排空的就绪阶段。

### F20 — P2：跨节点切换版本时静态资源可能 404

**证据：代码路径确认；新发现。** `server/internal/plugin/routes/routes.go:322`、`plugin/registry/registry.go:474`；宿主资源另见 `server/internal/webui/webui.go:78`。

请求 A 的 `/ui/plugins` 得到新版本 hash，资源请求落到尚未切换的 B。B 只接受当前 generation 的 AssetBase，即使已准备新包也返回 404。旧页面延迟加载旧 hash 也受影响。宿主前端滚动发布时，旧 HTML/新节点之间也存在仅持有本版本 assets 的同类风险。

修复：按明确 key/version/hash 获取已批准、受信且允许暴露的包资源，保留旧版本资源窗口；继续执行路径白名单与 CSP。宿主资源可采用保留多版的统一静态分发。单纯把普通 API 固定到某个节点不是完整的版本资源策略。

## 4. 设计边界和需要明确的保证

| 项目 | 当前事实 | 后续处理 |
|---|---|---|
| jobs 执行互斥 | `job/job.go:264` 的 key 含触发时间；`:310` 手动执行是另一个 key | 同触发点去重不等于执行期间互斥。长任务可跨周期重叠，手动/定时也可重叠；有业务副作用时按业务对象 claim/锁，而非只依赖 jobs |
| jobs 故障恢复 | 运行记录写入后节点崩溃，该触发点不会自动再执行 | 任务应能在下个触发点继续处理未完成数据，或者提供明确重试/持久任务状态机 |
| 事件 ID 空洞 | `event/delivery/worker.go:391` 超过默认 5 分钟跳过空洞；先取较小 ID 的事务可能迟提交 | 若要求严格至少一次，迟到事件不能永远越过；应持久化逐事件/投递领取状态或使用可重扫窗口。普通短事务下不能声称必然丢事件 |
| 余额缓存提交窗口 | `billing/ledger.go:74`、`:172`、`:199`：DB 提交后更新 Redis；余额缓存 TTL 10 分钟 | 节点在提交后、缓存更新前退出，其他节点可继续按旧余额准入。当前系统本就允许缓存准入与短时透支；若希望严格/快速收敛，需要可靠失效或原子预占，ledger_id 只能防已到达更新倒退 |
| moderation 全局额度 | `max_concurrency`、`queue_size` 文案明确“每个节点” | N 倍总容量符合当前契约，不能当 bug；若要保护一个共享审核账号，另设计集群额度 |
| moderation 请求合并 | singleflight 仅本机，共享 KV 只缓存结果 | 冷缓存时不同节点可重复调用 LLM；属于成本优化，可按策略和文本 hash 合并，不能把所有审核串行化 |
| 广播 | Redis Pub/Sub，无持久确认/重放，过载可丢 | 仅作为变化提示；权威状态入共享存储，版本/周期刷新兜底 |
| guard webhook | 有 lock 时全集群节流；未授权或锁服务失败时降级本地冷却 | 这是明确的可用性选择。若业务要求绝不重复告警，应采用持久投递记录/接收方幂等，并明确故障时是否停发 |
| 视频裸 ID 命名空间 | `video.go:149` 冲突会覆盖账号与用户 | 不同 relay 若返回相同 ID 可发生归属覆盖；未发现真实碰撞样本，归为设计风险。统一任务模型应使用内部 ID/上游身份命名空间 |
| SDK 能力上报 | `sdk/pluginsdk/serve.go:189` 未给 rank-only 实现正确上报 scheduler.rank.v1 | P3 信息一致性缺陷；宿主实际仍按 manifest 建立路径，不是视频硬绑定的充分修复 |

## 6. 已有保护与旧结论修正

- 核心迁移、插件 schema 创建和 SQL 迁移有数据库串行化保护；迁移 checksum 防止修改已应用迁移。
- 核心锁使用同一 Redis 命名空间，owner token 比较释放；使用 `KeepLock` 的调用点在续期丢失时取消工作 context，实际工作仍须遵守取消。插件锁隔离命名空间，新旧版本共享该插件空间。
- 正常 rollout 提交/完成与接管有数据库 CAS 和数据库时间；F07 是失败分支的遗漏。
- 事件投递按插件持锁、原地续期、游标 CAS；插件仍需按 event ID 幂等。
- 定时任务的数据库唯一索引有效防止同触发点双跑。
- 普通用量结算、预扣和补退有事务与账本幂等键；多个节点执行 RetryPending 不等于重复扣款。
- 账号快照有 epoch 防旧回填；凭证更新锁行并检查快照版本；last_used_at 单调更新无需全集群单例。
- 权限版本保存在 PG，修改共用 authz_meta 锁，广播之外有轮询；最后超级管理员等路径已有锁保护。

**修正“reserved 回滚后无人处理”：** 当前初始 usage、预扣和 pending entry 在一个事务内（`usage/settler.go:339`、`:472`）。后续结算事务失败时原 reserved 和 pending entry 保留，认领租约过期会再处理（`usage/reconcile.go:551`）。本次未确认“事务回滚导致永久孤儿”，不能继续按既成缺陷报告。插件停用/卸载、跨版本程序回退是另外的生命周期条件；不能用这个事务结论替其保证可恢复。

**修正“停用用户后 key 必然还能用 60 秒”：** Authenticate 每次还调用 authz.Can；权限查询要求用户 active，停用会推进权限版本并广播（`apikey/apikey.go:196`、`authz/service.go:263`、`iam/users.go:278`）。正常广播能阻断后续请求，丢广播通常由 30 秒权限版本轮询兜底。真正确认的缓存问题是 F10 的“单把 key 撤销旧值回填”和“用户并发限额未失效”。
