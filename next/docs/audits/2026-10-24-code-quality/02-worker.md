范围：`f546fa31a..HEAD` 中 `next/plugins/ccgateway/companions/{engine,worker,contracts}` 和 `next/plugins/ccgateway/internal`。审的是这些包现在的代码，重点是这次新写或重写的部分：Worker 只运行 CLI 的 `request` 命令，native 路径、Mod 和工具目录已经删掉；同时查了这些被删功能的残留。只读审核，没有改代码。下文路径都相对于 `next/plugins/ccgateway/`。

## 摘要

- 这轮删得很干净（engine 减少约 5 万行）。新写的 `request_command.go` 拆成 admit、slot、prepare、runCLI、writeOutcome 几步，能力表 `requestCapabilityGates` 也只有一张，结构清楚。`features.WorkerPolicy`/`CLIPolicy` 把核心→Worker→CLI 的线形放进 contracts，并配了夹具，方向是对的。
- 价值最高的问题集中在**跨模块复用**：
  - CC 上下文头表、客户端 User-Agent 正则、请求 ID 正则，在插件和 engine 里各写了一份。
  - CLI 版本正则有 4 份。
  - `requestfailure` 已经有常量，但 engine 和插件里仍然写字面量。
- 真问题或接近真问题的：
  - `build_attachment_sources_v1` 现在只是 Worker 自己合成的一个别名，核心预检和 Worker 闸门的要求对不上。
  - 未固定版本、又读不到 `--ccgateway-info` 的 CLI 能正常启动并报健康，但之后每个请求都会被 409 拒绝。
  - 关闭日志或清除完整内容时，会在 `store.mu` 下遍历删除整个目录，期间所有新请求都卡在 `capture`。
- 残留：
  - Worker 的 `/admin/features` 仍以 `"native"` 和 `features.Catalog()`（整套 native 目录）作初值。
  - `features.Catalog()` 本身仍描述 EXTRA_BODY、原生 JSONL、前缀命中等已删除的机制。
  - 请求日志里有只为测试保留的“无 store / 无级别”分支。
  - Worker 配置里 `LogLevel`、`HealthTimeout` 没有任何地方使用。
  - 另有若干说法过时的注释。
- 工具检查：
  - `go vet` 通过。
  - `staticcheck` 只报了 4 处 ST1005（错误信息首字母大写：`cli_check.go:65`、`cli_management.go:209`、`runner.go:30,61`），都是给人看的报错，可以不改。
  - 以 `cmd/worker` 为入口跑 `deadcode`，engine 没有不可达函数；contracts 里报的大多被核心使用。真正无人调用的只有：`BuildAttachmentSources.RequiresWorker`、`BuildBillingSources.RequiresWorker`、`RequestIdentitySources.Mode`，以及只在测试里调用的 `ScanReferences`。
