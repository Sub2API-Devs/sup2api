## 4. 三份对拍结果

### 4.1 请求头（B vs C，同一鉴权形状）

以 a（API-key 客户端）/ f（OAuth 客户端）为例，对**官方同鉴权形状参考**比较：

| 项 | A 客户端→网关 | B Worker→上游 | C 官方直连 | 判定 |
|---|---|---|---|---|
| 头集合与顺序 | 13 个（含网关私有 `X-Ccgateway-*`、`X-Request-Id`） | **24 个，名称与顺序与 C 完全相同** | 24 个 | ✅ 完全一致（B 的 24 个头 = 官方 `sF`/SDK 生成的默认头 + 上下文头） |
| `user-agent` | `claude-cli/2.1.304 (external, sdk-cli)` | 原样 | 原样 | ✅ 一致 |
| `authorization` / `x-api-key` | 网关 Key | 账号自己的 OAuth `Bearer`（回放里是假令牌） | 官方自己的令牌 | ✅ 账号替换（设计） |
| `x-app`、`x-stainless-*`、`accept`、`accept-encoding`、`anthropic-dangerous-direct-browser-access`、`anthropic-version` | — | 原生重算 | 同 | ✅ 一致（`x-stainless-timeout=600`，非旧稿的 3600） |
| `x-claude-code-session-id` | 有 | **与 body `metadata.user_id.session_id` 完全相同**（映射值） | 与 body 一致（客户端原值） | ✅ 一致（映射是设计；值与 body 自洽） |
| `x-claude-code-request-class` / `agent-type` / `agent-id` | 有（subagent 场景） | **原值保留**；子代理三个头都在 | 同 | ✅ 一致 |
| `anthropic-beta` | 客户端 8 项（无 `oauth-2025-04-20` / `extended-cache-ttl`） | 与 C(OAuth) **集合完全相同**（10 项） | 10 项 | ⚠️ **顺序不同，且只在特定组合下出现**（见下） |
| 网关私有头泄漏（`X-Ccgateway-*`、`x-request-id`、`x-api-key`=网关 Key） | — | **0 处** | — | ✅ 无泄漏（9/9 请求） |

**beta 顺序差异的限定条件**（据 wf-offline 在 v23 上的 pass17 反证）：出口 beta = `normalizeBetas(客户端, 原生新增, oauth)` 的首次出现顺序（`cli-mods/request-options.js:2-17`，调用点 `request-build.js:243` / `request-options.js:96`）。因此**只有当客户端自己的 beta 表不含 `oauth-2025-04-20` / `extended-cache-ttl-2025-04-11`**（即客户端以 API-key 形状接入、账号是 OAuth）时，这两项才会被追加到末尾，产生顺序差异；若客户端本身是 OAuth 形状（自带这两项），A/B 五十余个请求（主线程/子代理/压缩/两轮）beta **逐位相同**。本次生产用的正是 API-key 形状客户端 + OAuth 账号 31，命中了该组合。故此项降级为「场景相关」，不是普遍缺陷。

另一条同类归因：`mid-conversation-system-clear-at-2026-08-21` 在生产对照里缺失，是**入站就缺失**（同一 ELF 对自定义 base URL 不发这个 beta），与网关无关，不计入网关差异。

### 4.5 非 CC 请求（e）

客户端只发 `{model,max_tokens,system:"Answer concisely.",messages:[…]}`；出口被原生 CLI 重建成：

| 出口变化 | 值 | 判定 |
|---|---|---|
| `system` 字符串 → 数组 | 插入计费头块 + `You are a Claude agent, built on Anthropic's Claude Agent SDK.` + 原 system | 设计（非 CC 走原生主线程形态） |
| 计费头 | `cc_version=2.1.304.e6a; cc_entrypoint=sdk-cli; cch=00000; cc_prompt_id=<派生>; cc_turn_origin=sdk; …` | ⚠️ **D2**：`cch=00000`，官方运行时必为 5 位 hex（已知边界） |
| `thinking` / `temperature` | 补 `{"type":"disabled"}`、`temperature:1` | 原生默认；**`temperature` 是模型相关**：sonnet-4-6 / haiku-4-5 补 `1`，opus-4-8 不补（wf-offline 01 §3.2 6b 实测；本次 e 场景用 haiku-4-5，符合该规则） |
| `tools` / `metadata` / `diagnostics` | 无 | 原生主线程不带 |
| 键顺序 | `model,messages,system,…`（与客户端 `model,max_tokens,system,messages` 不同） | 原生构造器顺序 |
| `anthropic-beta` | `prompt-caching-scope,extended-cache-ttl,cache-diagnosis,oauth-2025-04-20` | 按注入层生成，与官方 13 项差异大 |

结论：非 CC 请求**本来就不与官方客户端一致**（设计如此，`REQUEST-HEADERS.md` 已写明），差异集中在计费头 `cch` 与原生默认字段；没有出现「非 CC 请求被当成子代理」的旧问题（v23 已修）。

### 4.6 fallback-credit beta（g，新发现）

普通 Messages 请求带 `anthropic-beta: fallback-credit-2026-06-01,fallback-credit-2026-07-01,server-side-fallback-2026-06-01,server-side-fallback-2026-07-01`（无 token、无 fallbacks）：

- 核心给它加 `X-Ccgateway-Fallback-Credit-Track: 1` + 资源 principal/generation 头，Worker 转成 CLI 请求，**上游 200**（Worker 日志有真实 ratelimit 响应头）。
- 核心随后在 `observeFallbackCredit` 校验响应里的资源身份头，Worker 不回写这些头 → `fallback credit issuer evidence mismatch` → **客户端拿到 502 `upstream_error` / "upstream response could not be converted"**（核心 `gateway/fallback_credit.go:155`，`forward.go` 转换失败分支）。
- 两次复现一致。即：**任何带 fallback-credit beta 的请求都会 502，且已经白打一次上游**。官方客户端基线里不含这些 beta，正常 CC 流量不受影响，但这是核心与 Worker 的契约缺口（静态核对 D3 的实测确认；wf-static 已按本次复现定为 P1）。
- 触达面：触发条件是 `credits.Enabled(betas)`（`contracts/credits/prompt.go:28-38`），**只认三个名字** `fallback-credit-2026-06-01`、`fallback-credit-2026-07-01`、`server-side-fallback-2026-07-01`，不需要 token。
- **名单不对称的实测边界**（2026-10-24 追加，真实上游各 1 次）：只带 `server-side-fallback-2026-06-01` → **200 正常通过**；只带 `fallback-credit-2026-07-01` → **502**。原因是 `features/betas.go:18-21` 把 `server-side-fallback-2026-06-01` 标为 `forward`（会原样过网关并告知上游），但 `credits.Enabled` 的名单里没有它，于是不进 credit 路径、也就不会断言失败。两个名单需要一起对齐，否则同一个"fallback"族里四个名字的行为不一致。
- 修法二选一（与 wf-static 一致）：核心对 CCGateway 账号不发这两类头、不做该断言；或 Worker 按 `resources.Identity` 回写资源身份响应头。

### 4.7 辅助请求

本链路未观察到标题/摘要等辅助请求（`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`；wf-offline 基线 07 在允许非必要流量时也没有）。`provider_helper_records` 生产库当前 `expires_at > now()` 记录为 **0**，因此静态核对 R8（helper history 会让客户端 400）在现网**不成立**。
