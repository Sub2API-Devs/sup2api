## 0. 一句话现状

用户想把 CCGateway 改成“**每个账号一个容器，容器里是 Claude Code CLI + 我们的 HTTP 服务；插件按账号直接把请求转给该账号的容器；去掉文件通信；顺便清理旧代码，代码要抽象、复用、解耦、低嵌套、简洁**”。
这次会话写了一个从零开始的新服务 `tools/ccgateway-worker/`，**它目前不能完成任何一次模型调用**，而且丢掉了原 `tools/ccgateway/` 里几乎全部已验证的逻辑。用户对此明确不满（原话：“原来的逻辑抄过来都不会？”）。

**建议接手者先读第 3 节，再决定是继续 worker 还是改为在 `tools/ccgateway/` 上原地改造（推荐后者，理由见 6.1）。**

## 1. 用户的目标与已经拍板的决定（按对话顺序整理）

这些是用户在对话中明确说过或确认过的，不要再推翻：

1. **不用 gRPC 常驻 CLI**：调研结论是 Claude Code 2.1.288 没有 gRPC / `agent serve` 之类的服务模式，只能每次 `exec claude -p --input-format stream-json --output-format stream-json`，通过 stdin/stdout 走 stream-json 协议。（会话前期我曾错误地声称存在 `claude agent serve`，已被 agent 调研否定。）
2. **一个账号 = 一个容器 = 一份 CC 授权 = 一份历史**。用户原话：“每个cc work一个cc客户端一个授权 一个容器”。
3. **不需要 gateway manager / 负载均衡层**。用户原话：“sup2api 每个账号对应一个cc容器，调度时指定账号，然后ccgateway就调度到指定账号不需要所谓均衡负载”。账号选择由核心现有调度完成，插件只按 account → 容器地址转发。
4. **容器内的服务直接读写 CC 的历史会话文件**（`~/.claude` 下的 JSONL），封装好即可。用户原话：“直接操作历史会话文件吧 封装好就行了”。
5. **Mod 的配置与回调不要再走临时文件**（ready 文件、system 文件、ack 文件、tool-deferral 文件），改为只有 Mod 能看到的环境变量 + HTTP 回调。用户原话：“mod 配置文件中的所有配置能不能直接用只有mod能访问到的环境变量？”
6. **授权方式不变**：容器内 CC 通过 OAuth 授权，或配置 API Key；授权在**账号管理列表里**完成（现有草稿运行时 + 授权流程），不是手工 `docker exec claude auth login`。用户原话：“cli 我们是 oauth授权 或者配置apikey 需要在账号管理列表中去授权”。
7. **旧代码要清理，不留“狗屎旧代码”**；代码规范：抽象、复用、解耦、低嵌套、简洁。
8. 用户要求用 **agent team** 合理分工做，而不是主会话全包；过程要有文档记录方案、进度、规划。

## 2. 现有系统里**已经存在**的东西（接手前必须知道）

这一点这次会话没有充分认识到：**用户要的架构，现有系统已经实现了一大半。**

| 组件 | 位置 | 作用 |
|---|---|---|
| 每账号业务容器（Go HTTP + Claude Code 2.1.288） | `tools/ccgateway/`（镜像 `ccgateway:0.1.x`，例如 cc-max 上的 `ccg-21-app`） | 就是“容器里装 CC + 我们的 HTTP 代理”。完整实现了 stream-json 协议、initialize 握手、权限回调、SDK MCP 虚拟工具、原生历史续聊/分支/重建、client system 消息还原中继、附件过滤、结构化输出、ToolSearch、请求日志、上游错误透传、OAuth 管理接口等 |
| Mod | `tools/ccgateway/mod/hooks/register.js` + `hooks.json` | 拦截工具执行、附加 system、过滤附件、控制轮次。**目前通过文件与 Go 侧通信**（见 2.1） |
| 控制器 | `tools/ccgateway/runtime/`（镜像 `ccg-controller:0.1.45`，容器 `ccg-controller`） | 每个 runtime key 一组：app 容器 + egress(sing-box) 容器 + 内部网络 + 数据卷；接口 `PUT /accounts/<key>/config`、`DELETE /accounts/<key>`、转发 `/accounts/<id>/v1/messages`。只监听回环，Bearer 密钥。见 `tools/ccgateway/runtime/README.md` |
| 核心侧 CCGateway 服务 | `next/server/internal/ccgateway/` | SSH 远程连接、草稿运行时、授权、重授权、代理同步、请求日志、用量等 |
| 插件 | `next/plugins/ccgateway/` | `managed` / `apikey` 两种账号类型。`BuildUpstreamRequest` 返回**虚拟地址** `https://ccgateway.internal/v1/messages`，由核心识别后经受限传输（SSH）送到控制器 |
| 运行时表 | 迁移 `0032_ccgateway_runtimes.sql` | runtime key（账号 id 或草稿 key `d`+16hex）与账号的绑定 |

**当前链路**：客户端 → 核心调度选中账号 → 插件返回虚拟地址 → 核心经 SSH 到远端控制器 → 控制器转发到 `ccg-<key>-app:8787/v1/messages` → 容器内 Go 服务 exec CLI。

**用户目标链路**：客户端 → 核心调度选中账号 → 插件 → 直接 HTTP 到该账号容器。差别主要在“去掉中间这一层（SSH + 控制器转发）”以及“Mod 去文件化”，而不是重写容器内的业务逻辑。

### 2.1 现在用文件通信的点（要改成环境变量 / HTTP 的就是这些）

- `CCGATEWAY_READY_FILE`：Mod `session.start` 写 `ccgateway-v1`，Go 侧 `checkMod()` 读（`runner_session.go`）
- `CCGATEWAY_SYSTEM_FILE`：Go 写待附加的 system 文本 JSON，Mod `prompt.submit` 读
- `CCGATEWAY_SYSTEM_ACK_FILE`：Mod 写 `ccgateway-system-v1:<n>`，Go 读核对
- `CCGATEWAY_TOOL_DEFERRAL_FILE`：Go 写 deferred 工具表，Mod `tool.describe` 读
- `CCGATEWAY_DEBUG_FILE`、`CCGATEWAY_ATTACHMENT_TRACE`：调试用，同样是文件

设置位置：`tools/ccgateway/runner_config.go`（`newRunConfig` / `cliEnv`）。

## 5. 关键技术事实（照抄原实现即可，不要再踩坑）

Claude Code 2.1.288 CLI，`-p` 模式：
- 不存在 `--max-tokens`、`--plugin`、`--import-snapshot`、`--session`、`--stream-json`（单独）这些参数
- `max_tokens` 用环境变量 `CLAUDE_CODE_MAX_OUTPUT_TOKENS`
- Mod 目录用 `--plugin-dir <dir>`
- 模型用 `--model=<值>`（等号形式，防参数注入）
- `--resume` 在 `-p` 下只接受 **session ID 或标题**，不接受任意文件路径；原实现是把原生 JSONL 写到 CLI 自己的会话目录、用 `--resume <path或id>` + `--resume-session-at <assistant uuid>` + `--fork-session --session-id <新id>` 组合（看 `tools/ccgateway/history.go` 的 `prepareHistory`/`resumeFrom` 和 `runner_config.go` 的 `cliArgs`）
- 新会话用 `--session-id <uuid>`
- 输入必须是 stream-json 帧：先 `{"type":"control_request","request_id":...,"request":{"subtype":"initialize",...}}`，收到成功的 `control_response` 后再发 `{"type":"user","session_id":...,"uuid":...,"parent_tool_use_id":null,"message":{...}}`（看 `runner_session.go` 的 `run` / `onControlResponse`）
- 完整参数清单与环境变量：`runner_config.go` 的 `cliArgs` 与 `cliEnv`，直接复用，不要自己拼
- 容器镜像：`node:22-bookworm-slim` + `npm i -g @anthropic-ai/claude-code@2.1.288`，非 root 用户 `node`，`CLAUDE_CONFIG_DIR=/work/config`（看 `tools/ccgateway/Dockerfile`）
- 本机是 Windows（Git Bash / PowerShell），没有 docker、没有 make；`-race` 需要 cgo，本机跑不了；Linux 专属代码要 `GOOS=linux go vet`。测试类容器一律走 compose（CONTRACTS §2）

## 6. 建议的下一步

### 6.1 方向选择（需要用户确认）

**推荐：放弃 `tools/ccgateway-worker` 这条从零重写的路线，在 `tools/ccgateway/` 上原地改造。**理由：
- 容器内“CC + HTTP 服务、按账号隔离授权与历史”已经由 `tools/ccgateway` + 控制器实现并在生产验证过
- worker 要追平需要把 runner / history / system_restore / outbound_relay / accumulator / mod 全部搬过来，等于复制一份再删旧的，违背“不留旧代码”
- 用户真正要改的是：链路（插件直连账号容器，去掉中间层）和 Mod 去文件化，这些都能在原代码上做

如果用户仍坚持独立 worker，那 worker 的 `internal/worker` 必须直接移植 `runner*.go`、`history.go`、`system_restore.go`、`outbound_relay.go` 等，而不是重新发明。

### 6.2 原地改造的大致拆分（供 agent team 分工，一个 Go 模块同时只给一个 agent 写）

1. **Mod 去文件化**（`tools/ccgateway/mod/hooks/register.js` + `runner_config.go` + `runner_session.go`）
   - system 文本、tool deferral 改成环境变量（只注入给该 CLI 子进程）；注意环境变量长度上限，原实现对最后一轮 system 有 100k/200k 字符限制，要确认放进环境变量是否安全，不行就保留 stdin/控制帧方案
   - ready / ack 改成 Mod 回调 Go 侧回环 HTTP（每个请求一个随机端口或一个带 token 的路径），Go 侧等待回调而不是读文件
   - 先查清 Mod SDK 的 `$` 是否提供网络能力（有没有 `fetch`）；没有的话 HTTP 回调不可行，要换方案
   - 保留现有 fail-closed 语义（Mod 没确认就不放行响应）
2. **链路**：确认“插件直连账号容器”在网络上是否可行（容器只有内部网络 + egress，控制器只监听回环，核心与运行时不在同一主机，靠 SSH）。直连意味着要给容器暴露端口或建隧道，并重新设计鉴权。这是架构决定，**先和用户确认目标链路的网络形态再动手**
3. **清理**：删除 `tools/ccgateway-worker/`（或至少删其虚假文档和嵌套目录），删除本目录里不可信的规划文档或标注作废
4. **验证**：真实 CLI 测试（`CCG_REAL_CLI`）必须跑，不允许 Skip；附件过滤 `TestAttachmentSourcePolicy` 补跑
5. **部署**：按 ovh 的既定流程（核心镜像 + manifest 复制到 publish + **import** + primary-first plan），先解决 3.1 的 preflight 404
