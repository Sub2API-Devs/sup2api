## 一、项目背景

### 当前问题

1. **独立工具** - CCGateway 作为独立工具运行，未与 sup2api 账号体系集成
2. **手动管理** - 账号、分组、调度需要手动配置
3. **监控缺失** - 无统一监控、日志、计费
4. **技术债务** - 旧代码存在临时文件通信、深度嵌套等问题

### 目标状态

1. **统一架构** - CCGateway 作为标准插件，与其他账号类型（Anthropic、OpenAI）一致
2. **自动调度** - sup2api 核心负责账号选择、负载均衡、限流
3. **完整监控** - 统一的监控、日志、计费系统
4. **零技术债** - 重构而非搬运，不留狗屎代码

### 2.2 架构决策记录（ADR）

已确立 4 个关键架构决策：

#### ADR-001: 不需要 Gateway Manager 层 ✅
- **决策：** 插件直接访问 Worker，无需 Manager 中间层
- **理由：** sup2api 核心已有账号调度，Manager 只是透明代理，无业务价值
- **影响：** 架构更简洁，延迟更低，故障点更少

#### ADR-002: 账号与 Worker 容器一对一绑定 ✅
- **决策：** 每个 sup2api 账号对应一个独立的 CC Worker 容器
- **理由：** 隔离授权、隔离历史、故障隔离、易于管理
- **影响：** 容器数量 = 账号数量，资源消耗较高但可接受

#### ADR-003: 零文件通信，使用环境变量 + HTTP 回调 ✅
- **决策：** 改用环境变量传递配置，HTTP 回调接收 Mod 信号
- **理由：** 更清晰、更可靠、更易测试、符合容器化最佳实践
- **影响：** Mod 代码需改造（约 50 行变化），Worker 需启动 HTTP 服务

#### ADR-004: Worker 直接操作历史文件，不引入共享存储 ✅
- **决策：** Worker 是唯一的文件操作者，每个 Worker 有独立数据卷
- **理由：** 避免并发冲突、性能更好、易于备份、故障隔离
- **影响：** 续聊到不同 Worker 需导入历史（首次 ~100ms）

### 2.3 代码规范制定

确立 5 大原则：

1. **抽象** - 识别通用模式，定义清晰接口
2. **复用** - 提取公共代码，避免重复
3. **解耦** - 依赖注入，接口隔离，事件驱动
4. **低嵌套** - 提前返回，小函数组合（< 3 层嵌套）
5. **简洁** - YAGNI，避免过度设计

**质量门禁：**
- 单元测试覆盖率 > 80%
- 圈复杂度 < 15
- 函数长度 < 50 行
- 嵌套深度 < 3 层
- 无 golangci-lint 警告

### 2.4 旧代码清理计划

**清理策略：**
- **D+0** - 新代码上线（灰度期：新旧并行）
- **D+7** - 新代码全量（旧代码停止但保留）
- **D+14** - 移至 archive/（生产环境删除）
- **D+30** - 确认无回滚需求
- **D+60** - 永久删除（从代码库删除）

**重构决策矩阵：**
- `runner.go` → **重构**（核心逻辑清晰，需要分层）
- `mod/hooks/register.js` → **重写**（改用 HTTP 回调）
- `inline_system_*.go` → **重构**（逻辑正确，整合到协议层）
