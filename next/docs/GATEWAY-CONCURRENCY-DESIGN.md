# 网关并发控制设计（参考旧版 sub2api）

状态：待用户确认，尚未实现。2026-11-04。

旧版指 `backend/`：`handler/gateway_helper.go`、`service/gateway_scheduling.go`、`service/concurrency_service.go`、`repository/concurrency_cache.go`。新平台指 `next/server/internal/`：`cluster/slots.go`、`gateway/dispatch.go`。

## 1. 结论

保留新平台的槽位存储，把旧版的两个行为搬过来：

1. **账号满了先排队，不立刻换号或报错。** 这是旧版和新平台最大的差别。
2. **并发统计出问题时，不切断正在跑的请求。** 旧版的槽位过期不影响请求，新平台会取消请求。

新平台的槽位存储比旧版好，不退回去：有续期，节点死后约 45 秒回收，而旧版的孤儿槽要等 30 分钟 TTL；还有模型列表并发，旧版没有。

## 2. 两边的差异

| 项目 | 旧版 | 新平台现状 | 本方案 |
|---|---|---|---|
| 账号满时 | 粘性账号排队，否则选一个账号排队 | 换下一个账号，全满返回 429 或 529 | 照旧版排队（§3） |
| 粘性账号满时 | 等最多 120 秒，最多 3 个排队 | `failover` 立刻改绑，提示缓存失效 | 照旧版，先等 |
| 排队上限 | 粘性 3 个，兜底每账号 100 个 | 无排队 | 同旧版，可配置 |
| 重试节奏 | 100ms 起，×1.5，上限 2s，±20% 抖动 | 无（WebSocket 后续轮次固定 200ms） | 照旧版 |
| 等待时保活 | 流式每 10 秒发 SSE ping | 无排队，所以不需要 | 第三期（§5） |
| 选排队账号 | 优先级 → 负载率 → 最久未用 | 无 | 同优先级内选负载率最低 |
| 选号顺序 | 负载感知 | 权重随机（§18.2，dynweight 依赖） | 不变，只影响排队账号 |
| 槽位寿命 | 30 分钟 TTL，不续期 | 5 分钟 TTL，每 5 秒续期 | 不变 |
| 槽位丢失时 | 请求继续跑 | 取消请求 | 照旧版（§4） |
| 释放失败时 | 打日志，等 TTL | 打日志，等 TTL | 加重试（§4） |
| 上限为 0 | 不占槽，不访问 Redis | 占槽，用于显示 | 占槽，但 Redis 出错时放行（决定 D） |
| 流式空闲超时 | 默认 180 秒 | 默认不限 | 照旧版（§4） |
| 用户级并发 | 有，排队 30 秒，队列 = 上限 + 20 | 已移除，只有 Key 级，满了立刻 429 | 决定 C |

## 3. 排队

### 3.1 流程

`pick` 现在只返回“有账号”或“忙”。改成在“忙”且原因是并发满时，同时给出排队计划。

1. **粘性绑定的账号并发满：** 这个账号就是排队目标，用粘性参数。
2. **没有粘性绑定，候选全满：** 取最高优先级层里负载率最低的账号，用兜底参数。负载率 = (在用 + 排队) ÷ 上限。读取可缓存 200 毫秒，和旧版一致。
3. **排队已满：**
   - 粘性账号的排队满了：`failover` 规则走普通调度，`stick` 规则返回 429。
   - 兜底账号的排队满了：返回 429，code 为 `queue_full`。
4. **等待：** 按退避节奏重试占槽，占到后退出排队。
5. **占到之后：** 回到现有流程（`TryHit` 检查 RPM、TPM、会话）。限流拒绝就换号。同时重新检查账号是否还能用，因为等待期间可能进入冷却或被禁用。
6. **超时：** 粘性账号超时后，`failover` 规则走普通调度，这次不再排队，`stick` 规则返回 429。兜底账号超时后返回 429。
7. **客户端断开：** 立即退出排队，记录 499。

限流满的账号不排队，因为等几秒通常没用。排队不计入重试次数，也不占账号的 RPM。

### 3.2 默认值

取旧版配置的默认值，放进网关设置，可在后台修改。

| 设置 | 默认 |
|---|---|
| 粘性最长等待 | 120 秒 |
| 粘性每账号最多排队 | 3 |
| 兜底最长等待 | 30 秒 |
| 兜底每账号最多排队 | 100 |

设为 0 时关闭对应的排队，行为回到现状。

### 3.3 排队计数

旧版用 `INCR` 加 TTL。进程崩溃后计数会留到 TTL 到期。

这里直接复用槽位：kind 用 `account-wait`，上限是最大排队数。排队的请求占一个 `slot:account-wait:{id}`，占到账号槽后释放。这样不用新写 Lua，节点死亡回收和续期都现成，计数也不会泄漏。

粘性和兜底共用一个计数。粘性上限是 3，兜底上限是 100，所以排队已有 3 个以上时，粘性请求不再等，和旧版一致。

### 3.4 模型列表

每次重试都同时占账号槽和列表槽，失败就都释放，不会持有账号槽去等列表槽。排队计数按账号算。

### 3.5 显示

账号和模型列表的 `rate_usage` 新增 `waiting`。账号页的并发列显示为 `3/5 · 等待 2`。使用记录新增 `queue_wait_ms`。

## 4. 槽位不再影响在跑的请求

旧版的原则：并发只是准入控制，请求一旦开始，统计出问题也不切断。

### 4.1 改动

| 情况 | 现状 | 改后 |
|---|---|---|
| 续期命令出错 | 立即取消请求 | 打日志和计数，下一轮再试 |
| 成员已不存在（被回收、Redis 重启） | 取消请求 | 重新写入成员，可能短暂超过上限；打日志和计数 |
| 本地到期定时器 | 取消请求 | 去掉 |
| 释放时 `ZREM` 失败 | 打日志，等 TTL | 放进队列，由 `Slots.Run` 重试直到成功或成员过期 |

这样 CONTRACTS §78.4 的这几条一起消失：续期出错取消请求、租约丢失被当成客户端取消、PG 卡住导致请求被取消。`dispatch` 和 `forward` 不用再区分“租约丢失”和“客户端取消”。

### 4.2 代价

- Redis 重启或节点被误判死亡后，并发可能短暂超过上限，直到在跑的请求结束。这也是旧版的行为。
- 节点确实和集群失联时，它上面的请求会继续跑完。节点隔离仍由 `g.healthy()` 拦截新请求。

`CONTRACTS` §7 和 `ARCHITECTURE` §2.3 写着“失去成员即取消”，但我没查到写明原因的记录。如果当初是为了严格保证不超发，请告诉我（决定 A）。

### 4.3 兜底超时

这两项防止槽位被卡死的请求一直占着：

- **流式空闲超时默认 180 秒**，和旧版一致，仍可按全局、分组、账号覆盖。图片这类长间隔端点由所属层覆盖（旧版是 900 秒）。
- **写客户端加 deadline**：每次写设 60 秒。旧版没有这一项，但新平台审核发现客户端不读数据时槽位会一直被占。

WebSocket 进行中的一轮也要受空闲超时约束，现在它忽略 idle。

## 5. 等待时保活（第三期）

流式请求排队时，客户端长时间收不到数据，部分代理和客户端会断开。旧版每 10 秒发一次 ping。

难点在于第一次 ping 就发出了 200 和响应头，之后：

- 失败只能用 SSE 错误事件告诉客户端，不能再返回 429。
- 新平台靠 `Writer.Written()` 判断“响应已提交，不再换号”，要改成区分“只发过 ping”和“已转发上游数据”。旧版有 `gatewayStreamHasOnlyHeartbeats` 做这件事。
- ping 格式按平台声明：Anthropic 用 `{"type":"ping"}`，OpenAI 用 SSE 注释，其余不发。

只在等待超过 10 秒时才开始发，大多数排队不会提交响应头。

## 6. 分期

| 期 | 内容 | 风险 |
|---|---|---|
| 一 | §4：槽位不切断请求、释放重试、空闲和写超时 | 低，主要是删逻辑 |
| 二 | §3：排队、负载选择、`waiting` 显示；顺带修 `stick` 规则的 429 | 中，改变满载时的行为 |
| 三 | §5：等待时 ping | 中，涉及响应提交状态 |

每期单独合入、单独部署。第一期不依赖后两期，建议先上。

## 7. 测试

- **槽位：** 注入续期错误后请求继续跑；成员被删后自动写回；`ZREM` 失败后恢复，槽位很快归零。
- **排队：** 粘性满时等到空位并保持绑定；排队满返回 429；超时后按规则走；客户端断开立即退出且排队计数归零；节点死后排队计数被回收。
- **并发：** 真实 Valkey 上多节点压测，确认任何时刻 `in_use` 不超过上限，请求全部结束后 `in_use` 和 `waiting` 都归零。
- **对比：** 灰度时观察 429、529 比例、粘性命中率和 `queue_wait_ms`。

## 8. 待决定

- **A. 槽位丢失是否切断请求：** 建议不切断。
- **B. 第一版是否带等待 ping：** 建议不带，放第三期。第二期上线后，流式请求最多可能 120 秒收不到数据，要确认线上代理的超时够长。
- **C. API Key 并发满时：** 建议保持立刻 429，因为这是 Key 的主人自己设的上限，§60 也这样写。旧版的用户级排队（30 秒，队列 = 上限 + 20）可以以后按需加。
- **D. 上限为 0 且 Redis 出错时：** 建议放行。这样没配并发上限的账号不受 Redis 影响，但 RPM、TPM 计数也要同样放行才有意义，要和 §78.2 一起改。
