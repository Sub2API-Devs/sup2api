## 2. 设计原则与取舍

1. **布局和信息架构照 sub2api，组件和样式用 next 现有的。**
   - 组件用 `@sub2api/ui`：SStatCard、SChart（ECharts）、STable、STabs、SSegmented。
   - 图表库不换成 chart.js。
2. **sub2api 有、但 next 没有对应业务的，不照搬**：订阅、平台日/周/月配额、推理强度、按次/图片/视频计费类型、批量生图、渠道状态、模型广场、邀请返利。
   - 对应位置留给插件：`PluginSlot`，以及插件自己的菜单。
3. **一页一个时间范围。** 卡片、图表、表格共用同一个范围和同一个时区。
   - 时区固定用浏览器的 IANA 名称，以 `tz` 参数传给服务端。
   - 服务端用它划分日和小时。默认 UTC，兼容旧调用。
4. **不用双 Y 轴。**
   - sub2api 的 Token 趋势（右轴是命中率）和 next 现在的每日图（请求数 + 费用）都是双轴。读者会把两条线的交点、高低当成有意义的比较。
   - 改为两种做法：一个主图（Token 构成）加一排同宽的小图（请求数 / 费用 / 缓存命中率），横轴对齐、各自一个纵轴；或者用页签切换指标。
5. **自助接口继续隐藏上游信息。**
   - 现有 `hideUpstream()` 的规则不变：用户页没有账号、上游协议、上游模型维度。
   - 端点分布只看入站端点。
6. **管理员看不到别人的 API Key。**
   - 这是现有规则（apikey-owner-only）。
   - 管理员的排行按用户聚合，不做按 Key 的排行，也不显示别人 Key 的名称分布。
7. **统计不引入日志写入。**
   - 一律从 `usage_logs` 查询。
   - 如果以后要做汇总表，在结算的同一事务里维护（见 §7），不另起日志通道。

## 3. 信息架构

### 3.1 普通用户（只有 `user` 角色权限）

侧边栏平铺，不显示分组标题，顺序与 sub2api 相同：

```
仪表盘        /dashboard              （所有登录用户）
API 密钥      /me/api-keys            apikey:self:manage
使用记录      /me/usage               usage:self:read   页签：用量明细 / 错误请求 / 余额变动 / 调用 IP
── 插件菜单 ──                       （充值、兑换码等，由插件声明）
个人资料      /me/profile             （新增，P3：基本信息、修改密码、余额）
```

**实现**
- 平铺由前端判断（实现时改的，接口不变）：菜单里没有网关、财务、系统任何一个分组时，侧边栏不画「我的账户」的分组标题（`layouts/AppSidebar.vue`）。插件分组照常有标题。
- 菜单文案改成与 sub2api 一致：「概览」→「仪表盘」，「API Key」→「API 密钥」。
- `/me/stats` 改为重定向到 `/me/usage`，其内容并入使用记录页顶部（§4.2）。
- 菜单项 `my-stats` 删除。

### 3.2 管理员

保持现有的分组（概览 / 网关 / 系统 / 插件），只调整两处：
- 「我的」分组改名「我的账户」，与 sub2api 相同，收 API 密钥、使用记录、个人资料。
- 管理员的「仪表盘」显示全站数据（§4.4），不再出现「我的今日请求」这种混合卡片。

页面顶栏不再重复标题：标题只在 `SPageHeader` 里出现一次，顶栏只放面包屑或留空（审计里提过的重复问题）。

**统计卡的口径**（数据一次取齐，都来自 `GET /me/usage/overview`，§6.2）

| 卡片 | 主值 | 副文字 |
|---|---|---|
| 余额 | `balance` | 可用；有充值插件时显示「充值」链接 |
| API 密钥 | 总数 | 启用数 |
| 今日请求 | 今日请求数 | 「近 30 天 n」；旁边 ▲/▼ 与昨日对比 |
| 今日消费 | 今日 `total_cost` | 原价（倍率 ≠ 1 时才显示）· 近 30 天费用 |
| 今日 Token | 输入 + 输出 + 缓存读 + 缓存写 | 三项分列 |
| 缓存命中率 | `cache_read / prompt_tokens` | 今日；`prompt_tokens` 为空（语义未知）时显示「—」 |
| RPM / TPM | 近 5 分钟平均 | — |
| 平均响应 | 今日平均首 token | 平均总耗时 |

**关于「累计」**
- sub2api 的「总计」是全部历史。在 next 里，这意味着按用户扫全部 `usage_logs`。
- 所以统一改成「近 30 天」。API 密钥页的「累计」也一起改（§4.3）。
- 「累计」以后若有汇总表（§7）再加回来。

**图表**
- 下方图表跟随页面的时间范围，默认近 7 天、按天。
- 跨度 ≤ 1 天时自动按小时；用户可以手动切回。
- 「最近使用」取 `/me/usage?page_size=5`。不要像 sub2api 那样先取 100 条再截前 5 条。

### 4.2 使用记录（用户）`/me/usage`（画面 ②）

页面从上到下：

1. **页头**：标题，右侧放「刷新」「导出 CSV」。
2. **筛选卡**，一行，所有内容共用：
   - 时间范围、粒度、API 密钥、模型、分组、状态。
   - 「更多筛选」保留现有字段：端点、协议、请求 ID、客户端请求 ID、状态码、错误类型、流式、计费状态。
3. **统计卡 4 张**，用 `UsageSummaryCards`，内容改成 sub2api 的样子：
   - 总请求数（成功率）。
   - 总 Token（输入 / 输出 / 缓存，ⓘ 弹出缓存读 / 写明细）。
   - 总消费（原价划线，倍率 ≠ 1 时才显示）。
   - 平均耗时（首 token / 总耗时）。
4. **图表区**：标题旁有「收起」，状态记住在 localStorage。
   - 第一行：模型分布 + API 密钥分布。都是环图加表，可切 Token / 费用。
   - 第二行：Token 使用趋势，加三张小图。
5. **页签**：
   - **用量明细**：现在的 `UsageTable`，保留展开详情、列设置、移动端卡片。
   - **错误请求**：同一个表，固定 `success=false`，默认显示错误类型和状态码列。next 的失败请求本来就在 `usage_logs` 里，不需要 sub2api 那张单独的错误表。
   - **余额变动**：现在的 `MyLedgerTab`。
   - **调用 IP**：现在的 `UsageIPPanel`。原来是工具栏上的开关，默认开着，挤占了表格上方的位置，所以挪成页签。

页签同步到 URL `?tab=`；旧链接 `?tab=ledger` 照常能用。

**与现在相比去掉的**：工具栏上的「趋势」「调用 IP」两个开关，以及 `UsageStatsBar` 的 5 个小块。这些功能由第 3、4 步的统计卡和图表代替。

### 4.3 API 密钥 `/me/api-keys`（画面 ③）

**用量列**照 sub2api，显示「今日 $x · n 次」和「近 30 天 $x · n 次」。
- 查询从 `from=1970` 改为 `from=now-30d`。

**新增「用量」抽屉**：点用量单元格打开。
- 抽屉内放 7 / 30 / 90 天切换、每日费用柱图、按模型表。
- 数据来自 `GET /me/usage/summary?api_key_id=&group_by=day&tz=`，已有接口加 `tz` 即可。
- sub2api 后端有 `/user/api-keys/:id/usage/daily`，但前端从未调用，这里补上这个用法。

限速、额度两列不变。

### 4.4 管理员仪表盘 `/dashboard`（画面 ④）

**第一行统计卡**
- 今日请求：成功率，▲/▼ 与昨日对比。
- 今日收入：原价，近 30 天。
- 活跃用户：今日有请求的用户数，加今日新增用户数。
- 可用账号 x / y：异常 z。用 `COUNT` 查询，不再只数前 200 个，修 P0-5。

**第二行统计卡**
- 今日 Token、缓存命中率、RPM / TPM、平均响应。

**图表区**
- Token 使用趋势与小图，与用户仪表盘相同。
- 模型分布：环图，可切 Token / 费用。
- **用户消费榜 Top 10**：横向条形图加表，按费用排序，其余合并为「其他」。点一行跳到 `/usage?user_id=…&from=…&to=…`。
  - sub2api 的「Top 12 用户趋势」是 12 条折线叠在一起，分不清，不做。
  - 想看单个用户的趋势，就从排行点进去。
- 「分组分布」用条形图。

**其他**
- `PluginSlot name="dashboard.widgets"` 保留，放在统计卡之后。
- 卡片按权限显示：
  - 没有 `usage:all:read` 的管理员只看到自己有权限的卡片。
  - 只有 `usage:self:read` 的用户走 §4.1。
- 这个区分在前端做，规则是：有 `usage:all:read` 就显示管理员版。

### 4.5 管理员使用记录 `/usage`（画面 ⑤）

与 §4.2 用同一个组件，管理员多出以下内容：

**分布图**
- 模型分布可切来源：请求模型 / 上游模型（`group_by=upstream_model`，仅管理员）。
- 分组分布、用户分布（代替用户页的 API 密钥分布）。

**页签**
- 用量明细、错误请求、**用户排行**、调用 IP。
- 用户排行显示 Top 20 / 50 / 100 / 200，各列可排序：请求数、输入、输出、缓存、总 Token、费用。前三名加金 / 银 / 铜标记。点一行就筛选这个用户。

**统计卡**：「总消费」旁边显示原价与倍率。sub2api 的「成本」（账号成本）next 没有对应数据，不做。

**导出**：CSV，见 §6.4。不做 Excel，避免引入 `xlsx` 依赖。

- 浅色：相邻 CVD ΔE 最差 9.1，正常视觉最差 19.6，全部通过。
- 深色：分别为 8.4 和 19.3，全部通过。
- 浅色有 3 个槽位对白底对比不足 3:1。规则要求可见标签或表格，分布卡本来就带表，满足。

**规则**
- 颜色跟着实体走，不跟名次走：同一个模型在各图里颜色相同。按名称哈希分槽，同现有 `UsageTable` 的模型点。
- 筛选后剩下的系列不重新上色。
- 「成功 / 失败」用状态色（emerald / red），并且配图标或文字，不用分类色。
- 文字一律用前景色，不用系列色。

## 6. 接口

所有改动都在 `next/server/internal/usage/`，权限沿用 `usage:self:read` / `usage:all:read`。契约写进 CONTRACTS §66。

### 6.1 `GET /me/usage/summary`、`GET /usage/summary` 扩展

**新参数 `tz`**
- IANA 名称，用 `time.LoadLocation` 校验，非法时回 400。
- 默认 `UTC`，与现在相同。
- 日、小时分组改为 `to_char(u.created_at AT TIME ZONE $tz, …)`。

**新的 `group_by` 取值**
- `hour`：`YYYY-MM-DD HH:00`，跨度上限 31 天，超过回 400。
- `none`：只返回一行合计，key 为 `""`。
- `group`（分组名）、`endpoint`、`platform`。
- `upstream_model`：仅管理员；自助接口回 400。

**新参数 `order`、`limit`**
- `order=cost|requests|tokens`，`limit` ≤ 200。
- 只对 `user` / `model` / `api_key` / `group` 生效，用于排行。
- 超出 `limit` 的部分另返回一行 `key="__other__"`，前端显示为「其他」。

**每行新增字段**
- `standard_cost`：`sum(total_cost / NULLIF(rate_multiplier, 0))`，倍率为 0 的行按 0 计。
- `latency_ms_avg`、`first_token_ms_avg`：只算成功请求。
- `total_tokens`。

### 6.2 新接口 `GET /me/usage/overview`、`GET /usage/overview`

**用户版**：一次返回仪表盘第一、二行需要的全部数据，代替前端现在的拼凑式调用。

```json
{
  "tz": "Asia/Shanghai",
  "today":     { "requests": 1284, "success": 1270, "input_tokens": 0, "output_tokens": 0,
                 "cache_read_tokens": 0, "cache_creation_tokens": 0, "prompt_tokens": 0,
                 "total_cost": "3.86", "standard_cost": "4.83",
                 "latency_ms_avg": 12400, "first_token_ms_avg": 1800 },
  "yesterday": { "...": "同上" },
  "last_30d":  { "...": "同上" },
  "last_5m":   { "requests": 60, "tokens": 241000 },
  "api_keys":  { "total": 3, "active": 2 }
}
```

- `today` / `yesterday` 按 `tz` 划分；`last_30d` 是今天加前 29 个日历日，与日期选择的「近 30 天」一致。
- 实现时去掉了 `balance`：控制台顶栏本来就取 `/me/balance`，仪表盘直接用它。

**管理员版**多出以下字段：
- `users {total, new_today, active_today}`：要求有 `user:read` 才给。
- `accounts {total, available, error}`：要求有账号读取权限才给。

管理员版结果在 Valkey 里缓存 30 秒。键里带 `tz`，用整分钟作时间戳。

### 6.3 API 密钥页的用量

前端把 `from=1970` 改成 `from=now-30d`，不需要新接口。

### 6.4 导出 `GET /me/usage/export`、`GET /usage/export`

- 参数与列表相同，另加 `format=csv`。
- 服务端用游标分页流式写出，不像 sub2api 那样由前端循环翻页拼 CSV。
- 上限 100,000 行，超过时在末尾写一行提示。
- 文件带 UTF-8 BOM，以 `= + - @` 开头的单元格前加 `'`，防公式注入。
- 列头用中文，跟随界面语言。
- 用户版的列不含账号和上游信息，复用 `hideUpstream`。
- 文件名：`usage_<from>_<to>.csv`。
- 每次导出都写审计。

### 6.5 顺带修的前后端不一致

| 问题 | 做法 |
|---|---|
| `MyLedgerTab` 读 `updated_at`，但服务端从不给，「更新于」永远不显示 | 删掉这行 |
| `UsageSummaryRow` 的 TypeScript 类型缺 `anomalies`、`estimated`、`estimated_cost`、`user_email` | 补上 |
| `KeyUsageCell` 和 `/v1/usage` 的「今天」口径不同 | 都改成显式 `tz`；`/v1/usage` 接受 `timezone` 参数，与 sub2api 同名，默认 UTC |

## 7. 性能

**现状**
- `usage_logs` 有 `(user_id, created_at DESC)`、`(created_at DESC)`、`(api_key_id, …)` 索引。
- 没有任何汇总表。

**用户侧查询**：都带 `user_id` 和时间范围，走索引。一个月几万行的用户在毫秒到百毫秒级，不需要汇总表。

**管理员侧查询**：近 30 天全站 `GROUP BY` 是范围扫描。

**做法**
1. **P1 / P2**：直接查。
   - 管理员仪表盘缓存 30 秒（§6.2）。
   - 每个统计查询 `SET LOCAL statement_timeout = '5s'`，超时回 503 和明确的错误，界面显示错误状态而不是 0（审计 P0-7）。
2. **上线 P2 前**：在 Supabase 上对 `overview` 和 `summary(group_by=model, 30d)` 跑 `EXPLAIN ANALYZE`，记录行数与耗时。
3. **P3，只有实测超过 1 秒才做**：建 `usage_rollup_hourly` 表。
   - 列：`hour, user_id, api_key_id, group_id, model, platform`，加计数和求和列。
   - 在结算事务里 `INSERT … ON CONFLICT DO UPDATE` 维护，并配一个回填命令。
   - 只服务无自由文本筛选的查询；带 `model_contains`、`client_ip` 这类筛选时仍查明细表。
   - 有了它，「累计」可以加回来。
