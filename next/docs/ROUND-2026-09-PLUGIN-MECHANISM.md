# 这一轮的前因后果：一个插件需求如何变成核心契约的五期改造

> 2026-09-29 ~ 2026-09-30。分支 `feat/next-platform`。
> 这份文档讲**为什么**。要查**是什么**，去 [CONTRACTS](CONTRACTS.md) §25 / §26（落地记录，按契约条目组织）；要查当初**怎么设计的**，去 [PLUGIN-EXECUTES-CORE-RECORDS](PLUGIN-EXECUTES-CORE-RECORDS.md) 和 [PLUGIN-VOLCENGINE-ARK](PLUGIN-VOLCENGINE-ARK.md)。
> 那三份是参考资料，密度高但没有时间线。这份是时间线，读完能回答「当初为什么这么定」。

---

## 1. 起点：一个听起来很小的需求

> 「把字节火山方舟、豆包通用 / 豆包视频一起弄成一个新插件，支持自定义 baseurl、素材端点。现在 new-api 那边是拆成两个渠道类型的。」

字面上的要求三条：**合并成一个插件**、**自定义 baseurl**、**素材端点**。

探索完 new-api 的实现之后，这三条本身都不难：

| 要求 | 在 sup2api 的插件模型里怎么表达 | 难度 |
|---|---|---|
| 合并成一个插件 | 一个 manifest 声明多个平台、多个端点即可。new-api 拆成两个渠道类型是它的渠道模型所限，不是上游的约束 | 无 |
| 自定义 baseurl | 账号类型的 `base_url` 字段，已有机制 | 无 |
| 素材端点 | 插件自己的 HTTP 路由 + 自己的表，已有机制 | 无 |

所以一到三期（对话 / 图片 / 素材库）**没有依赖任何核心改动**，可以独立发布。

**难的是第四类东西：豆包视频。** 而它暴露的不是「这个插件不好写」，是**核心的插件契约表达不了一整类上游**。

---

## 2. 第一个真正的发现：四个口子都堵着

Seedance 视频是**异步任务**：提交返回 `{"id": "..."}`，几十秒到几分钟后才有结果和真实用量。把它套进当时的核心契约，四处同时卡死：

### 2.1 模型提取：端点根本声明不出来

端点必须能拿到模型——核心要用它做分组白名单、价格、候选账号的 `models` 过滤、使用记录。当时只有两种取法：`request.modelPath`（请求体 gjson）或 `request.modelParam`（路径参数）。

而**查询任务状态的请求里没有模型**——只有 task id。于是这个端点声明不出来。

> 用户当时一句话点中了要害：「核心应该给插件提取模型名称的 api 来让插件实现吧？不然怎么声明端点的」

### 2.2 用量提取：声明式规则表达不了

当时用量只能靠 manifest 里的声明式 gjson 规则（`UsageRules`）。视频的用量是 `帧数 × 输出宽 × 输出高 / 1024`——**一个需要计算的量，而且计算要用到请求里的参数**。gjson 路径表达不了乘法。

### 2.3 异步 / 延迟结算：完全没有

`usage_logs.request_id` 是唯一键，一次请求一行，秒级结算完。**没有「先记一笔、稍后核实」这个概念。**

### 2.4 预扣费：完全没有

请求前只做余额检查（`CheckBalance`），允许短暂透支。所以**用户可以用 $0 余额提交 1000 个视频任务**——每一个都会真的发往上游、真的产生成本，而账上一分钱都收不到。

### 2.5 另外两个当时已核实的硬约束

- `HostService` 只有 log / kv / db.schema / authz / ledger / broadcast——**插件没有任何列账号、读凭证的接口**（`accounts.read` 这个权限在非测试代码里从未被使用）。所以插件不能自己挑账号发请求。
- `core.PlatformBinding` 是 `{Plugin, Builtin, Platform}`，**没有 `Client`**。核心只握着「账号类型所属插件」的句柄，调不到「声明该平台的插件」。

**这两条决定了一个看起来自然的方案走不通**：让插件自己起后台任务、自己轮询上游、自己上报用量。那条路要给插件开放「自己联网」和「写账本」两项能力。

## 3. 关键决策：插件执行，核心记录

用户给了原则，而且是完整的：

> 插件来提取模型 / 插件来进行计费，比如返回 token 信息核心来计费（系统管理员配置模型定价）/ 异步任务 插件来支持预扣费、异步核对逻辑，核心配合进行轮询调度真是扣费 / 插件来返回使用日志实体，填写相关字，核心写入使用日志
> **总之就是插件执行，核心记录。**

这条原则一旦确立，前面每个问题的解法方向就唯一了：

| | 谁知道 | 谁做主 |
|---|---|---|
| 模型在这次请求的哪里 | **插件** | — |
| 上游用了多少 token / 生成了几张图 | **插件** | — |
| 上游这个错误意味着什么 | **插件** | — |
| 这个异步任务算完成了没 | **插件** | — |
| 这个模型多少钱 | — | **核心**（管理员在价格表里配） |
| 这笔请求归谁、扣谁的钱、扣多少 | — | **核心** |
| 调度哪个账号、限不限流、能不能过 | — | **核心** |

**一句话：插件只陈述上游事实，核心据此做决定并落账。插件永远不说「扣多少钱」，只说「用了多少」。**

这不是新原则，是把既有设计推到底——价格早已归核心、由管理员配置（ARCHITECTURE 7.3）；`RankAccounts` 早已定死「核心保留最终调度权」（CONTRACTS §24）。缺的只是**用量与使用记录这一侧还只有声明式规则**。

### 3.1 这条原则直接否掉了一个方案

「插件自己起后台任务轮询」被作废。取而代之的是**核心驱动核对**：核心跑一个通用循环（它不认识「任务」，只认识「有条目待核对」），每轮问插件两件事——

```
BuildReconcileRequest  → {method, url, headers, body}   核心带着账号代理、SSRF 防护、超时去发
ParseReconcileResponse → {PENDING | SETTLED | FAILED}   核心据此落账
```

这与 `BuildTestRequest` / `BuildModelsRequest` **完全同一个模式**，而且有一个很关键的收益：

**因为核对是核心发起的，核心可以像 `BuildUpstreamRequest` 一样把账号（含凭证）传给插件。** 于是插件**不需要** `net` 权限、**不需要**列账号的接口、**不需要**自己起定时任务。**一项新能力都不用开。**

### 3.2 一个必须由人拍板的策略

核对超时（次数或时限到顶）怎么办？退钱还是不退？

用户裁定：**「超时保留预扣」**。理由是这笔调用已真实发往上游、上游侧已产生成本，核对不上通常是上游异常或任务被上游丢弃，让平台承担更不合理。同时留人工出口——管理员可以在使用记录详情里「重新核对」或「退款」。**自动策略偏向平台，人工兜底偏向用户。**

这条决策带出一个**必须钉死的实现细节**：

```sql
-- 已存在的重试索引，结算重试循环靠它捞行
CREATE INDEX usage_logs_billing_pending_idx ON usage_logs (id)
  WHERE billing_status IN ('pending', 'failed');
```

放弃核对时**绝不能**把 `billing_status` 写成 `failed`——钱已经扣过了，写 `failed` 会被这条索引**再捞一次，导致重复扣费**，而且是静默的、几分钟后、在一行没人看的记录上。正确值是 `billed`：一个金额已被算出、已被收取、并且是终值。这段注释现在活在 `keepEstimate()` 上面，是全仓库最该保留的注释之一。

## 4. 五期为什么这么切

| 期 | 内容 | 为什么必须在这个位置 |
|---|---|---|
| **A** | `RequestMeta.path_params`；`PlatformBinding.Client` | 纯增量。**一处改动，五个已有调用点同时受益**（`BuildUpstreamRequest`、`ClassifyError`、`OnGatewayRequest`、`ResolveAffinityKey`、`RankAccounts`），`ResolveModel` 是第六个 |
| **B** | `ResolveModel` + `request.modelSource`；`request.queryParams` 声明式白名单 | 解开 2.1。与 C 互不依赖 |
| **C** | `ExtractUsage` + `usage.source` + `streamEvents`；`UsageReport`；`usage_logs.plugin_detail` | 解开 2.2。**D 依赖它**——预扣搭在 `UsageReport` 上 |
| **D** | `Reservation` + `pending_settlements` + 核对循环 + `BuildReconcileRequest` / `ParseReconcileResponse` | 解开 2.3 + 2.4 |
| **E** | 三处缺口收尾（见 §6） | 只有**第一个真实使用者**才能暴露的东西 |

**没有一条带厂商或「任务」语义。** 即梦、可灵、Sora 之后都是直接复用——豆包视频只是第一个用户。这是整轮里最值钱的一点：四期是**核心投资**，不是为某个插件开的后门。

### 4.1 两条设计稿当时写错、实现时才发现的

**「`ExtractUsage` 在响应转发完之后调用，所以对客户端延迟零影响」——错。**

响应没有 `Content-Length`（chunked / SSE）时，**终止分块要等 gin handler 返回**。所以「字节发完」≠「客户端看到响应结束」。把调用留在 handler 里，客户端就实打实多等一个插件往返——**实测插件 sleep 150ms，客户端等 151.6ms**。

正确做法：`forward()` 末尾只**装配**（从池化的 gin context 里把需要的东西拷出来），真正的调用放进结算提交阶段的 goroutine，handler 立刻返回。现在有测试用「客户端耗时 < 插件 sleep」钉住。

连带必须一起挪的：TPM/TPD 的 token 计数原本紧跟 `forward()`，会用插件还没上报的（往往是 0 的）数字去记限流。

**「`query` 整个兜给插件 + 黑名单挡凭证」——错。**

黑名单永远在错的一侧：既误杀 `key_field` 这类无辜参数，又漏掉将来新发明的凭证参数名。改成端点声明 `request.queryParams` 白名单，核心只填声明过的，`auth.query` 自动排除。

## 5. 沿途挖出来的核心缺陷

这些**不是这一轮引入的**，是被这一轮照出来的。按后果分类：

### 5.1 会漏钱（静默地）

| 缺陷 | 后果 |
|---|---|
| **流式端点声明了计费但 SSE 用量规则为空** | 运行时流式只读 `UsageRules.SSE`，`JSON` 规则**从不**施加于它。每个流式请求提取零 token——请求正常应答，钱一分不计，什么都不说。已加 `check.streamUsage` 静态拦截 |
| **`billing:"free"` 与预扣静默解耦** | `initialStatus` 只在 `Billable` 为真时走 `StatusReserved`。端点填 `free` 会让整条预扣被丢弃：不写 `pending_settlements`、不预扣、不核对、**不报错**。直觉上「提交本身不产生最终用量」很容易让人填 `free`，而正确答案是 `"usage"` |
| **视频预估把 16:9 当成所有比例** | 1080p 21:9 是 2206×946 = 208.7 万像素，**比 16:9 的 207.4 万还多**——对 21:9 低估；1.0 系列 720p 16:9 实际是 1248×704 不是 1280×720——高估。两个方向同时错 |
| **参数可以藏在 prompt 里** | Ark 的七个参数除了顶层字段，**也能写成 `--rs 4k --dur 15` 挂在 `content[].text` 后面，全系模型都认，而且官方从未说明优先级**。只读顶层字段，一个用文本写法的客户端会被按 720p 默认档计费而实际渲染 4k/15s——**差 9 倍，请求一路 200** |
| **`ParseReconcileResponseRequest` 缺 `truncated`** | 核对响应被 `io.LimitReader(…, 256KiB)` **静默截断**。截断的状态文档里 `status` 在前会读出 `succeeded`、`usage` 在后被切掉读成 0 → 插件答 `SETTLED` 带 0 → **全额退款**。**这条还没修**，见 §8 |

### 5.2 会静默（声明了没人管）

| 缺陷 | 后果 |
|---|---|
| **`endpoint.response` 是死声明** | 声明了上游的响应形状，运行时**从来不读**。已让网关真的读它 |
| **图标名不校验** | manifest 里写一个不存在的图标名，运行时**不空白、不报错、零控制台输出**——画一个 `M5 5h14v14H5z` 的空心方块，和真图标 `stop` 几乎一模一样。**写错不像坏了，像故意的**。`anthropic` 就有一个不存在的 `list` |
| **`ui.pages.*.source` / `submit` 指向不存在的 route** | 空表；Save 按钮什么都不做。零报错 |
| **搜索框随数据量在能用和不能用之间切换** | `serverPaged = total > items.length` 是启发式：一页装得下时客户端过滤真的生效，超过一页同一个框立刻变哑。而三个页面里只有一个认 `?q=`，另两个**返回全量却显示成搜索结果** |
| **`anthropic /models?q=` 不转义 LIKE 元字符** | `?q=%` 返回全量目录并显示成搜索结果。`moderation` 本来就是对的，`anthropic` 是唯一例外。**还没修** |
| **`plugin_detail` / `client_error_code` 之前不存在** | 插件分类出的上游错误码在最后一步被抹成 `"upstream_error"`：Ark 的内容审核拦截和普通参数错误，到 OpenAI SDK 手里一模一样，客户端分不出「换个 prompt」和「改参数」 |

### 5.3 会崩

| 缺陷 | 后果 |
|---|---|
| **`readBody` 不查 UTF-8** | gjson 的校验**不检查 UTF-8**（`{"model":"a\xffb"}` → valid=true），而 RFC 8259 §8.1 要求 JSON 必须是 UTF-8。那个字节串会进 `RequestMeta.model`、`BuildUpstreamRequest.fields`、`PriceParams`，而 **`proto.Marshal` 拒绝非法 UTF-8** → 该请求每次插件调用都失败 → failover 全挂 → **一个 curl 就是稳定 5xx**，`usage_logs.model` 也会被 PG 拒 |
| **`sdk/platforms.Builtin()` 浅拷贝** | `copy()` 只拷了切片头，返回的结构共享底层数据。任何调用方改一处，**污染全进程** |
| **官方 SDK 的调用不接受 `ctx`** | 素材库调用全在控制台路由里，请求取消后 `DoCall` 仍占一个 goroutine 和一个 socket 最多 30 秒，而这插件的 manifest 只给了 `maxOpenFiles: 128`——**反复刷素材列表就能打满 fd**，连数据库都连不上 |
| **官方 SDK 重试非幂等的 `Create*`** | 重试一次就在上游多建一个资源，而创建路由只拿得到最后一次尝试的 id——「上游成功但索引写失败就补偿删除」这条设计**永远够不到第一个** |

### 5.4 一个仓库级陷阱

`.gitignore` 里曾有一条**裸 `scripts`**——它忽略树里**任何**叫 `scripts` 的目录。CI 脚本最初写进 `.github/scripts/` 时 git 直接当不存在，连 `git status` 都不显示。而且这不是第一次踩：`next/tools/sub2api-plugin/.gitignore` 里留着「仓库根忽略 scripts，保住本工具的 scripts」这样的注释 + `!/scripts/`。已收窄成 `/scripts/`。

同类还有一个：`next/server/web/dist/index.html` 是**被 git 跟踪**的占位文件（给 `//go:embed` 兜底），而同目录 `assets/` 被忽略。每次 `npm run build` 都会把它覆盖成引用一堆 ignored 文件的真页面——一旦提交，仓库里就有个指向不存在资源的 index.html。

## 6. E 期：只有第一个真实使用者才能暴露的三件事

四期落地、火山插件五期（视频）真的用上之后，三处口子之间对不齐的地方才显形。**这是「先做完一个真实使用者」而不是「先把契约想周全」的直接回报。**

### 6.1 `ExtractUsage` 拿不到请求体

提交请求里明明有 `resolution` / `duration`，但 `ExtractUsageRequest` 只给 `meta / account / status / headers / body(响应)`。而 Ark 的提交响应只有 `{"id": "..."}`。于是预扣的预估只能靠 `meta.model` + 保守常量猜。

**这是 B 期与 C 期的直接不对齐**：`ResolveModel` 有 `fields`，`ExtractUsage` 没有。

修法是 `Endpoint.usageRequestFields`，**声明在端点层而不是复用平台级 `requestFields`**——后者会被账号类型层整块覆盖，而 `ExtractUsage` 的被调方是平台插件。让第三个插件决定平台插件能看到什么，就是「`usage.source` 放错层」那个错误再犯一次。

顺带发现一件事：**「为这个功能多留一份请求体拷贝」这个顾虑不成立，真实开销早就存在**——`submit()` 的 goroutine 闭包捕获的是整个 `call`，所以 D 期以来整个请求体一直活到插件往返结束，图生视频那几 MB base64 也一样。新增的 `releaseBodies()` 是**净减少**。

### 6.2 `ReconcileResult` 无法表达「按预估结算」

`SETTLED` 强制带 tokens。上游 succeeded 却没返回 usage 时，插件返回 0 会把预扣**全额退掉**——等于白送一次视频。火山插件的绕法是自建 `est_tokens` 列。**每个插件都要自建这张估值表，这是核心该提供的语义。**

修法是枚举值 `SETTLED_ESTIMATE`，**不是** bool。bool 会允许 `SETTLED + keep + tokens`、`PENDING + keep`、`FAILED + keep` 三种需要靠文字解释的矛盾组合；枚举让它们不可表达。

它与「核对超时保留预扣」是**同一个落账动作**（共用 `keepEstimate()`，那段「必须写 `billed`」的注释也搬了过去），但**在行上分得开**：`anomalies.reconcile` 是 `estimated` 还是 `abandoned`——一个是「活确认干完了，只是没有数字」，一个是「没人能确认这活干了没」。运营看记录时分得清。

### 6.3 `billing:"free"` 的静默解耦

见 §5.1。校验层改成**硬错误**——原本想给 warn，但 `check` 只有 `FieldError` 没有 warning 等级，要么硬错误要么什么都没有。代价（免费端点想用插件计量做统计也被拒了）写在规则旁边。

## 7. CI 这条支线：可能是这一轮最大的收益

`next/` **一直没有 CI**——四个 workflow 没一个引用 next，「绿」全是本地跑的。这是「测试空跑很久没被发现」的根因。

补上 CI 之后的第一次运行就抓到东西：三次 run 全部失败，都挂在同一个、且唯一一个测试上。

```
--- FAIL: TestPolicyDeniesAndDialErrors
    egress_test.go:235: always-allow: <nil>
```

根因不是操作系统，**是 CI 自己把断言弄反的**。那条断言用「连 `db.internal.test:5432` 应当失败」来*间接*证明 `AlwaysAllow` 绕过了策略，而测试环境把所有 `.test` 主机解析成 `127.0.0.1`——所以它实际在连 `127.0.0.1:5432`，而 CI 的 `server` job 用 `ports: 5432:5432` 把 postgres 发布在那里（GitHub runner 上 job 不在容器里，必须这么发布）。

**这条断言从 2026-09-24 写下就是错的，距当时 HEAD 206 个 commit。** 一条「从来没在 5432 被占用的机器上跑过」的错误假设。

**这次红是 CI 的胜利，不是回归。** 由此立的三条规矩：

1. **测试不许假设某个本地端口是空闲的**，也不要用「A 失败」来间接证明「B 生效」——直接证明 B
2. **CI 红先看日志，不要先猜**（`git credential fill` 里就有能打 Actions API 的 token；主控一度断言「需要 admin 取不到」，白花了大半时间做无谓的 Linux 复现）
3. **run 级 conclusion 才是结论**（主控一度用步骤级的 grep 误报过一次「全绿」，必须更正）

顺带确认：Linux 上 `next/server` 的 `go test -v ./...` 共 **599 个 `=== RUN`，只有 1 个 SKIP**。原先怀疑的那批 `//go:build linux` 代码（seccomp / `oom_score_adj` / io_uring）都真的跑了并且都通过。

## 9. 方法论：哪些做法真的抓到了东西

这一轮用 agent team 并行推进，以下几条是**被实践反复证明有效**的，值得下一轮照做：

**1.「报告里必须指出我的设计写错或不可行的地方，直说，不要替我圆场」。** 每一轮都有 agent 靠这条抓到真东西：一条会把整列变成噪音的错误指令、`Builtin()` 的浅拷贝、`endpoint.response` 是死声明、一条 206 个 commit 没人发现的错误断言、一个 curl 就能打出的稳定 5xx、主控给的字段清单漏掉一个会低估 9 倍的入口。

**2. 同一个 Go 模块同时只让一个 agent 写。** 两个 agent 并行改同一模块时，彼此的 `go build ./...` 会看到对方的半成品，产生大量假失败，agent 会去调查不存在的问题。可安全并行的切分：核心轨（`sdk` + `server`）/ 插件轨（单个插件）/ 工程轨（`.github`、`e2e`、`deploy`）/ 前端轨（`web`）。

**3. 收紧校验规则必须设前置关卡。** 先量全量资产（三个内置平台 + 七个插件）满不满足新规则。不满足时判断是资产不规范还是规则太死，**不许为了让测试过悄悄放宽规则，也不许为了保住规则硬改资产**，两种都要显式报告。这一轮每条新规则都是零误伤落地的。

**4.「钱算错了但没人发现」这一类必须有测试证明现在会被发现。** 不是「新行为有测试」，是「旧的错误行为会被这个测试抓住」。最好的例子是那个直接把 `est_tokens` 清成 0 再跑一遍的断言——它证明的是「预估现在由核心持有」，而不是靠「旧列没了」间接推断。

**5. 替换厂商实现（尤其是加密 / 签名）必须交叉验证，而且向量要来自被替换的那一方。** 换掉官方 SDK 之前先用它真的发出两个请求、把整个请求逐字段冻结成 golden vector，自写实现必须逐字节复现。这个过程立刻暴露三个照文档写一定会写错的细节（签名头集合不是固定列表而是「四个具名 + 所有 `X-` 开头的」；`Content-Type` 实际带 `charset=utf-8` 且参与签名；`url.PathEscape` 不等价于 RFC 3986 unreserved 集）。**向量一旦要重新生成，必须再从那一方取——用新实现重算会让测试变成同义反复。** 主控另外独立复核过一次：从 Go 模块缓存取出被删掉的那个库，用同样输入独立签名，与提交的向量逐字节相同。

**6. 生成物必须有办法发现自己过期了。** `icons.json` 里记 `icons.ts` 的 sha256，Go 测试重新哈希比对。而且那个查找源文件的辅助函数**找不到就 FAIL，绝不 skip**——「找不到所以跳过」正是让一个跨模块测试绿着空跑好几个月的写法。

**7. 迁移文件是 checksum 不可变的**，改已应用的文件 = 安装硬失败。所以：列的增删一律新写迁移；**迁移文件里不要写「这一列为什么存在」**——那种注释会随语义变化而失效，而且**无法修改**。

**8. 看起来像占位符的常量，如果其实是产品决策，就在代码里说明它是定过的。** `max_reconcile_age_sec` 的 7 天、未知时长按模型上界预扣，都是决策不是随手填的数字。不写明，下一个人会当成随手填的调低。
