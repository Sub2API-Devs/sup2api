# 0.1.286 权限加固的回滚

核心 0.1.286 有两个新迁移：`0097_authz_hardening.sql` 单事务写出权限加固的最终状态（见 `docs/DESIGN-2026-11-12-AUTHZ-HARDENING.md` 发布说明），`0098_plugin_staged_grants.sql` 只新建插件待生效授予表 `plugin_staged_grants`（CONTRACTS §5.7，旧核心不读它）。回滚目标是上一版本核心 0.1.285（无迁移，schema 与 0.1.284 相同，仍是 0096）。旧核心 0.1.285 读不懂改写后的授权数据：托管核心见到库里有它不认识的迁移会拒绝启动（`app/managed_checks.go` `appliedPrefix`）；非托管核心照常启动，但不读范围授予，它的权限同步还会重新建出 `role:manage` 和旧 own 键并按旧默认值给内置 admin、operator。反向脚本 `0.1.286-authz-down.sql` 把库改回 0.1.285 的形态（表结构与只迁移到 0096 的库一致，角色与访问密钥的旧键授予与升级前一致）；0.1.285 已经在新库上启动过时照样可以跑，结果相同。

**托管部署（线上网关）不能经升级计划回到 0.1.285。** 迁移一旦提交，网关的规则是“跨数据库契约的回退被拒绝；需修复迁移或通过数据库备份恢复”（`deploy/gateway/README.md`），具体三处都会拒绝：

- 建计划：目标的 `schema_before` 必须等于当前基线的 `schema_after`（`control.Compatibility`：`target migration must start at the approved baseline schema`）。0.1.285 的签名清单不满足；按当前 schema 重签一份也过不了下面一条。
- 主节点启动目标核心：网关把源版本（0.1.286）的 `schema_after` 作为 `expected_schema_before` 交给 0.1.285，0.1.285 在自己的迁移清单里找不到这个前缀，拒绝迁移许可（`approved source schema is not a compatible prefix of embedded migrations`），与库里实际是什么形态无关。
- `sub2api-gateway rollback`（回到基线）：跨 schema 一律拒绝（`automatic baseline recovery is forbidden across schema or business protocol changes`）。另外新版本插件的 `hostCompat` 是 `>=0.1.286`，计划预检也会因插件不兼容而拦下。

所以线上出问题时首选**修复前进**：在 0.1.286 基线上发下一个核心版本（0.1.287，新迁移接在 0098 之后）。确实要回到 0.1.285，只能按网关 README 从数据库备份恢复（会丢掉恢复点之后的写入），或先改网关支持跨 schema 的回退；反向脚本只负责库这一半。下面的步骤适用于非托管部署（测试环境、生产备份验证环境、不经网关直接运行核心的部署）。

## 先判断要不要跑反向脚本

```sql
SELECT id FROM schema_migrations WHERE id = '0097_authz_hardening.sql';
```

- **没有这一行**：迁移没有提交（例如超管数量检查报错 `no super admin` / `several super admins`，整个事务已回滚），库还是 0.1.285 的形态。不要跑反向脚本。按报错处理（`sub2api admin recover-superadmin --email <要保留的超管>`）后 `resume -id <计划>` 恢复同一计划。不要用 `sub2api-gateway rollback`：它比较的是两份签名清单的 schema，0.1.286 改了 schema，回到基线一律被拒（见上）。
- **有这一行**：按下面的步骤回滚。

## 发布前记下

```sql
SELECT key, active_version FROM plugins ORDER BY key;
```

回滚时要把本次升级过的插件切回这些版本。数据库有自动备份，发布流程不另做备份。

## 回滚步骤

1. **停掉所有 0.1.286 核心**。反向脚本运行时不能有 0.1.286 核心在用这个库；0.1.285 核心要在脚本跑完后再启动（先启动了也不要紧：停掉它再跑脚本，结果相同）。
2. **跑反向脚本**（数据库属主，一个事务，失败不留半截）：

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f next/deploy/rollback/0.1.286-authz-down.sql
   ```

   脚本先检查 `0097_authz_hardening.sql` 已应用、`0098_plugin_staged_grants.sql` 之后没有更新的迁移，否则直接报错退出、什么也不改。
3. **启动 0.1.285 核心**。库里的迁移正好是它的 0001–0096，不再跑迁移；它的权限同步把只有 0.1.286 才有的核心权限标为 removed（授予保留，再次升级时恢复）。
4. **插件切回发布前的版本**：本版本升级的 6 个内置插件（anthropic、ccgateway、codex、dynweight、moderation、volcengine）新版本 `hostCompat` 都是 `>=0.1.286`，在 0.1.285 上启动失败、`/healthz` 503，内置安装器约每 20 秒重试一次（每分钟约 24 条 `plugin.upload` 审计）。用超管会话对第 0 步记下的每个本次升级过的插件调用 `POST /api/v1/plugins/:key/upgrade {"version": "<发布前的版本>"}`，几秒内恢复健康。
5. **核对**：

   ```sql
   SELECT count(*) FROM schema_migrations WHERE id >= '0097';                       -- 0
   SELECT to_regclass('role_permission_scopes'), to_regclass('role_assignable_roles'), to_regclass('plugin_staged_grants'); -- 都是 NULL
   SELECT r.key, p.key FROM role_permissions rp JOIN roles r ON r.id = rp.role_id JOIN permissions p ON p.id = rp.permission_id
   WHERE p.key LIKE '%:own:%' OR p.key = 'role:manage' ORDER BY 1, 2;               -- 旧键授予已恢复
   SELECT target_id, detail FROM audit_logs WHERE detail->>'via' = 'rollback 0.1.286' AND detail ? 'dropped';
   ```

## 脚本改回了什么

| 0.1.286 的状态 | 回滚后 | 依据 |
|---|---|---|
| 角色的 `<action>:own` 范围授予 | 旧 own 键（`account:own:read` 等）授予 | 当前授予 |
| 迁移时因已有全量键而只记审计、没有写入的 own 授予 | 旧 own 键授予（角色仍持有该全量键时） | 迁移审计 `authz.grant.migrate` `redundant` |
| 分组、指定账号或代理的范围授予 | 删除，每条写一条 `dropped` 审计 | 0.1.285 无法表达 |
| `role:define` 或 `role:assign` | `role:manage` | 当前授予 |
| 迁移从内置 admin、operator 收回的超管专属权限 | 恢复 | 迁移审计 `authz.reclaim.super_only` |
| 访问密钥里的 `<action>:own`、`role:define`/`role:assign` | 旧写法；分组、id 范围去掉 | 当前密钥，前后写审计 |
| `role_assignable_roles`、`roles.assign_custom`、`roles.defaults_rev`、`accounts.admin_locked`、`permissions.scope_type`、`role_permission_scopes`、超管唯一索引与触发器 | 删除 | — |
| 有待生效授予（`plugin_staged_grants`，同意了、尚未激活的升级版本）的插件版本 | 回到 `awaiting_consent`，每个版本写一条 `plugin.grants.withdraw` 审计（`reason = rollback`）；0.1.285 没有待生效授予，照旧需要重新同意 | 当前待生效授予 |
| `plugin_staged_grants` | 删除 | — |
| `schema_migrations` 的 `0097_authz_hardening.sql`、`0098_plugin_staged_grants.sql` | 删除 | — |

每处改动都写 `audit_logs`（系统操作者，`via = rollback 0.1.286`），最后推进 authz 版本。

## 回滚后的已知差异

- **operator 重新能定义角色**：0.1.285 只有 `role:manage`，内置 operator 持有 `role:assign` 就会拿回 `role:manage`（与升级前相同）。回滚期间需要保持“operator 不能定义角色”时，由超管在旧版角色页取消 operator 的 `role:manage`。
- **只在 0.1.286 存在的东西不保留**：可分配角色清单、管理员禁用锁、分组与 id 范围授予（审计里有原值，再次升级后可照着重新授予）。超管唯一不再由数据库保证。
- **supplier 角色留下**：0.1.286 新建的内置 supplier 角色保留（`builtin = true`），它的 own 范围已改回旧 own 键，持有它的用户照常可用；0.1.285 不认识它的默认值，不会改它。
- **审计与新权限行留下**：0.1.286 写的审计、新增的核心权限行（被 0.1.285 标为 removed）不删除。
- **首次重置清掉的授予不恢复**：0.1.286 启动同步把 `defaults_rev` 落后且无人持有的内置角色整体重置为 0.1.286 默认值（审计 `role.reset`，`detail.via = 'sync'`），默认值以外的核心授予被删除。反向脚本只按当前授予和迁移审计改回旧键、恢复第 5 步收回的超管专属权限，不读 `role.reset` 审计，所以这些被清掉的授予回滚后不会回来。线上即 operator（0 人持有）白名单外的 11 个：`balance:adjust`、`usage:settle`、`user:delete`、`user:password:reset`、`account:credential:view`、`account:settings:custom`、`account:group:bind`、`account:relay`、`price:manage`、`task:manage`、`system:update:read`（`account:credential:view:own` 改回旧键 `account:own:credential:view`）；admin 的核心授予在 0.1.285 本就是全部权限，重置只新增可分配清单，回滚后没有差异。需要恢复时可以在 0.1.285 角色页对 operator 点“恢复默认”（按 0.1.285 默认值，含这些权限），或按审计手工补回：

  ```sql
  SELECT target_id, detail->'before'->'permission_keys' FROM audit_logs
  WHERE action = 'role.reset' AND user_id IS NULL AND detail->>'via' = 'sync';
  ```

  逐个对比 `before` 与当前授予，缺的按 `INSERT INTO role_permissions ... ON CONFLICT DO NOTHING` 补回（范围写法 `<action>:own` 换成旧键），最后 `UPDATE authz_meta SET version = version + 1 WHERE id = 1;`。
- **首次补缺补上的授予留下**：0.1.286 启动同步给 `defaults_rev` 落后且有人持有的内置角色补上的默认权限（审计 `authz.sync.grant`，`detail ? 'defaults_rev'`）不撤销。它们都是 0.1.285 默认值里本来就有的（0.1.286 的 admin、operator、user 默认值是 0.1.285 默认值的子集），所以回滚后这些角色只会更接近 0.1.285 的默认；按 0.1.285 默认值、未被改过的生产库没有这样的授予。需要逐条撤销时按这些审计的 `target_id`、`detail.key` 删除对应的 `role_permissions` 行。

## 再次升级

直接再发 0.1.286。迁移会像第一次一样整体执行：旧 own 键与 `role:manage` 再次改写，内置 admin、operator 上的超管专属权限再次收回（各写审计），`roles.defaults_rev` 重新从 0 开始，启动同步再处理一次（无人持有的内置角色再次重置为默认值，有人持有的再补缺）。回滚期间删掉的分组、id 范围授予不会自动回来。

`TestAuthzHardeningRollback`（`server/internal/migrations`）在测试库上验证：从 0.1.285 形态的库升级、跑 0.1.286 权限同步、执行本脚本后，表结构与只迁移到 0096 的库一致，角色与访问密钥的旧键授予与升级前一致（首次补缺补上的授予与重置清掉的授予除外，见上：测试库里 user 多出 `balance:self:read`，无人持有的 operator 少了 `account:credential:view`、`system:update:read`），再升级的结果与第一次相同。
